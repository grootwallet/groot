# Groot design system

Status: canonical UI guidance for the current desktop/mobile application.

The approved website-alignment direction is recorded in
[`design-alignment-proposal-2026-09-08.md`](design-alignment-proposal-2026-09-08.md).
The application adopts its typography, semantic palette and geometry through the
existing components, not the concept's sample data or markup. Implementation and
verification scope are recorded in [`design-refresh-2026-09-08.md`](design-refresh-2026-09-08.md).

The symbol, application icon, identity palette, outlined Manrope 690 wordmark, and brand voice are canonical in [`brand-identity.md`](brand-identity.md). This document continues to own product layout, components, states, accessibility, and semantic color behavior.

All wallet logo placements use the shared `BrandLockup` or `BrandMark` component. Never reproduce the lowercase name with live text, position the symbol and wordmark as separate flex children, or override the internal baseline. The complete lockup is at least 96 px wide and receives at least one scaled symbol-stroke of external clear space; exact construction, padding formulas, background selection, approved surface widths, and accessibility rules live in [`brand-identity.md`](brand-identity.md#formal-lockup-construction).

## Direction

Groot combines calm, task-focused desktop density with restrained native-utility conventions. It should feel quiet, fast, and explicit about security state. Blue Ink and Warm Ivory carry the identity, Action Blue directs interaction, and restrained Signal Red marks rare identity or high-consequence emphasis. Bitcoin amber is reserved for Bitcoin-specific or attention-worthy state.

## Principles

1. One primary action per state. Secondary and destructive actions must be visually distinct.
2. Put the durable result in the page. Toasts acknowledge events but never carry the only copy of an error or success state.
   Manual-sync failures use the same concise retry banner on Overview, Activity,
   and Receive, with normal section spacing below it so the next controls never
   overlap the banner.
3. Show plain-language policy before descriptors, fingerprints, or PSBT terminology.
4. Never suggest that a coordinator can sign. Copy says which device is needed and how many signatures remain.
5. Use progressive disclosure for long addresses, xpubs, descriptors, and transaction IDs while preserving copy/export access.
6. User-facing copy always calls a participant a **signer**, never a cosigner. Legacy `cosigner` names may remain inside persisted schemas, command contracts, and implementation identifiers, but must not surface in labels, instructions, errors, accessibility text, printable views, or device fixtures.
7. Empty, loading, offline, invalid, and retry states are designed states—not exceptions. A completed read transitions immediately from its skeleton to data, an explicit empty state, or a durable retry state; empty results never remain behind an artificial loading delay.
8. Default UI copy is brief, plain, and action-led. Prefer one short sentence. Do not repeat technical values already visible nearby; move optional protocol detail behind disclosure. Keep security consequences and recovery instructions explicit, but state them once.

The desktop keyboard reference in Settings is the visible source for global shortcuts. Command on Apple desktop platforms and Ctrl elsewhere performs navigation; Command/Ctrl+L locks only the selected wallet. Command/Ctrl with plus, minus, or zero adjusts persistent app zoom in ten-percent steps within the layout-tested 80–140% range and resets it. Navigation and lock shortcuts remain inert during text entry and dialogs; zoom retains the platform-standard behavior there.

Hardware operations use the shared animated hardware-action panel wherever Groot is waiting on discovery, public-key import, device unlock, saved-identity health checks, address approval, or transaction signing. The panel names the current action, states what the user must do on the external device, exposes a polite live status to assistive technology, and respects reduced-motion preferences. Device- and network-specific instructions may refine its copy, but must not replace this common interaction pattern with a static icon or button-only spinner.

Receive-address verification uses one shared flow component for single-key and multisig wallets. It owns discovery, typed device actions, Trezor PIN transition, retry/error presentation, and the shared comparison panel. It renders the canonical address or, only for documented Regtest device families, a Rust-supplied script-equivalent `tb1` hardware-display alias selected by the hardware-display policy helper. Testnet4 Coldcard always renders the canonical `tb1` address; route code must not transform prefixes or infer the signer's active network. Coldcard-specific progress copy explains that its address is returned automatically without an approve/reject step. Every awaiting-payment row for a hardware-verifiable wallet shows its address-specific **Hardware verified** or **Hardware not verified** state directly; software wallets retain the ordinary awaiting state, and delayed policies do not imply that unsupported HWI display is available.

Signer readiness uses four reusable states: **verified** (green check and durable evidence), **current** (blue emphasis and the next available action), **deferred/setup required** (amber clock with explicit consequence), and **upcoming/unavailable** (muted but readable). Discovery **Ready** means only that a device can communicate; it must never substitute for wallet-policy verification or signature state. The shared policy-review component presents device-specific expectations plus the same complete fingerprint, origin, and public-key checklist in setup, Policy, and transaction signing.

## Foundations

- Dark Blue Ink background `#091625`, panel `#10233a`, inset `#142c47`, with warm `#f7f3e9` text. Light mode uses crisp ivory `#fbfbfa`, white panels, a paper `#f2f3f4` rail, and `#102a4c` text and primary actions.
- Freedom Blue `#1b56c5` carries selected controls; accessible theme-specific blue links, red danger and amber attention remain separate semantic tokens. Signal Red `#d3293a` is adapted to `#ff8a95` for readable dark-mode state copy. Amber uses dark `#f1d18b` on `#382d16` and light `#795200` on `#fff6df`; it is semantic, not decorative.
- Red may also provide restrained identity cues—eyebrows, locked-state labels, a two-pixel edge, or a low-chroma tint—when the copy clearly describes a neutral state. Solid red surfaces and red error copy remain reserved for destructive actions and failures.
- Locally bundled Source Sans 3 for headings and UI, system sans-serif fallback, and system monospace for identifiers. The unmodified 3.052R variable WOFF2 is 170,188 bytes, licensed under SIL OFL 1.1 with its notice shipped in `static/fonts`. `font-display: swap` never gates wallet data. No font service, new dependency or CSP origin is introduced. The outlined wordmark, trusted native secret-entry sheets and existing backup print typography remain unchanged.
- Primary UI copy is 13–16 pixels. Shared supporting copy uses `--font-size-meta: 13px` on desktop and mobile; 12-pixel type is limited to compact tags and technical identifiers, while anything smaller is reserved for print metadata or nonessential technical notation. Do not make the interface feel quieter by making required copy difficult to read.
- Shared radii are 10px for controls, 12px for inset surfaces and 20px for major panels. Joined rows keep their shared outer container, not separate cards. Pills remain limited to status/policy chips. Financial surfaces are opaque; mobile navigation does not apply blur behind its opaque background.
- Motion is limited to 140–220 ms state transitions, restrained one-pixel icon/button hover feedback, a two-pixel route-progress acknowledgement, a restrained modal-panel rise, toasts, disclosure panels, newly revealed list rows, sync indicators, and a brief modal attention response when dismissal is blocked by an active trusted-device decision. Native launch is the sole brand-motion exception: the canonical SVG lockup reveals once from left to right over 900 ms and remains on the neutral startup gate only until trusted session routing resolves, without a minimum branding delay. It never repeats during route navigation. Route progress appears immediately after navigation begins so a short data or route transition never looks like an ignored click; it never delays or replaces destination content. The modal attention response repeats for the close button, Escape, and backdrop attempts so the required on-device action cannot look like a frozen app; reduced-motion mode replaces the shake with a temporary focus-colored outline. Modal backdrops render at their final opacity immediately because animating opacity together with backdrop blur can flash in desktop webviews. On macOS the document-positioned desktop backdrop extends beneath the translucent native title bar so underlying settings never remain visible above a dialog. Desktop dialogs use the same restrained top-weighted viewport position so attention starts near the top of the window; their body scrolls internally within the viewport instead of anchoring the dialog to the underlying page position. Identical non-action toasts are coalesced while visible so a remount or repeated event cannot stack duplicate feedback; actionable toasts remain independent. Every toast is bounded by the current viewport and mobile safe-area gutter, and its title, description, and action wrap without forcing horizontal overflow. Initial wallet, transaction, and coin reads use shape-matched skeletons so the interface never presents false zero or empty states. Skeleton shimmer remains low contrast and never blocks an already rendered snapshot. Motion should clarify a state change rather than decorate a static page. `prefers-reduced-motion` removes meaningful movement and shimmer globally; the static startup mark may retain the brief security-gate hold.

Shared loading buttons retain a visible text status and `aria-busy` while
disabled. Their asymmetric ring has a distinct moving point, so long device
operations do not resemble a static or repeatedly restarting icon. Reduced
motion intentionally leaves that ring still while retaining the text status.

Warning surfaces use the shared `WarningNotice` component on every route. It owns
warning/danger tone, title/body hierarchy, optional insight tooltip, semantic role,
icon treatment, and credential-field spacing; routes provide content and actions but
must not recreate the panel markup or styling.
Its inline-action variant places duplicate-wallet navigation to the right of the
message on desktop and beneath it on mobile. Policy-review titles are vertically
centered with their icon. App Logs pagination is centered with 24px block spacing.

Tokens live in `src/app.css`. Component surfaces must use semantic tokens such as `--panel`, `--surface-control`, `--surface-inset`, and `--surface-icon`; hard-coded dark neutral backgrounds are prohibited because they break light mode. Reusable behavior belongs in `src/lib/components`; route files may compose components but must not introduce wallet policy.

Hardware-signing review dialogs are the desktop placement exception: they are
top-weighted so authoritative values begin in the user's primary reading area.
Other desktop dialogs remain centered, and mobile keeps its safe bottom-sheet
placement.

## Layout

Desktop uses a 224-pixel persistent navigation rail and a centered content area. Coordinator screens may use a main column plus a narrow safety sidebar. Mobile removes the rail, uses four fixed navigation destinations, preserves safe-area padding, and places high-frequency Receive/Send actions above the tab bar.

App logs is a Settings utility, not a separate wallet destination or navigation
item. Its only normal entry is a standalone Settings section immediately before
wallet deletion, and opening it retains the regular unlocked desktop rail or mobile
tabs with Settings selected. While native records load, the destination header and
shape-matched summary, controls, and table skeletons render immediately; the page
must never show a blank content area or a false zero-event summary. The page leads with the privacy boundary and durable
event count. The complete allowlisted category inventory is optional insight behind
the standard blue disclosure label and a chevron that turns 90 degrees when open.
Search covers event names and every displayed safe-context value; event and outcome
filtering each allow multiple selections; date order supports newest or oldest first.
Search and date order use matching 38-pixel fields with aligned visible labels;
the date selector uses a styled control surface and chevron across browser engines.
Users can switch between an accessible aligned table and readonly raw JSON, explicitly copy the
current JSON result, or export CSV/JSON. Failed rows group the safe code, stable
explanation, and allowlisted scalar details in a restrained error surface. Recovery
scan failures use the existing durable inline error pattern and show retained-history
heights when supplied. Mobile may scroll the table and raw JSON
inside bordered containers, but the page itself must not overflow horizontally.

The desktop rail ends with a quiet, tabular-numeric native build identity (`Groot v… · commit`) below network status. The same shared control remains available on shell-less welcome/setup/recovery flows and at the end of Settings, including mobile Settings, so a packaged candidate can always be identified without exposing wallet data. On setup forms it follows the content in normal page flow; on full-screen welcome overlays it uses an opaque fixed footer with reserved bottom spacing. It must never cover a setup action. Activating it copies exactly that public version-and-commit string for debugging or customer support, with inline status and a toast; no wallet, device, node, or profile data is included.

Required review sizes are 1180×780 and 390×844. At mobile width, content must have no horizontal overflow, long identifiers must truncate or wrap, and actions must remain above the keyboard/safe area.

Transaction-review action grids respond to the width of their own card, not only the window. They use three columns when the card is spacious, two at compact desktop widths, and one on mobile. Action labels remain concise and on one line; shrinking a card must never create stacked word fragments or horizontal overflow. The compact **View more details** disclosure is separated by spacing rather than a decorative divider.

## Components and states

- Dialogs use the shared `Modal` component, including a dialog opened from
  another dialog. The shared body portal, focus containment, Escape handling,
  focus restoration, complete viewport backdrop, and reference-counted page
  scroll lock must not be reimplemented in a route.

- Dialogs use the shared `Modal` component, including a dialog opened from
  another dialog. The shared body portal, focus containment, Escape handling,
  focus restoration, complete viewport backdrop, and reference-counted page
  scroll lock must not be reimplemented in a route.

Activity's upper-right manual sync uses the existing secondary sync-button
pattern, wraps beside the filter at narrow widths, and keeps loaded rows
visible during progress or error.
Activity uses the existing secondary Button for **Load more** after each 50-row
page and the existing LoadFailure pattern for retry. A later-page error keeps
earlier rows visible. Overview secondary-details loading and retry do not replace
an already visible balance. Send's completed public-identity strip remains visible
while coin snapshots or fee quotes load; identity read failures use the existing
durable retry surface and must never display a hardware wallet as a software signer.

- Buttons: default, secondary, ghost, danger, and danger-outline. Disabled means unavailable for a visible reason—not a placeholder interaction.
- Fields: visible label, optional short help, inline error. Credential fields clear after each use.
- Hardware device discovery uses `HardwareDeviceList`; flows supply their selection action, empty-state guidance, and whether readiness or rescan presentation is needed.
- A detected Trezor that requires Groot's PIN matrix shows only its model and the **Locked** state. Selecting it immediately replaces aggregate-discovery presentation with the shared targeted Trezor PIN/loading dialog; selected-device work must never continue to say that all USB signers are being scanned. Another wallet application's exclusive USB session is reported concisely and Groot never attempts to terminate or preempt that application.
- Modals: one decision or compact data-entry task; Escape/backdrop close; destructive confirmation names the consequence.
- Long modal bodies scroll independently while their headers remain visible. Every desktop dialog is top-weighted with the same bounded viewport clearance; its body, not the dialog or document, owns overflow. Nested or rapidly replaced dialogs must restore document scrolling after the last dialog closes.
- Desktop dialogs re-anchor to the visible viewport after window or fullscreen resizing; the backdrop must continue covering the complete viewport and actions must remain reachable through the internal scroll body. Mobile retains the safe-area bottom-sheet treatment.
- Hardware policy signing review shows only the step, saved signer identity, device account/policy values, optional signer keys, first-address reference, and primary action. Address-detail dialogs show one copy-safe spacing note and do not repeat the same comparison guidance below it.
- A modal whose optional details change its height preserves its initial desktop top edge so expansion grows downward instead of making the whole dialog jump. On mobile, expandable modals begin at the safe top inset and retain that position.
- Status chips: network, threshold, signer readiness, confirmation state. Color is never the only signal.
- Wallet labels use the shared `PermanentLabelTags` component everywhere they identify a receive request, payment intent, transaction, coin, or provenance source. They are compact rounded rectangles rather than status pills, wrap without widening their row, preserve every Rust-derived inherited label, and collapse to one neutral **Labels hidden** tag in discreet mode. Never flatten multiple labels into punctuation-separated prose. Signer, device, and wallet names remain ordinary text because they are identities rather than wallet labels.
- Lists: whole-row interaction only when a details view exists. Otherwise use a semantic article or informational row.
- A saved hardware signer appears once on the Policy page. Its primary row combines identity, source, latest health context, and a compact wallet-policy badge; selecting it opens one detail view containing public identity, device health, policy-registration explanation, and any setup or reverification action. Do not render a second readiness card for the same signer.
- Navigation: the current destination uses a clearly contrasting blue-tinted surface and blue edge/icon in light mode, plus `aria-current`; selection must remain obvious without relying on color alone.
- Desktop keyboard navigation uses a small global set documented under **Settings → App appearance**: primary modifier + 1/2/3/4 opens Overview/Activity/Coins/Settings, and primary modifier + Shift + R/S opens Receive/Send. The primary modifier is Command on Apple platforms and Ctrl elsewhere. Shortcuts only navigate; they never submit, sign, broadcast, discard, or lock. They are disabled while onboarding or locked, while a dialog is open, and while an input, textarea, select, or editable surface has focus.
- Wallet switching uses a compact labeled list with an explicit active state; changing profiles never implies that the target wallet is unlocked. Activating the already selected locked wallet from a global utility route opens its unlock screen, so Settings cannot trap the user. The compact desktop list automatically scrolls the active wallet into view on launch and after selection. Once selection succeeds, wallet-scoped content remounts into the target wallet's skeleton rather than retaining the previous wallet's figures while data loads. A desktop name that truncates exposes the complete name in a hover/focus tooltip. On desktop the list remains visible beside the selected wallet's focused unlock card. On mobile, unlocked Overview places a compact wallet selector beside its overflow action; its menu stays within the viewport. The unlock card never duplicates the complete wallet list, Back, or add-wallet controls. While locked, wallet-scoped navigation disappears but global Settings, theme, and network status remain available; network details distinguish verified values from information that requires unlock. When the selected network has no wallets, shell-less onboarding provides its own keyboard-focusable Settings control so the network choice cannot trap the user in that empty namespace.
- The wallet-list heading includes its count. A focused unlock card uses the wallet name as its primary heading, a red neutral `WALLET LOCKED` eyebrow, and a compact credential heads-up that is visually distinct from both the input and disabled action.
- Settings is scoped to the selected wallet. **Lock now** is the first standalone security action. Backup verification offers direct proof for users with a written copy and a separately labeled, freshly authenticated native re-presentation path for users who still need to write the recovery words down; neither path reveals recovery words or credentials in the webview. Profile switching and wallet creation remain in the persistent wallet list rather than being duplicated inside Settings.
- QR: real encoded image, high contrast, click-to-enlarge modal, and a copy fallback. Payment-request scanning uses the wider dialog treatment with a large square camera viewport and centered square guide, remaining viewport-bounded on mobile. Animated PSBT URs default to one frame per second so physical signer cameras can acquire every frame reliably. The enlarged receive view groups the address into balanced three-to-four-character visual chunks, emphasizes its opening and closing groups, and states that spacing is visual only. Copy always receives the original unmodified address. A successful copy temporarily replaces its copy glyph with a check glyph while the toast confirms the same action; this feedback applies consistently to copyable technical values.
- Bounded names and permanent labels: every visible field with a character limit shows the shared live `current/maximum` counter. Existing guidance appears before the counter in the same supporting line so users never need to discover a limit by reaching it.
- Receive and Send use a compact token input following the normal Groot field treatment. User-facing fields and headings say **Label**, not **Permanent label**; explanatory copy states immutability only where it helps the decision. Selected labels wrap inside the field; Enter, Tab, comma, and semicolon commit typed text as a token. Empty-input Backspace selects the final token before a second press removes it. Each token overlays a centered, non-scaling remove control on hover or keyboard focus without reserving inline space, while touch layouts keep the control visible. The field uses the compact control height rather than expanding before tokens wrap. A fixed-height single row below the field shows at most four recently used labels. Typing filters the selected wallet's complete label history and shows at most four matches, ranking an exact normalized match before prefixes, substrings, and recent use; an empty match set retains the row's height so the surrounding layout does not jump. Choosing a suggestion adds an in-field token and removes that label from the suggestion list; removing it restores the suggestion immediately. A truncated suggestion exposes its complete text in the shared hover/focus tooltip. One to five distinct labels may be submitted atomically; every resulting assignment is permanent. Existing and provenance-derived records may render more than five labels. Suggestions are absent while locked or discreet mode is active and are scoped to the selected wallet.
- Easy by default, with optional insight and control: each screen leads with the one consequence and action needed to continue. Derivation paths, descriptors, spending-path logic, privacy mechanics, exact transaction structure, and expert controls stay collapsed until requested or until the review step makes them actionable. Defaults remain sufficient to complete the flow safely.
- Privacy insight: address reuse uses one compact amber status badge on each affected coin row, never a blocking page-level danger state. A delayed-policy wallet places its short per-coin timeline note inside the coin list using the established compact warning treatment, never as a competing page banner. Expanded coin details lead with current spending access and its actions, then separate **Privacy & history** and **Technical details** disclosures. Linked-coin counts, provenance, confirmations, and identifiers stay in those optional groups so policy actions never compete with raw metadata.
- Keep Receive and Send visible on action-oriented wallet surfaces; mobile Activity and Settings omit the floating payment actions so they cannot cover history or controls. Place infrequent descriptor, export, and policy-lab actions in an accessible overflow menu that is never clipped by its card or viewport. Descriptor inspection leads with a standard portable multipath descriptor when one can be derived safely, then offers receive and change branches as optional detail.
- The policy-wallet overflow button is the canonical three-dot control everywhere: 38×38 pixels, horizontal 18-pixel ellipsis, neutral bordered surface, shared 10px control radius, and identical hover, focus, and expanded states. Overview uses that shared control left-aligned with its actions. A multisig Overview menu contains Activity, Coins, Policy, Show descriptors, and Export & verify. Recovery policy lab remains exclusive to Policy and appears only when the selected wallet carries a Miniscript recovery template. Other wallet kinds do not expose multisig descriptor actions. Discreet mode stays in the desktop shell for quick amount hiding; language selection belongs in Settings so the rail does not overflow at compact desktop widths.
- An active software, external-signer, or multisig proposal appears immediately above Overview's primary actions as one compact, fully clickable resume surface. Amber means the payment still needs one or more signatures; green means the threshold is complete and broadcast remains pending. It shows the payment labels and signature progress, but not the amount, recipient, or signer identities, and collapses the redundant **Resume** label on mobile while retaining the link's complete accessible name. The link identifies the exact proposal, and Send restores its authoritative recipient, labels, amount, and review/sign state rather than restarting the intent form.
- When a saved standard multisig proposal's inputs are no longer in the current wallet UTXO set, its resume surface names the unavailable-input state instead of promising signing progress. Its review remains inspectable, but the signing, PSBT transfer, and broadcast actions are replaced with an inline explanation and explicit cancellation; refresh the chain before preparing a new payment. The original proposal and transaction history remain intact.
- A pre-PSBT payment draft uses the same compact Overview position but is not one undifferentiated link: **Discard draft** and **Resume** are separate actions. The resumed Send header repeats **Discard draft** beside Back. Its destructive confirmation uses the modal description plus payment-label tags; it does not repeat the consequence in a warning panel or inventory every saved field. On mobile the two actions occupy their own full-width row without horizontal overflow.
- Optional explanations use one consistent blue disclosure label with a directional chevron when the content is longer than one short sentence. A small focusable insight control is reserved for a concise definition beside a visible label. Neither pattern may contain information required to complete the flow. Every tooltip uses an intentionally inverted high-contrast surface—a dark surface in light mode and a light surface in dark mode—with a compact four-pixel radius, no border, and a soft elevation. On touch-width layouts, optional content uses safe edge insets and cannot escape the viewport.
- Interface copy and control labels are non-selectable by default so dragging cannot highlight whole application surfaces. Editable fields and explicitly technical values—addresses, transaction IDs, URLs, descriptors, public keys, derivation paths, hashes, and recovery text—opt back into native text selection.
- Human-facing timestamps use a concise, unambiguous long-month date and local hour/minute without repeating “local time.” The native system tooltip exposes seconds, the exact IANA timezone, and the UTC equivalent on hover.
- Wallet-type choices use compact visual cards with an icon, a plain-language title, and one short consequence-focused subtitle. Do not detach explanatory lines below generic buttons.
- Multi-step wallet creation keeps a persistent labeled progress indicator visible. Completed stages use the shared light-blue check treatment, the current stage uses darker blue emphasis, and upcoming stages retain neutral numbered markers so users can estimate the remaining work without reading body copy. Sequential task groups use the same three states: completed tasks collapse behind optional detail, the one current task receives primary emphasis, and unavailable later tasks remain readable but muted with disabled controls. Routes compose `SetupProgress` and `SetupTask`; they do not recreate these semantics locally.
- Collection surfaces use the shared empty-state pattern after a successful zero-item read. Overview uses a compact message, while full Activity and Coins pages use the larger treatment. Skeletons represent an outstanding read only, and an offline or failed read replaces them with a durable explanation and retry action.
- Balance displays use only the global sats/BTC denomination and derive from integer satoshis. Do not add fiat estimates, price charts, or market-provider controls without a new privacy decision.
- Payment send flows use the same labeled three-stage progress indicator: **Intent**, **Amount & fee**, and **Review & sign**. On desktop, the Send heading and progress begin in the compact top band so the authoritative review and its actions fit without avoidable document scrolling. The header says only **Send bitcoin** for an ordinary payment; each active card carries one short task title without a repeated step number, explanatory subtitle, or decorative divider. Intent leads with the permanent payment labels before the recipient address. Advancing commits every valid trailing label into the same in-field token state, so returning from Amount & fee never loses or demotes it. Authoritative transaction, hardware, cancellation, and resume reviews render every payment label as a compact blue-tinted tag instead of collapsing the set into punctuation-delimited text. The compact hardware-signing review preserves the main review's amount-first hierarchy, `To → Label → Network → Network fee → Total` ordering, type scale, and horizontal row separators without a redundant section title. Expanded technical rows keep separators between adjacent rows, not above the first or below the last row. The signer summary occupies a narrow right-hand desktop column beside every ordinary stage and stacks above the card on mobile: software wallets identify Groot on this device; external-hardware and multisig wallets show imported labels/models and shortened public fingerprints with the required threshold. Imported identity must not be styled as live device availability. Funding-selection privacy context lives inside **View more details**, not as a second default warning. A single-purpose wallet maintenance action such as **Renew protection** omits payment progress and signer identity from its initial form; both return at authoritative review/signing, when they become actionable.
- Automatic coin selection uses three plain-language choices in both send flows: **Balanced**, **More private**, and **Lower fee**. Each choice includes its tradeoff in one line, and the active choice uses the standard blue selection outline rather than an amber warning treatment. Manual selection leads with amount and funding-label tags without repeating a “Funding labels” heading or exposing estimated input weight. Its coin rows use a restrained hover/focus surface and pointer cursor, while separators stay absent inside the compact picker. When Rust reports that the manual set creates a new privacy link and one existing group can fund the payment, the warning offers a quiet, normal-weight one-action switch to **More private** selection without silently changing the chosen coins. Coin rows and the authoritative review identify mixed/unknown provenance and address reuse without implying that a heuristic is a security guarantee. Permanent-label text is replaced with neutral hidden copy everywhere discreet mode applies.
- Amounts follow one global sats/BTC preference. The `sats` unit is always lowercase and `BTC` is always uppercase. BTC always renders eight decimals as one uninterrupted numeral with uniform size, weight, and color across every digit; zero and non-zero digits must never form separate visual runs. Transaction-review amounts and their units use the primary text color so they cannot be mistaken for disabled data. Units stay visible and tabular numerals prevent layout jitter. The large Overview balance, the unit inside single-key and multisig send amount fields, and hardware transaction-review amounts are explicit denomination toggles. Each is a real button with a visible focus treatment and an action label naming the other denomination. Other amount surfaces follow the preference without becoming competing controls.
- Single-key and multisig sends share one fee selector. Estimate provenance appears once below Economy, Standard, Priority, and Custom.
- Wallet changes, route content, live selection totals, and conditional actions use short opacity/position transitions. Motion stays subtle and never delays an authoritative security state.
- Coin rows keep inherited permanent-label tags on the same wrapping line as **Received** or **Change**. Expanded details use readable row spacing and explain provenance, privacy clusters, source payment intent, and change lineage through the shared insight control.
- Delayed-policy coin badges describe authority, not Miniscript state: **Wait starts after confirmation**, **Backup key protected**, **Recovery/heir key available in N blocks**, and **Recovery/heir key can spend**. Technical terms such as branch, relative timelock, immature, and mature remain optional detail only. A coin the extra key can spend leads with **No action is required**, then composes existing buttons for **Use recovery/heir key** and policy-specific wait restart. Fee choices and exact mechanics remain collapsed until requested; signer identity and complete transaction structure appear at review.
- Policy summarizes delayed-key access in one quiet card: a short heading with the existing insight tooltip, one explicit sentence naming how many coins the backup key can currently spend, two compact existing `info-banner` facts for normal-key coverage and the next change, one secondary **Review coins** action, and one collapsed explanation. The disclosure may list each concerned coin with its amount and established coin-status chip; these rows remain hidden by default. The card does not recreate input-like segmented controls, repeat the security consequence in nested cards, or use display-sized typography for status copy. The tooltip explains that every coin begins its own wait after confirmation.
- The Policy wallet hero presents its signing rule once with consistent vertical spacing between balance, policy, and network. Standard multisig uses one compact **N of M keys** policy tag. Recovery and Inheritance split the same established tag pattern into **N of M primary keys** and **Recovery/heir key after wait**. Invalid policy data fails closed to one **Policy details unavailable** tag. The combined policy sentence is never repeated as a headline or page chip, and prototype credentials do not appear in this summary card.
- A multisig coin that is an observed external receive output with no address metadata or label may expose one compact **No local label / Add label** row inside expanded details. Activating it opens the standard compact modal with the bounded permanent-label field and explains that this one initial assignment cannot be changed. Its text may intentionally reuse an existing wallet label. Do not turn the exceptional action into a large warning panel or compete with coin details. It is hidden in discreet mode and never appears for change or an already labeled coin. Hardware-policy address review separately calls its address a verification reference and directs funding through a labeled Receive request.
- Recovery words are concealed by default behind a private-place warning. Once explicitly revealed, their desktop grid reads down each column (1–8, 9–16, 17–24); fixed-width number and word columns keep every row aligned. Mobile uses the same column-first reading order in two columns.
- Recovery backup confirmation uses an empty numbered sequence and a shuffled word pool. Tap/click is the primary interaction; drag-and-drop is an enhancement, never the only way to reorder. Exact order marks the backup verified. **Verify later** remains visually secondary and produces a compact, persistent amber Overview/Settings status with a direct verification CTA; it never looks like successful verification.
- Long addresses, account public keys, and transaction identifiers preserve both identifying ends as `prefix…suffix` in compact rows. Activating an address or account public key reveals the full value in balanced visual groups with emphasized ends; copied data never contains display spacing.
- Hardware-policy flows use the shared instruction card and policy signer list. Device-specific differences are data and actions—not bespoke typography or signer rows. The signer list has compact fingerprint and full inspectable-identity variants; both preserve the same spacing, type scale, current-device treatment, and identifier-detail behavior across setup, Policy, and signing.
- Completed device-health and wallet-policy evidence always shows its event date and time through `LocalTimestamp`; status words alone are insufficient. Use **Public account key (xpub)** consistently, compact it as `prefix…suffix`, and open the standard grouped identifier detail when activated.
- Theme: light/dark choice is functional, local-only, and follows system preference until explicitly selected.
- Language: English, French, and Spanish are local-only preferences selected under **Settings → App appearance**, persisted across launches, and applied before first paint. All frontend product copy—including routes, dialogs, progress/error states, toasts, and accessibility names—uses the central catalog. Wallet names, labels, addresses, descriptors, transaction data, device identifiers, and other user/protocol data are never translated.
- Counts use locale-aware grammar. Never render forms such as “1 confirmations” or build translated plurals by appending an English suffix.
- Recovery words, credentials, descriptors, disabled actions, overlays, navigation, modals, and mobile controls must meet the same contrast requirements in both themes. Theme selection is applied before first paint.
- Toast: broadcast, received payment, first confirmation, copy, creation, deletion, connectivity, and recoverable failure.
- Reusable insight tooltips render through a body-level portal, remain fully inside the viewport, and support hover, focus, click, outside-click, and Escape dismissal. Dialog overflow must never clip tooltip content; routes must use the shared component instead of inline tooltip markup.
- Slow App Logs navigation immediately replaces the current route with the shared diagnostics skeleton. The destination keeps the same skeleton until native records resolve, so desktop and mobile never show a blank content pane.

- A Rust-proven wallet-owned recipient adds one calm, always-visible **Self-transfer** status and the Rust-derived **Consolidating** total above the technical disclosure. Their info tooltips explain the fee-only outflow and hardware-signer comparison. Neither ownership nor that total is inferred from labels, matching text, renderer-side address scanning, or renderer arithmetic. Inside **View more details**, **Coins spent together** shows the authoritative funding-label tags and explains the public source linkage without cluster jargon; unknown sources and reused addresses remain explicit.

## Voice

Use “bitcoin” for the asset and “Bitcoin” for the network/protocol. **Wallet** is the top-level concept for software-key, hardware-key, standard multisig, and custom-policy accounts. In every user-facing surface, call a physical signing device a **hardware signer**, never a hardware wallet: the signer holds a key, while Groot tracks and coordinates the wallet. Reserve **Hardware Wallet Interface (HWI)**, compatibility-sensitive filenames, and legacy storage identifiers for their exact technical meanings. Never use **vault** as a synonym for ordinary multisig; reserve it for a specifically defined product or policy with constrained spending paths such as timelocked recovery or inheritance. Prefer “2 of 3 signatures” to “quorum,” and “public account key” before “xpub.” Say **wallet passphrase** only for a Groot-generated software wallet; it is part of the BIP39 backup and also unlocks Groot. Say **app PIN** for multisig and hardware-signer wallets; it protects local app data and is not a hardware-signer passphrase or seed backup. Never imply that an app PIN can recover a hardware signer or that a public descriptor can spend.

Headings and controls should carry the flow whenever possible. Do not repeat a heading with a subtitle that merely restates it. Use the shortest familiar wording that preserves meaning. Keep permanent consequences and recovery instructions explicit, but move protocol detail behind optional insight.

Top-level routes render one primary page title without an eyebrow or explanatory subtitle. Wallet-specific Settings names the selected wallet directly as **{wallet name} settings**. Supporting context belongs in the relevant card, field, disclosure, or durable state rather than above the page content.

## Accessibility

- Semantic buttons/links and explicit form labels are required.
- Every enabled semantic button, link, disclosure, and role-button uses the hand cursor on pointer devices; disabled actions use the unavailable cursor.
- Interactive targets should be at least 38 pixels desktop and 44 pixels on touch layouts.
- Focus indicators must remain visible against dark panels.
- Normal text must meet WCAG AA contrast (4.5:1); primary text tokens target 7:1. Fixed black/white QR rendering is the only component-level neutral palette exception.
- Dialog title/description and keyboard dismissal are required.
- All status changes need readable text and an appropriate live region when asynchronous.
- Secrets must not be placed in accessibility labels, notifications, screenshots, or copied automatically.
