# Groot repository code-quality audit — 2026-10-18

Audit and planning only. See the [remediation plan](remediation-plan.md). No fixes, format migrations, dependency changes, release-policy updates, commits, pushes, publications or messages to other chats were performed.

## Most consequential results

1. **D1 / P1:** Core-accepted broadcasts can still become ordinary command failures when the subsequent local commit fails. All three signing paths need an explicit accepted-but-not-recorded outcome and recovery tests.
2. **D2 / P2:** Some expensive native commands still execute synchronously, including public-network fee RPC and software creation/recovery. The earlier scheduling cleanup is incomplete.
3. **D3 / P2:** Activity preserves rows on a failed next-page request, but hides them on a failed refresh of the same view.
4. **D4–D5 / P2:** Shared tooltip text lacks an accessible description relationship; scanner failures bypass localization despite the localization gate passing.
5. **V1/V2:** The mandatory validation gate correctly rejects the dirty mobile source against the reviewed 5.2 inventory. The first real-Core harness run failed during compact-filter reorg handling; a complete repeat passed. The preserved source-policy gate prevents a green validation handoff claim.

These are code-quality/correctness observations, not a security certification. No new signing-authority bypass or confirmed exploit is claimed. Historical security residuals are separated below; a future scoped vulnerability investigation must use the applicable security workflow.

## Verified defects

Priorities: P1 = address before the next affected release; P2 = targeted next maintenance work; P3 = lower-risk cleanup. Source-verified means the cited control/data flow is present; runtime triggers not executed are explicitly identified.

### D1 — P1: accepted broadcasts lose their outcome on local persistence failure

**Evidence:** `src-tauri/src/wallet/transaction_commands.rs:1581` broadcasts before the fallible database transaction at 1583–1618. `wallet/hardware_commands.rs:3210` does the same for external signers; `wallet/multisig_proposal_commands.rs:1046` calls broadcast before the fallible `commit_multisig_broadcast`; that helper's transaction/commit are at `wallet.rs:6004–6036`. Only the later sync failure is converted to `sync_pending` (`transaction_commands.rs:1619`). `wallet.rs:4233–4253` already recognizes an accepted expected txid idempotently.

**Trigger/impact:** Core accepts the exact transaction, then SQLite begin/write/snapshot/commit fails, for example under storage failure. The command returns a generic failure and the saved proposal may remain active even though the payment has left the wallet. Retrying identical bytes can reconcile an already-known tx, but recreating the payment can encourage duplicate intent. For RBF, the original-mempool precheck can also obstruct a naive retry after the replacement was accepted. This is source-verified; no disk fault was injected into a running wallet.

**Fix:** define an explicit outcome carrying the accepted txid and local-recording warning, separate from pre-acceptance failure. Never manufacture a committed snapshot. Reconcile the exact proposal/transaction on retry and reopen before inviting another payment; preserve atomic status/lineage/notifications. Design crash behavior before selecting any durable receipt mechanism.

**Validation:** fault injection after acceptance at each local write/commit boundary for software, external-signer, multisig and acceleration; UI warning/retry; restart reconciliation; exact-byte retry; no duplicate notification/lineage; successful broadcast plus failed refresh stays successful.

**History/dependencies:** refines the historical post-broadcast-success invariant (ADR 0013); existing fixes cover refresh failure, not this earlier interval. No BIP wire/policy change is needed. A result DTO may change; any new durable record needs compatibility design and ADR review. No existing format may be changed implicitly. Wallet/recovery review required; no dependency is needed. Independent of CSS/module extraction.

### D2 — P2: remaining blocking command paths violate scheduling guidance

**Evidence:** `wallet/profile_commands.rs:996–1033` is a plain `#[tauri::command] pub fn` and synchronously resolves credentials/config, checks chain identity, estimates three fees and reads the verbose mempool. `profile_commands.rs:265`, 339, 400 and 445 retain synchronous credential/native-sheet/persistence orchestration. The pinned local Tauri macro defaults to blocking command execution and directly calls the function; an IPC Promise is not a worker boundary. By contrast unlock, snapshot, sync and transaction preparation already use `spawn_blocking`.

**Trigger/impact:** slow/unavailable Core or expensive credential/storage work occupies native synchronous dispatch; wallet responsiveness and cancellation suffer. Source scheduling is verified; native stall duration has not been measured. Browser Regtest fees return constants and do not exercise this public-network path.

**Fix:** start with fee retrieval on the established blocking-worker pattern, capturing/rechecking selected identity/session around queued work. Inventory remaining synchronous commands; preserve macOS main-thread sheet dispatch, operation ordering, cancellation and zeroization rather than blindly adding async everywhere.

**Validation:** delayed RPC and large mempool fixture; native UI responsiveness; lock/switch while queued; expiry before work; worker failures; unchanged stable errors. Creation/recovery additionally need native-sheet cancellation and platform checks.

**History/dependencies:** still present from A1 of the September maintenance plan; deletion, transaction and acceleration scheduling portions are fixed. Backward compatible; no BIP/dependency/schema change. Retest affected native surfaces. Separate from M3 code movement.

### D3 — P2: failed same-view Activity refresh hides committed history

**Evidence:** `src/routes/activity/+page.svelte:54–55` reloads on a wallet update. `load(false)` sets loading and clears cursor (74–83), then assigns `loadError` on failure (108–112). Rendering chooses skeleton/error before the retained `transactions` array (239–251). `e2e/navigation-performance.spec.ts:3–29` covers next-page failure only.

**Trigger/impact:** load history successfully, then fail the Activity read after a refresh/update in the same wallet/filter/query/sort. The old rows remain in memory but disappear from the page. This contradicts product history-retention behavior. A filter change is distinct: stale rows must not masquerade as results for a different query.

**Fix:** distinguish first load, same-view refresh, query change and pagination. Keep the last committed rows for the same identity/query visible with an inline refresh error/retry; replace data/cursor only on successful response. Preserve generation checks and selected transaction behavior.

**Validation:** reject the second same-view Activity read after 50 visible rows; rows stay visible with retry, then update once. Cover query changes, pagination, wallet switch, lock and out-of-order responses at both viewports.

**History/dependencies:** related to historical retained-state work; existing next-page behavior is fixed and is not the same defect. No contract, BIP, format or dependency change; use existing LoadFailure/TxList. Independent of route extraction.

### D4 — P2: explanatory tooltip content is not linked to its trigger

**Evidence:** `src/lib/components/InsightTip.svelte:76–96` portals `role="tooltip"` text to the body, without an ID or `aria-describedby` on the button. `aria-expanded` uses `open` although focus/hover can make `visible` true. `PasswordField.svelte:43–44` uses this shared control for credential guidance.

**Trigger/impact:** a keyboard/screen-reader user focuses “More information”; the DOM provides no description relationship to the safety explanation. Actual VoiceOver announcement quality remains untested; the missing relationship is source-verified.

**Fix:** add stable per-instance tooltip identity and the appropriate description relationship while visible; align disclosure semantics with focus/hover/tap behavior. Reuse the existing component.

**Validation:** accessible description assertion with two instances, focus/blur, Escape, touch activation, modal portal and teardown; VoiceOver on the physical supported platform. Test desktop/mobile, both themes, translated long copy.

**History/dependencies:** newly recorded defect, aligned with #86's accessibility guardrails. No BIP, dependency, public DTO or persisted-format effect. No new component required. Independent of CSS split.

### D5 — P2: scanner failure and count messages escape translation checks

**Evidence:** `UrQrScanner.svelte:22`, 54–57 assign English errors; line 76 renders `{error}` directly. Line 79 builds a dynamic English key for the count. The catalog has the fragment `unique frames scanned`, not a stable parameterized full message. `scripts/quality/check-localization.mjs:166–174` inspects selected expression forms but does not trace a rendered Identifier back to assigned copy.

**Trigger/impact:** camera denied/unavailable or frame limit in FR/ES displays English guidance. Dynamic count translation also needs a stable catalog key. These paths were source-verified; no real camera permission dialog was exercised.

**Fix:** use stable error/state keys translated at render time and a parameterized count message. Add narrow detection/behavior coverage for component-owned messages without accidentally translating user/protocol data. Keep existing native UR limits and file fallback.

**Validation:** mocked denial/unavailability/frame-cap and locale switch while error remains visible; count in EN/FR/ES; localization gate regression. Physical camera tests remain separate.

**History/dependencies:** prior localization cleanups did not finish these states. No BIP/format/dependency change; no new component. Independent of mobile pairing.
