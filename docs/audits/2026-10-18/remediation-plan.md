# Groot prioritized remediation plan — 2026-10-18

Companion to the [audit report](code-quality-report.md). This is an implementation-ready backlog, not approval to implement, migrate, push or release. Finding IDs link the plan to exact evidence and validation in that report. Estimates are engineering days for one experienced maintainer, excluding physical-device scheduling, independent reviews and release work.

## Ordering and constraints

Fix observable correctness before moving its code. D1 is the first product fix; D2 and D3 are independent small fixes. Establish visual characterization before the #86 split. Extract native and hardware ownership last. Do not bundle CSS, wallet behavior, dependencies and release policy into one PR.

For each nontrivial slice, verify/create the owning issue before implementation. Existing live trackers: [#86](https://github.com/grootwallet/groot/issues/86) CSS; [#116](https://github.com/grootwallet/groot/issues/116) feedback; [#117](https://github.com/grootwallet/groot/issues/117) release/updater; [#6](https://github.com/grootwallet/groot/issues/6) mobile; [#7](https://github.com/grootwallet/groot/issues/7) compact filters. They were open when read. D1/D2 and assurance work need focused trackers, not automatic issue closure or public exploit details.

Preserve shipped 5.2.0 commit/tag/assets/trust keys. A new reviewed-source inventory is a separately reviewed, version-scoped decision; do not update existing hashes to make these PRs pass. Keep the ordinary validation failure visible while independently running skipped checks. Before a release, obtain a coherent reviewed candidate with the appropriate gates; audit documents cannot waive them.

## Phase 0 — reproducible evidence and decisions

**PR 0A, 0.5–1 day — finding characterization (V1/V2/M4).** Start from an inspected owned checkout; record commit plus dirty-tree identity if applicable. Keep fresh Core roots and separate browser ports. Add a focused reproducibility tracker for the compact-filter reorg failure at `compact_filters.rs:616`; capture safe phase/timing/result metadata, Core version and test-owned data only. The first audit run stopped with NodeStopped; a complete repeat passed. Gateway saturation passed in the current validation run; neither failure history proves a product bug.

Acceptance: deterministic reproduction or documented inability to reproduce under controlled serial and loaded runs; no blind retries, increased timeout, suppressed assertions, or wider protocol admission. Save useful diagnostic evidence before harness cleanup, avoiding wallet/peer identifiers. Existing Core/profile processes remain untouched. Also classify nonfatal Vite module-import rejections from the passing browser run; make unexpected errors fail only after known cancellation/abort cases are understood. No runtime/dependency/schema/BIP change in this slice. Review: test/harness owner. This can precede all fixes.

**Decision 0B — D1 result and crash contract, 0.5–1 day.** Specify accepted-but-local-recording-pending versus rejected/unknown outcome, authoritative txid, snapshot optionality/freshness, retry/restart reconciliation, RBF/CPFP races and durable inline copy. Inventory what the existing proposal preserves at every crash point. Prefer compatible recovery from existing data where sufficient; do not invent a new receipt schema incidentally.

Acceptance: concrete DTO/state table and failure matrix reviewed by wallet/recovery maintainers. If a new store/schema is necessary, first write an ADR, old/new fixtures and migration-versus-discard choice; obtain explicit approval for a breaking change. This is a dependency for PR 1A, not for unrelated frontend fixes.

**PR 3D — M2 adapter facets, 1–2 days.** Extract diagnostics/export first, then profile/session only if it improves ownership. ## Phase 4 — assurance, dependencies and platform gates

**PR 4A — M4 native acceptance, 3–5 days initial harness.** Use disposable profiles and a real supported Tauri runtime to exercise registration, args, serialization, stable errors, selected identity/session, lock/cancel and D1 faults. Add mobile-target tests that invoke prohibited commands and prove entropy/decryption/device/network/persistence side effects remain zero. Source-prefix guards remain as separate checks. Pairing is absent and stays out of scope. No funded profiles, signer secrets in screenshots or release claims from simulators.

**PR 4B — M4 bounded parser exploration, 1–2 days setup plus investigation.** Add seed corpus and bounded fuzz/property targets for PSBT, BSMS/descriptors and UR. Include private-material rejection, network mismatch, malformed lengths/depth, allocation limits and nonmutation. Keep reproduction seeds and sanitized crash triage; never weaken bounds to pass. Tooling dependencies need explicit supply-chain review; parser fixes need their own scoped review and BIP/compatibility assessment.

**PR 4C — M5 advisory maintenance, 1–3 days initial triage.** Inventory all 10 current warnings by transitive path, target, reachable API, upstream remedy and owner. Review compatible update candidates individually; include supply-chain/license/SBOM/native feature review, lockfile diff and target checks. Refresh full Node dev advisory evidence separately. Do not upgrade wallet/protocol/framework dependencies in a cosmetic PR or infer safety from scanner exit 0. No version change is preapproved by this plan.

**Platform evidence — #6 and #7, separate milestones.** Preserve ADR 0089 rejection and the existing 5.3 plan. Before functional mobile enrollment, approve protocol/threat-model/storage design; do not transplant old signer/continuity branches wholesale. New pairing persistence requires version/unsupported-data rules. Physical iPhone install requires inspected development signing, selected connected/unlocked device and disposable data. Android/Windows/Linux runtime/camera/filesystem/USB acceptance is separate from compilation. Compact-filter cache/recovery/peer expansion stays behind its existing ADR/issue decisions.

## Decision backlog: do not silently implement

H1 whole-Core-sync budget: measure first, then choose recovery-friendly deadline/cancellation policy. H2 PIN commit-edge behavior: fault-inject first, then select a truthful outcome without silently adding a journal migration. H3 safe-open, H4 PDF construction, H5 Xpriv wiping, H6 temporary-root policy and H7 service enrollment quotas each retain the historical explicit owner-approval boundary. These need a concrete reviewed design before any implementation decision. No deployments are authorized.

The unconfirmed-coin rule, credential minima, screenshots/native confirmation, cooldown trusted-time source, independent consensus validation and fee ceiling remain deferred product/security choices. They are not refactor tasks. No recovery passphrase may be rewritten to meet a new-creation rule.

## Common completion criteria for every implementation PR

- Exact baseline/issue, owning invariant and compatible-data statement; preserve unrelated work. References use `Refs #N`; closure needs complete merged acceptance.
- Named regression for the actual trigger, including relevant failure/retry/lock/cancel/teardown behavior. Keep established secret, release, policy and provenance gates.
- `pnpm validate` attempted and its exact result recorded. Run skipped later stages independently while the unchanged reviewed-source mismatch persists; a release still requires resolved review/authorization gates.
- Rust changes: format, locked strict all-target/all-feature Clippy/tests and affected isolated Core scenarios. Native docs/network/coverage checks when the owning scope warrants them; do not clean another task's build state.
- UI changes: browser acceptance, desktop 1180×780/mobile 390×844, light/dark, translations, keyboard/safe-area and appropriate accessible descriptions/results. Native/physical claims require their own evidence.
- Record explicit BIP no-impact or update evidence/scope in the owning guide. No dependency changes incidental to another fix; no breaking format without ADR and explicit migration-versus-discard approval.
- Independent review for transaction trust/persistence, supply-chain review for lockfiles/vendor/capabilities/release tooling, exact-device retest for hardware behavior. A new reusable UI component requires the repository's explicit verified-gap approval.

First delivery should be characterization/decision 0B, then PRs 1A–1C and the two small shared-UI fixes. The broad cleanup should proceed in measured slices after correctness is protected, with a separate reviewed candidate before any public release.
