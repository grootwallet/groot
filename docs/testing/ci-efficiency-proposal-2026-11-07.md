# Faster feedback without weaker acceptance

Proposal, 2026-11-07; refs #121. No workflow, coverage threshold, dependency or required check is changed by this document.

## Measured baseline

Read-only GitHub job metadata, not estimates from local debug tests:

| Run                                                                                                              | Expensive steps                                                                                                                                                     |
| ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Main CI 39855635323](https://github.com/grootwallet/groot/actions/runs/39855635323), released source `6a39bf50` | Core integration 1,130 s; whole-library coverage including Core 1,340 s; deterministic-core coverage 231 s; native ordinary tests 262 s; browser acceptance 1,110 s |
| [Internal packages 42373214648](https://github.com/grootwallet/groot/actions/runs/42373214648), `0ea17f63`       | Linux native validation 458 s + package build 484 s; Windows native validation 430 s + package build 725 s                                                          |

These are historical runner observations, not promised timings for a new source or machine. The package workflow currently has no Rust build-cache step. Main CI restores a cache, then runs `cargo clean` before instrumented coverage. Frontend validation runs units, and the following coverage command runs the same unit suite again. Of 107 current frontend test files, 52 read source text; these are mixed architectural guards and behavioral substitutes, not 52 automatically redundant files.

The internal Linux workflow currently recognizes its expected source-review stop by matching a log line. A CI redesign should also reject an unrelated failure occurring alongside that expected failure; test this with deliberate failure injection. Public source approval must remain failed until separately authorized.

## Recommended order

1. **Keep a small edit loop and one complete frozen-candidate run.** Agents run the affected pure/controller tests and the relevant browser flow while editing; use types/boundary checks when their inputs change. Run mandatory validation and applicable full suites once the code is stable. Preserve command, source hash, outcome and logs. Any new runtime change invalidates affected evidence. A source-policy stop stays a stop; do not hide it behind a permissive “development” command.
2. **Reuse compiled dependencies safely.** Add the already pinned Rust cache action to internal package jobs. Separate ordinary and instrumented target directories/cache keys by OS, toolchain, lockfiles and profile. Avoid cleaning the ordinary build cache to prepare coverage; clean only that coverage workspace. Keep audit/coverage tool versions pinned and cache their installations separately. Never cache profiles, signing credentials, certificates or unverified release executables. See [Cargo build cache](https://doc.rust-lang.org/cargo/reference/build-cache.html) and [GitHub cache trust boundaries](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching).
3. **Run funded Core once per full acceptance lane.** Prototype one instrumented library build: run ordinary deterministic units, report the deterministic-core thresholds **before** Core, then append all 15 isolated Core scenarios and report whole-library thresholds. Keep native all-target/all-feature and parser/integration obligations. Do not count an integration-covered core branch as a replacement for deterministic unit coverage. Removing the separate duplicate Core pass could avoid roughly 1,130 s of work in the observed run; validate the consolidated lane against the existing lane before replacing it. Timing measurements stay separate from instrumentation.
4. **Split browser work by project first.** Run desktop Chromium and mobile WebKit as independent jobs with one worker each, installing only the needed browser. Keep every case and both viewports/themes, retain failure traces and aggregate required results. Then consider splitting the large wallet-flow file by capability. File-level sharding cannot balance one oversized file well; enable test-level parallelism only after proving fixture isolation. See [Playwright CI guidance](https://playwright.dev/docs/ci) and [sharding](https://playwright.dev/docs/test-sharding).
5. **Remove duplicate unit execution and replace brittle tests gradually.** Use one coverage-enabled full frontend unit pass in the acceptance pipeline, preserving all current assertions and 100% policy coverage. Keep the simple non-coverage command for edit loops. Move asynchronous behavior assertions into small controller tests plus one meaningful browser integration case; retain source guards that enforce secret surfaces, command order and adapter boundaries. Delete a test only after naming its replacement obligation.
6. **Separate feedback, acceptance and packaging.** Fast checks fail first; heavy native/Core/coverage and browser jobs can run independently. Add explicit timeouts and timing artifacts. Keep existing cancellation of superseded runs. Conservative changed-path selection can reduce unrelated work, but changes to locks, native config, release tooling, manifests or workflow logic must trigger their complete obligations. Required aggregate checks must fail on missing/failed results. Keep full exact-candidate acceptance before handoff; do not move security-critical checks solely to a nightly schedule.

## Acceptance for a CI change

Trial each change independently on cold and warm caches. Compare the executed test inventory, coverage reports, negative fixtures, failure propagation, duration and cache trust boundaries with the current lane. Deliberately fail one relevant test to verify the aggregate remains red. Keep immutable action pins, read-only permissions, lock enforcement and source approval. Report measured improvement only after the trial; no blanket “skip slow tests” or blanket deletion of source tests is proposed.
