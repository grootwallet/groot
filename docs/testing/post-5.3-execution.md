# Post-5.3 cleanup: implementation and acceptance record

Refs #121. Goal: reduce code that becomes harder to maintain over time, preserve wallet behavior and security, improve measured performance, and avoid unnecessary app size.

This record covers implementation after the [approved plan](post-5.3-plan.md). That plan retains its historical c5bfc275 baseline; current results and limitations are recorded here. Released baseline: `6a39bf50b2a6a042354b43369765a9af2174d061` ([v5.3.0](https://github.com/grootwallet/groot/releases/tag/v5.3.0)). Starting maintenance source: `c5bfc2756752448cac35a05f08c8b0c684779124`. Application runtime source is frozen at `da7b81731173233b3576a17c020e468238f99566`. A later development-tooling fix at `5b6535f8ab2c9418f201392c1ed37d5b6b6e7ff1` restores unsigned iOS archive preparation from the approved 5.3.0 baseline; native and frontend application source remain identical. Test-only follow-ups at `641fd4addc07e40edf48473d1b726b1d2f864119` and `f4f22cd1` add the explicitly planned review, persisted-owner and composed-parser regressions. The clean final native campaign freezes all application and test source at `6a95822aae4d7f11960ccb7bfef3af5806b8d9e8`. Later reporting commits do not change runtime source. The [operation inventory](post-5.3-operation-ownership.md), [independent review](post-5.3-independent-review.md) and [final status](post-5.3-final-status.md) define the inspected scope.

## What changed

- **Safer screens:** phone decode/review/sign, multisig loading and Settings operations reject replies belonging to an old attempt, dismissed dialog or obsolete wallet/screen. A rejected wallet switch preserves the confirmed wallet's pending work. The phone-signing PIN clears immediately after dispatch. Scan pauses and busy state are released on the correct lifecycle paths.
- **Safer failures:** native cleanup preserves wallet files when registration may already have committed. Tests inject partial-write, pre-rename and post-rename directory-sync failures, SQLite transaction failures and pairing-completion failures, then reopen and retry. Completed native work is not undone merely because its screen disappeared.
- **Clearer ownership:** the existing profile, notification and recovery extractions remain intact. Shared fountain-header checks preserve the two protocols' distinct caps and errors. Full previous-transaction authentication has one pure native owner. Settings snapshot reads use WalletPort and explicit currentness; signing authority remains Rust-owned.
- **Bounded phone signing:** complete previous transactions must authenticate all input amounts/scripts. The paired signer count bounds derivation/signature maps. A conservative allowance of 109 added bytes per input must fit the actual 112,635-byte response limit before expensive signature checks and key access. Actual request/response encoder boundaries and a signed round trip are tested. Named review cases cover recipient-only acceptance, no-recipient rejection, authenticated input/output overflow and outputs exceeding inputs. There is no phone file-import fallback.
- **Measured database improvement:** reuse one prepared SQL statement within its existing bounded connection-local cache. Results are still read afresh. There is no cache of transaction approval, device identity, policy validity or wallet data.
- **Working iOS validation tooling:** the unsigned Testnet4 archive helper now accepts exactly 5.3.0 as well as existing numbered RC versions. The isolated identity, build number, no-sign/archive-only command and release checks stay unchanged. A regression first reproduced the old rejection; all 18 metadata/boundary tests then passed.
- **Better engineering checks:** controlled delayed-reply tests, fault injection, parser composition assertions, an isolated locked sanitizer workspace, repeatable production-profile measurements and package attribution. A build watcher now resolves tracked source paths from the repository root; a regression exercises the actual watcher from both working directories.

No profile, database, backup, registry, proposal, credential or pairing format changed. No migration, new signer support, new network support, dependency upgrade, signing-policy cache or panic-setting change was introduced. The package.json change registers a regression test; runtime dependency declarations are unchanged.

The earlier trilingual compatibility statement and pre-dispatch quote-cancellation check are intentional product/copy and behavior changes, not mechanical moves. Partner/Family remain experimental, and no direct USB Miniscript workflow is certified. Ordinary hardware compatibility does not imply Miniscript compatibility. Phone pairing remains standard multisig only.

## Performance and size

Measurements use the pinned toolchain on one shared Apple Silicon Mac. Owned compilers, fuzzers and coverage jobs were kept out of timing windows; unrelated user processes were left alone. These are controlled synthetic measurements, not physical phone or hardware certification.

### Accepted query improvement

The same 1,000 independent synthetic receives were measured before, after, after again and before again. Each run excludes five warmups and records 100 samples from release-profile executables. The before runtime is `4b8504bed0110efb6bcc26434df2a205e5d527c3`; after is `da7b81731173233b3576a17c020e468238f99566`. Intervening runtime changes are only the prepared-query reuse; other commits fix build/test tooling.

| Operation                                  | Before median / p95  | After median / p95 | Repeated before / after median |
| ------------------------------------------ | -------------------- | ------------------ | ------------------------------ |
| Full 1,000-transaction snapshot            | 123.669 / 130.933 ms | 85.833 / 89.567 ms | 123.819 / 85.531 ms            |
| First 50-row history page from that wallet | 83.650 / 87.020 ms   | 58.641 / 60.846 ms | 83.985 / 58.483 ms             |

This is about 30% less time in these native reads, not a 30% speedup of the whole app. SQL statement counts remain 20,007 and 13,003. Serialized full snapshot / overview / page remain 1,186,143 / 558,117 / 31,700 bytes. Process peak RSS overlaps across repeated runs (before 30.82–30.88 MB; after 29.85–31.31 MB). There is no demonstrated memory improvement or material increase in this fixture. Regression tests cover committed writes, rollback, label order, subject/connection isolation and schema failures with caching enabled and disabled.

### Other observations

A baseline/candidate/baseline-repeat comparison used the same instrumentation on `c5bfc275` and `4b8504be`. Native phone review was approximately 9.1–9.2 ms median; signing plus response encoding approximately 1.75 ms. Empty-registry durable saves varied around 10–12 ms. Uncontended operation-lock acquisition is near measurement resolution and says nothing about real contention. No signing speed improvement is claimed.

Production-built browser fixtures covered Home, Send, multisig Send, Settings, Activity and Coins on desktop Chromium and mobile WebKit, with five warmups and 100 document navigations per route/view. The observations show small mixed differences; they do not demonstrate a consistent route speedup or establish statistical equivalence. These measure first visible DOM markers, not native IPC completion or data readiness; the history fixture contains 120 rows. Native snapshot/history measurements above use 1,000 transactions. No physical device waiting or network latency is included.

Ten isolated process-cold launches per build use fresh empty Regtest profiles, a distinct app identifier and nonpersistent webview storage. The observed checkpoint is native `app_started` after window.show, not verified webview readiness; the OS file cache remains warm. Baseline/final median: 294.804 / 294.288 ms; ranges 285.675–1,329.984 / 287.764–1,129.845 ms. Main-process RSS is 105,184–105,856 / 105,296–106,224 KiB and excludes WebKit children. Ten launches do not establish p95 or a speedup. Final synthetic phone review/sign-and-QR medians are 9.194 / 1.758 ms, consistent with the earlier comparison.

Matched frontend assets against `c5bfc275`: CSS remains 315,493 raw / 63,709 gzip bytes across 50 files. Browser JavaScript increases by 3,337 raw / 894 gzip bytes; native JavaScript by 3,342 / 895. Compression is per-file gzip level 9 with the same Node/zlib and build timestamp. These are asset totals, not initial-route download sizes.

Matched isolated Regtest executables are 21,903,744 bytes at c5bfc275 and 21,903,824 bytes at da7b8173: an 80-byte increase. This is not a signed multi-network package comparison. The released app's regular files total 62,198,319 bytes: 39,967,857 hardware-runtime bytes, 21,943,792 native executable bytes (including embedded frontend), and 286,670 other bytes. Symlinks are excluded. Hardware support accounts for about 64%; removing it would risk supported workflows. No package-size saving was accepted, and no fresh signed package was produced. The released DMG is 33,104,918 bytes and ZIP is 32,981,084 bytes; these historical download sizes are not a rebuilt-candidate comparison. Download and installed sizes are distinct measures.

## What slowed verification

- Native/Continuity tests and sanitizer builds are expensive. The fixed maturity/reorg assertions and coverage thresholds were retained. The first complete coverage campaign missed function coverage; meaningful persisted-owner and composed-parser tests were added, and the clean final rerun passed the unchanged gate.
- The extended UR-composition sanitizer campaign stopped at its 512 MiB process cap after 4,948 seconds. The saved 11,712-byte input passed 1, 100, 1,000 and 10,000 fixed-input replays; peak RSS stabilized near 481 MB after 100 iterations. The failure snapshot showed 37.3 MB live heap and 66.1 MB quarantined, dominated by libFuzzer structures. This favors sanitizer/fuzzer overhead rather than a reproducible parser crash, but it does not prove the parser free of sequence-dependent memory growth. The campaign remains failed pending a fresh bounded diagnosis.
- Execution found a Cargo argument-order bug in the first fuzz wrapper: --locked reached the fuzz program after the separator. It was fixed and tested. Early smoke runs are diagnostic evidence, not proof that every subprocess was locked.
- The Apple linker rejected sanitizer initializer sections; the reviewed test-only classic-linker choice preserves ASan. The pinned nusb fuzz-only branch does not compile; --no-cfg-fuzzing exercises normal production branches with sanitizer coverage instead of upgrading dependencies.
- The source watcher used the wrong directory for Git enumeration, causing invalid watch paths and repeated native rebuilds. The narrow fix preserves source identity and clean-checkout checks.
- A browser geometry assertion ran during an existing dialog animation. It now waits for the transition before checking the same spacing bounds; 20 repetitions passed. Incorrect scanner/navigation test setup was changed to use real controls.
- The existing iOS metadata helper rejected the released 5.3.0 version. The narrow independently reviewed fix restores the documented unsigned development workflow without selecting a new version or weakening its identity/signing checks.
- One full coverage run was deliberately stopped before completion while freezing the final source. It is not counted as passing evidence.

## Source approval and physical checklist

Nine of 115 frozen source entries differ: package.json; src-tauri/build.rs; native lib.rs, registry.rs, proposal.rs, wallet.rs, wallet/profile_commands.rs; Settings and multisig/new routes. All changed/new files require review, including files outside that pin list. Hashes remain unchanged. The mandatory aggregate must remain reported as blocked until the owner approves exact source and the separate approval-only process runs; copying hashes to obtain a green result is prohibited.

Use the [physical acceptance checklist](post-5.3-maintenance.md#maintainer-physical-acceptance) on the exact desktop/phone candidate. Record model, firmware, source, observed outcome and limitations. Pending pairing cancellation/replay tests are supported; completed-pair key revocation is not implemented. Deleting a profile cannot revoke a retained Bitcoin key. Stop on inconsistent policy/address/amount/fee, unexpected signatures, lost durable state or failed recovery.
