# Groot 5.2.0-rc01 internal feedback test plan

This internal multi-network macOS Apple silicon candidate contains the feedback changes tracked in #116. The reported baseline was public Groot v0.5.1 · c731fa1c. The source branch is `codex/v0.5.2-feedback`; the displayed candidate version is exactly `5.2.0-rc01`, as requested. Existing persisted wallet/backup formats are unchanged.

Use disposable Testnet4 or Regtest wallets for destructive cases. Before removing a wallet, save its key backup, public descriptor backup and BIP329 label export. For software wallets, keep the passphrase backup separately. This test plan does not require deleting a funded production wallet.

Record each result with the candidate version/commit, network, wallet kind, device model/firmware, steps, expected versus actual behavior and elapsed time where relevant. Never attach recovery words, passphrases or PINs. Public descriptors and label files also reveal financial metadata; share redacted diagnostics where sufficient.

## 1. Install and identify the candidate

1. Quit the running Groot app before opening the internal candidate.
2. Open the supplied DMG and use the included Groot.app. This is the existing private ad-hoc signed build workflow; it is not a notarized public installer.
3. Check the sidebar build identity says `Groot v5.2.0-rc01` and matches the supplied BUILD-INFO commit. Verify the available networks match the multi-network build.
4. Open Settings/About and check current author/copyright presentation uses Rochal Holdings. Historical Git/ADR author records are intentionally retained; existing wallet names are user data.
5. Open an existing wallet and confirm its name, balance, activity and backup status still load. There is no profile migration or new file format.

## 2. First-open scan approval and privacy

1. Create a fresh wallet, or restore/import a wallet with no completed sync. On Mainnet, leave its fresh default Groot-managed connection selected.
2. On first open, expect **Approve wallet-history scan**, a genesis explanation, and a clear Groot-managed privacy disclosure. There must be no mandatory birthday/gap selector or additional passphrase prompt.
3. Choose **No, open Settings** (also test closing the dialog). Expect Settings, an unverified wallet history, and no wallet-history scan started by the scheduler. Node enrollment/health checks may still occur; wallet-script/history queries require approval.
4. Return to Overview. The declined approval should stay dismissed in that process. Use the visible scan action to reopen it deliberately.
5. Approve the scan. Expect height zero/genesis, progress, a responsive app, and verified history after completion. Check balances/activity update without reopening the wallet.
6. Repeat with your own already-configured node. The approval must disclose that connection and preserve it rather than silently replacing it with Groot managed.
7. Interrupt before completion and restart. Expect renewed approval before restarting the initial scan. A wallet with completed history should continue routine sync without a new first-scan prompt.
8. Check Settings still provides authenticated birthday and gap controls for an explicit custom scan.

## 3. Restore a 2-of-3 backup and import its original labels

1. In a disposable existing 2-of-3 multisig wallet, create several permanently labeled receive addresses. Include more than one label on an address and an address beyond the initial 20-index gap if available. Save its BSMS/Groot JSON public backup and export BIP329 JSONL labels.
2. Restore that saved backup in a clean test profile using **Recover from backup**, not the disabled timelocked Recovery creation card.
3. Expect the saved **2 of 3** threshold and saved public signer information. Do not choose a new 2-of-4 model or manually retype every key.
4. For Mainnet restore, use **Scan devices** and identify the backup signers through the device picker. Select the same standard/hidden account used originally. Exercise any required Trezor PIN prompt. A different account/key must be rejected even if its device label matches.
5. Identify the correct signer devices in a different order from the original setup. Verify the complete first receive address against the original wallet, then set the new app PIN and restore.
6. Approve the history scan, allow it to complete, and import the original JSONL. Expect compatible address labels to import without **An imported address does not belong to this wallet** merely because the presentation rows are missing or signer names differ.
7. Reimport the same file. Expect unchanged/idempotent labels, not duplicates. Request a new labeled receive address and confirm an imported address is not reused.
8. Include one known foreign address in a copy of the label file. Expect the whole import to fail and leave existing labels and receive position unchanged.
9. Current recovery search covers receive indexes 0–9,999, plus higher addresses already indexed by the native wallet. A higher unindexed address remains a bounded-search limitation; sync the matching history first. Transaction/output records still require known wallet history.
10. Repeat backup validation with Groot JSON and BSMS. Equivalent sortedmulti key ordering must still verify the same wallet and qualify its backup drill without relying only on one address.

## 4. Untested timelocked creation

1. Open Add wallet → multisig creation.
2. Expect Standard selected, with the usual 2-of-3 recipe when continuing.
3. The **Recovery** timelocked card must be visible, explain it has not been tested, and be disabled for mouse, touch and keyboard activation. Assisted recovery remains unavailable.
4. **Recover from backup** must still be available. This restores an existing standard multisig backup and is independent of the disabled card.
5. An old unfinished timelocked setup must not silently finish creation or be converted to Standard. Existing saved data remains intact.

## 5. Unknown-source address labels and Tab

1. In a multisig wallet, receive to a wallet-owned address that has no local permanent label (for example, an address shared before restoring the wallet).
2. After sync, open the coin's details and select **Add label**.
3. Type a label and press Tab. Expect a label token and an empty input while staying in the editor. Type a second label and press Tab again.
4. Save. Expect all submitted labels to appear, with the first as the primary label. Repeat with Enter and existing normal Receive label entry to compare behavior.
5. Check the existing one-to-five-label limit, normalization and immutable assignment behavior still apply. A used address cannot be relabeled to erase its history.

## 6. Detailed address and xpub grouping

1. Open a full receive-address view and a signer/xpub details view.
2. Expect blocks of four characters, with only the final block shorter. A six-character tail must be `4 + 2`, not `3 + 3`.
3. Copy each value and compare it to its original exact unspaced value. Presentation grouping must not alter copying or derivation.
4. Repeat at narrow window width and in dark mode; all characters should remain readable without horizontal overflow.

## 7. Cable identification tags

1. Scan an unlocked Ledger Nano S Plus before Groot has extracted its wallet identity.
2. Expect an amber **Select to identify** badge. Select it, follow the device prompts and verify the saved fingerprint/account matches before it becomes Ready.
3. Repeat for each available supported model: Coldcard Mk4, Ledger Nano S Plus, Trezor Model One, Trezor Safe 3, Jade, BitBox02 and BitBox02 Nova.
4. A genuinely PIN-locked selected device still needs its unlock/PIN instructions. Passive scanning alone must never establish wallet identity.
5. Wrong account, unrelated device, disconnect and rescan should retain their existing explicit error/retry behavior. This candidate is not proof of physical certification for all seven models.

## 8. Single descriptor and Sparrow interoperability

1. Open the wallet descriptor view, setup descriptor preview and backup QR/print/PDF views.
2. Expect one public descriptor containing both receive and change branches (`/<0;1>/*`), without separate receive/change panels or two QR codes.
3. Copy/export the descriptor and verify it derives both receive and change addresses in a compatible descriptor wallet. Existing Groot JSON/BSMS backup structures remain supported; their internal branch pairs are not a presentation regression.
4. Compare Groot and Sparrow standard `sortedmulti` descriptors. Textual key order and the checksum can differ while the policy is equivalent: sortedmulti sorts the derived public keys, and the checksum covers exact text.
5. Compare complete keys, key origins, threshold, network and derivation branches. Check receive and change indexes 0, 1 and another later index, not just the first receive address. Any actual derivation difference is a failure, not an expected checksum difference.

## 9. Policy verification first-address details

1. During hardware policy verification, find the shortened first address.
2. Before expanding it, its detailed path should stay hidden.
3. Click the address. Expect the complete address and the authoritative derivation path beneath it, using the existing details styling. For standard policy this is the displayed BIP48 account path followed by `/0/0`.
4. Collapse it and check the optional details disappear. Copy the address and compare the full value with the signer display.

## 10. Wallet deletion backup gates and responsiveness

1. For a disposable single-sig hardware wallet, open Delete, enter its correct app PIN and exact `DELETE`. Before checking the key-backup acknowledgement, deletion must stay disabled.
2. Check the backup acknowledgement and confirm. Expect responsive controls/loading and eventual success; expensive authentication/removal should not cause the reported multi-second beachball freeze. Record the elapsed time and whether the whole app stopped responding.
3. Repeat with wrong PIN and lowercase `delete`. Expect no removal, an inline error for incorrect credentials and exact-case confirmation enforcement. Duplicate clicks must not submit twice.
4. For a software wallet, check that separate recovery-word and passphrase-backup acknowledgements are both required, alongside the credential and `DELETE`.
5. With a funded software test wallet whose recovery backup is unverified, deletion must remain blocked and offer **Verify now**. Complete Groot's native recovery-backup verification, then reopen Delete and confirm the required acknowledgements/credential still apply.
6. With an empty unverified software wallet, both acknowledgements, credential and `DELETE` should allow deletion. Do not require successful backup verification for that empty case.
7. For multisig, also complete the existing successful public-descriptor recovery drill. Key-backup acknowledgement, app PIN and `DELETE` remain required. Verify the other wallets and their files remain intact after removal.
8. Close/reopen or navigate away from an idle deletion dialog. Sensitive credential input must be cleared. Active removal must not accept duplicate confirmation.

## 11. Issue-only and maintainability follow-ups

- File → View wallet files/Finder is proposed in #115; it is not implemented in this candidate. The issue calls for wallet-type-specific files, backup requirements and clear treatment of software private-key storage.
- `docs/code-quality-plan-2026-09-06.md` contains the updated staged refactoring recommendations. The current fixes reuse existing components and native label/backup logic; broad code movement and dependency changes are deferred.
- Existing feature branches for mobile pairing and continuity/Miniscript are not merged into this candidate. It is based on main plus the feedback changes.

## Evidence and public-release boundary

The feedback implementation passed frontend type checks, 722 frontend unit tests, strict Rust clippy/all-feature tests (503 native unit tests), isolated real-Core Regtest, focused desktop/mobile Chromium/WebKit flows and visual inspection. Version/package checks must be repeated for this exact internal candidate. These are distinct from exact-device physical results.

The public release authorization and Mainnet source-hash inventory remain unchanged. The strict public/pre-1.0 version policy and original reviewed-source hashes do not authorize this `5.2.0-rc01` candidate for public distribution. The existing internal builder verifies an exact clean commit, pinned HWI, rehearsal signing identity, app version, app signature and the resulting DMG. No public release, production signing, notarization, push or merge is part of this test build.
