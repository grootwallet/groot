# 5.3 native review and device test handoff

Tracking: #116 (defects) and #6 (mobile pairing), verified open on 2026-10-18. Base: `733bc513d5fe570a1ceb27d8815ed00a4b2a0459`, branch `codex/5.3-mobile-foundation`. This is an implementation review of the uncommitted working tree, **not independent approval or release authorization**. Exact patch bytes, source hashes and logs accompany the development archive under `release-artifacts/native-5.3-review/`.

## Review result and correction

Reviewed the native mobile restrictions, accepted-broadcast response and sync reconciliation, worker scheduling, corresponding IPC consumers, and iOS configuration/build script. Traced all native signing/broadcast call sites, backup-sheet dispatch, operation ownership, proposal identity, atomic repair/notification commits and selected-wallet handling.

One remaining issue was found: synchronous commands could wait on `operation_guard` on the main thread while a backup worker held that lock and waited for `run_on_main_thread`/its response channel. Even without that deadlock, a command arriving during a slow scan could freeze the UI. Moving only the originally identified expensive commands was incomplete.

The correction moves the remaining 29 serialized commands onto blocking workers, including onboarding cancellation, public imports/exports, signature import/discard, address retirement, policy preparation, recovery drills, network-source settings and Regtest reset. Wallet-specific work captures selection before queuing and rechecks it after acquiring ownership, before authorization or mutation; stale work returns the existing `wallet_selection_changed` error. App-global onboarding cancellation/setup drafts remain global. Credentials are wrapped in zeroizing memory before being queued. Domain validation, transaction review, signer proof, credential checks, SQL transactions and release restrictions remain in place.

Source-contract regressions inspect every serialized command in the six owning sources, including future additions, for worker-before-lock ordering. Each newly queued wallet-specific command also has selection-order assertions. These tests verify source scheduling contracts, not physical UI responsiveness; that remains a native device check.

No database/profile/registry/credential/backup/proposal/label schema changes, migrations, data discard, dependencies or BIP support changes. Existing persisted data remains compatible. The bundled adapter still awaits the same command names/arguments/results. BIP125/174 application recovery evidence remains as documented in ADR 0090.

## Gate boundary

The original mainnet source-policy verifier pins bytes from the reviewed 5.2 source. The candidate changes **21 pinned files**, including earlier CSS and adapter work, not just the first reported Rust file. The inventory records old reviewed and new candidate digests without modifying either the verifier or trusted material.

`pnpm validate` still stops at the reviewed-source mismatch. ADR 0088 requires independently reviewed source-policy changes and a corresponding review record; this implementation review cannot self-authorize its own changes. **No source pins, gates, public authorization, version, tag, update key or published artifact have been changed.**

To advance safely: freeze the candidate patch/commit; obtain an independent exact-diff review covering every changed pinned source and the native/IPC/mobile boundaries; fix and re-review any findings; only then update reviewed pins with the actual review record and rerun mandatory/extended checks. A new 5.3 version/public release requires its own accepted decision; the 5.2-only authorization/reproduction exception does not transfer. Do not make a green gate by restoring old behavior, weakening tests or mechanically copying candidate hashes.

The desktop internal builder also requires a clean tracked/untracked commit. No desktop package is produced from this dirty working tree or presented as a new reviewed candidate. The explicitly permitted ADR 0089 iOS **development** archive is separate from that release process.

## Hardware signer safety checklist

Run `pnpm hardware:preflight` after connecting the intended signer. Use a disposable, separately named test-network wallet and record the exact executable hash, model, firmware, Bitcoin app version where applicable, transport and observed result. Keep existing funded/certification profiles untouched. Do not put recovery words, credentials, raw xpubs, addresses, PSBTs or device paths into shared captures/logs.

Repeat for each supported exact model you have: Coldcard Mk4, Ledger Nano S Plus, Trezor Model One, Trezor Safe 3, original Bitcoin-only BitBox02, BitBox02 Nova and Jade Classic. Treat missing models/untested transports as pending; family discovery does not transfer certification. Model One uses its bounded host PIN flow; Safe 3 unlocks on-device. Original BitBox02 and Nova require separate records. QR/BLE are separate from USB evidence.

1. **Identity and receive.** Import the intended public account, check network/account/fingerprint, and verify the full receive address on the trusted device display. Assign permanent labels before reveal; verify labels/address survive restart. Reject a different device/account/network without changing the wallet. Discovery/readiness alone must not become Policy verified.
2. **Policy and transaction review.** For multisig, verify the actual threshold, every signer and first address on devices. Use a small test payment; compare recipient, amount and fee on trusted displays. Groot must derive review from the exact PSBT and retain it until completion. Public descriptors/backups must contain no private keys.
3. **Cancellation and interruption.** Reject on the device, cancel in Groot, disconnect during a prompt, reconnect, and retry the unchanged proposal. No signature may appear after rejection or be counted twice. UI, cancel controls and device prompts must recover without freezing. Recheck Model One PIN cancellation and Safe 3 on-device unlock independently.
4. **Signature and payment recovery.** Import a foreign/mutated signed test PSBT and confirm rejection without proposal changes. Import the correct signature, restart before broadcast, and finish once. If Local recording pending appears, retain the txid, sync and reconcile; do not create/resend a second payment. Automated fault injection owns storage-failure testing; do not corrupt a live profile manually.
5. **Accounting and acceleration.** Check recipient delivery, fee, change, balance, history, labels and restart persistence against the test node. Exercise RBF/CPFP on disposable transactions, including original-confirmation races and cancellation. One payment intent must not become duplicate outgoing payments.
6. **Recovery without the phone.** Restore the public multisig backup/BSMS in a fresh disposable profile and compare policy, first address, history and unspent outputs. Test the required threshold with each relevant signer pair and a missing signer. The original profile stays untouched; phone absence/revocation must never prevent desktop recovery.
7. **Native responsiveness.** On desktop, cancel/dismiss backup and recovery sheets, change settings during a long scan, and rapidly switch wallets around queued imports/cancel actions. The UI must stay responsive and stale work must fail or remain bound to its original wallet. Do not record native secret sheets.

## iPhone foundation checklist

After connecting/unlocking/trusting the phone and inspecting development signing, install only the isolated development identity with disposable data. Check cold launch, relaunch, light/dark, portrait/landscape, scrolling, keyboard dismissal/safe-area spacing, large text and VoiceOver. Exercise background/foreground and force-quit/relaunch. Confirm unsupported key creation/recovery/backup/signing/broadcast return stable errors and never create a wallet/key or claim success. Confirm desktop operation remains independent when the phone is offline/disconnected.

Pairing, scanning public enrollment, synchronized balances/receive requests, PSBT transfer and phone signing are not acceptance steps for this foundation. They require their implementation and protocol/recovery review first. An iPhone test cannot certify desktop USB signers or Android.
