# LocalCoinSwap Bitcoin execution contract

This is the upstream BTC/EUR trade contract for the selected provider. The [Groot gateway contract](localcoinswap-api.md) lists the endpoints Groot currently exposes. Create, accept, funding, seller receipt, BTC payout and funded refund require a native signer and are outside the current gateway.

The [LocalCoinSwap OpenAPI](https://localcoinswap.com/openapi.json) was refetched on 11 November 2026. SHA-256 `6d8b386d6dc53a0ee423d58b00c8fbcb08ae60126636b2dac836b00f41301045`. The origin is `https://api.localcoinswap.com` and authenticated requests use `Authorization: ApiKey <provider key>`. Identifiers are UUIDs. Amounts in trade bodies are decimal strings, with integer satoshis in transaction construction. The JSON below describes fields and their types. Use the provider schema for the full responses and status enums.

## Trade lifecycle

| Phase                               | Upstream method and path                                                              | Request                                                                                                                                                                                                                                                                                      | Response                                                                                                                                                            |
| ----------------------------------- | ------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Start a trade                       | `POST /api/v2/trades/non-custodial/create/`                                           | `offer` UUID, `fiat_amount` or `coin_amount`, `wallet_type: "webwallet"`, `wallet_address`, matching `wallet_pubkey`, `btc_trade_secrets`. The description says either amount and the generated required list marks both. The live contract needs an authenticated test for that difference. | `201` `TradeUuid` with `uuid` and `status: "CREATED"`.                                                                                                              |
| Accept as offer maker               | `PATCH /api/v2/trades/non-custodial/update/{uuid}/`                                   | `status: "ACCEPTED"`, `wallet_type: "webwallet"`, `wallet_address`, matching `wallet_pubkey`, `btc_trade_secrets`. Buyer signatures required when accepting a buy offer.                                                                                                                     | `200` `TradeRead`. Use the returned state. Provider docs describe seller acceptance advancing directly to escrow when the provider wallet has funds.                |
| Read authoritative trade and escrow | `GET /api/v2/trades/{uuid}/`                                                          | Trade UUID.                                                                                                                                                                                                                                                                                  | `200` `TradeRead` with parties, expiry, amounts, fees, `buyer_meta`, `seller_meta`, `tx_meta`, and `btc_escrow_data`.                                               |
| Prepare escrow                      | `PATCH /api/v2/trades/non-custodial/update/{uuid}/`                                   | Seller requests `status: "CRYPTO_ESC"`. Verify the resulting escrow data and wallet UTXOs before building any transaction.                                                                                                                                                                   | `200` `TradeRead`. BTC `tx_meta.escrow_unsigned_tx` may be `true`, which instructs the client to build the transaction.                                             |
| Submit funding                      | Same update path                                                                      | `status: "WAITING_FOR_MIN_ESCROW_CONFIRMS"`, `signed_txn` raw transaction hex.                                                                                                                                                                                                               | `200` `TradeRead`. Wait for the provider and chain to confirm escrow before showing fiat payment instructions.                                                      |
| Report fiat payment                 | Same update path                                                                      | Buyer sends `{"status":"FUND_PAID"}` after their bank transfer.                                                                                                                                                                                                                              | `200` `TradeRead` with `FUND_PAID`. This is a payment claim.                                                                                                        |
| Confirm bank receipt                | Same update path                                                                      | Seller sends `status: "FUND_RECEIVED"` and `seller_secret`, the seller's trade secret encrypted to the buyer's account public key.                                                                                                                                                           | `200` `TradeRead`. The buyer can use the encrypted secret to claim escrow.                                                                                          |
| Cancel                              | Same update path                                                                      | `status: "CANCELLED"`; funded cancellation can require `cancellation_secret`, with mutual confirmation when required by the trade state. The funded buyer sends their trade secret encrypted to the seller.                                                                                  | `200` `TradeRead`. Distinguish a pending cancellation from a completed cancellation or refund.                                                                      |
| Withdraw or reject cancellation     | Same update path                                                                      | `status: "CANCELLATION_REJECTED"`.                                                                                                                                                                                                                                                           | `200` `TradeRead`. Provider enforces who can act.                                                                                                                   |
| Open or withdraw dispute            | `POST /api/v2/trades/dispute/{uuid}/`, `POST /api/v2/trades/withdraw-dispute/{uuid}/` | `{"description":"…"}` for BTC opening. No body for withdrawal.                                                                                                                                                                                                                               | `200` dispute acknowledgement or `TradeUuid`. The resolved trade may supply `tx_meta.admin_release_secret` or `admin_return_secret` encrypted to the winning party. |
| Claim or refund bitcoin             | `GET /api/v2/trade-utxos/BTC/` and `POST /api/v2/wallets/publish/`                    | Fetch UTXOs and encrypted claim material. Build and sign locally. Publish `{"currency":"BTC","signed_tx":"<raw transaction hex>"}`.                                                                                                                                                          | `200` documented UTXO result shape, then `200` `{"error":false,"tx":"<hash>"}`. Reconcile by locally computed transaction ID and chain state.                       |

Trade writes require the `trade` scope and reads require `read`. UTXO, key and publish operations require `wallet`. Provider responses include `400` for invalid input, `401` for bad authentication, `403` for insufficient scope or role, `404` for missing or inaccessible records on some routes, and `429` for rate limits. A transport failure can leave a write outcome unknown. Fetch the trade or verify the transaction ID before trying another write. The provider publishes a three-per-minute limit on create and two-per-minute on the dedicated trade status endpoint.

## Published contract and website behavior

- The current website sends both fiat and coin amounts on create, matching the required field list in OpenAPI. The endpoint description says either. Capture the accepted request and actual returned amounts in a two-account test. [Website create client](https://localcoinswap.com/_app/immutable/chunks/Bn0skOwZ.js)
- The website builds seller funding from provider wallet outpoints. The escrow output is the trade coin amount minus the provider fee when the offer maker is buying, and the full coin amount when the offer maker is selling. It builds a separate fee output and seller change. The native verifier must check the script commitments, output amounts, change ownership and network fee independently before requesting a signature. [Website funding client](https://localcoinswap.com/_app/immutable/chunks/DMB-Fyg62.js)
- OpenAPI describes the BTC trade UTXO response as an array of result wrappers. The current website instead requests `limit=500` and `offset` and reads `results` and `count` on one response object. Obtain an authenticated response before committing a native decoder. [Website UTXO client](https://localcoinswap.com/_app/immutable/nodes/25.BMTY-upR.js)
- The published API has no separate bank-details endpoint for these trades. Offer terms and private trade chat are available. Treat a seller's receipt as a separate action after the bank transfer is verified.

## Native wallet inputs

`btc_trade_secrets` contains `encrypted_secret`, `hashed_secret`, and `hashed_public_key`. The buyer also supplies `hashed_secret_signed` and `address_signed`. The trade detail supplies the parties' `address`, `address_pubkey`, account encryption `public_key`, and side-specific hashed and encrypted secrets. `tx_meta` can supply `hashed_release_secret`, `hashed_return_secret`, `escrow_witness`, `fee_witness`, and funding transaction data. `btc_escrow_data` exposes `escrow_address`, `fee_address`, and optionally `escrow_tx`.

| Upstream method and path                 | Request                                          | Sensitive response                                                                                                                                                                                                                                                                                                                             |
| ---------------------------------------- | ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/v2/wallets/account-rsa-keys/` | `{"pin":"<six-digit LocalCoinSwap wallet PIN>"}` | `200` `account_rsa_keys`, including the account's private RSA key. This is a LocalCoinSwap credential.                                                                                                                                                                                                                                         |
| `GET /api/v2/wallets/non-custodial/BTC/` | No body.                                         | `200` `address_list`, `address_balance_map`, `address_enc_keys`, BTC fees in sat/vB, and balances. Encrypted key entries carry the address, `encrypted_private_key`, and `encrypted_private_key_iv`.                                                                                                                                           |
| `GET /api/v2/trade-utxos/BTC/`           | No body.                                         | `200` documented array of results wrappers. Each wrapper has `results`, `from_address`, `address_enc_keys`, and `network_fees`. UTXO entries carry outpoint and value, `witnessScript`, `trade`, `secret_uid`, `trade_secret_enc`, `tradeInstruction` and `type`. The advertised sweep destination is the account's newest BTC wallet address. |

The public web client shows provider-specific BIP39 trade-secret derivation, compact Bitcoin message signatures, and ECIES encryption of secrets to account keys. Its wallet unlock uses the returned RSA key to decrypt an encrypted account key that the website already has in browser storage. Account registration creates the account encryption key independently from the wallet mnemonic. The published API has no verified way for a fresh API client to obtain that encrypted account key from only an API key and wallet PIN. Key and escrow details in the public website bundles are evidence for that build. The [published Bitcoin script example](https://github.com/LocalCoinSwap/bitcoin-trading-scripts) supplies historical escrow branches. ## Evidence required to enable execution

1. Use two provider test accounts with BTC wallet access in a supported test environment. Verify both trade directions and the exact responses to create, accept, fund, cancel, and receipt. Confirm any automatic funding behavior on acceptance.
2. Verify how a fresh native client acquires and recovers the LocalCoinSwap account encryption key, binds a provider wallet address and key, and sends a payout to a fresh Groot receive address. Keep provider wallet secrets in the native boundary. Decide how active-trade keys and recovery material remain recoverable across device loss.
3. Validate the live witness and fee templates against independently generated vectors and verify every outpoint, network, output, amount, and fee in native transaction review. Prove cooperative payout, refund, both dispute outcomes, and interrupted broadcast recovery before enabling funded trades. Keep provider escrow keys and raw signing data outside the SvelteKit gateway.
