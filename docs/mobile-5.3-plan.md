# Groot 5.3 mobile delivery plan

Tracking: [issue #6](https://github.com/grootwallet/groot/issues/6), verified open on 2026-10-18. [ADR 0093](adr/0093-restore-mobile-key-delivery-scope.md) restores the owner's intended phone-held keys and QR coordination scope. The previous watch-first sequence was an incomplete interpretation of that goal.

## Required outcome

- **Software wallet on this phone:** create, back up, restore, unlock, receive and sign a BIP84 wallet. Its Bitcoin key stays native to the phone; retain the existing BIP39 passphrase semantics.
- **Phone as a multisig signer:** contribute an independent BIP48 key to a desktop-led standard multisig wallet, verify the complete policy, independently review the actual PSBT, and return only valid signatures by QR. The retained design uses words-only recovery and a separate local PIN, unlike the software wallet.
- **QR coordination:** exchange public account keys, origins, threshold, descriptors and signer names; compare the policy and first address. Never transfer a seed, private key, app credential or RPC credential. Desktop-only hardware certification is not inherited by the phone.

Use Testnet4 on the physical iPhone. Local Regtest remains useful for deterministic native tests without connecting the phone to it. Preserve desktop behavior, both themes, safe areas, pinch prevention and scoped styles. ADR 0092 governs numbered internal candidates. The installed phone trial now reports 5.3.0-rc2 in Groot, with numeric Apple build 530002; the earlier delivered desktop candidate remains 5.3.0-rc1 until its replacement is verified. Neither implies public mobile signer certification.

## Current implementation and remaining acceptance

ADRs 0094–0096 restore the retained coordination implementation with device-protected new iOS secrets, native backup verification, exact transaction review and worker/selection safety. Internal Testnet4 capability guards permit these candidate tests, not public certification. Full physical pairing/signing, recovery and lifecycle acceptance remain unfinished; see the [RC2 test record](testing/5.3.0-rc2-mobile-keys.md). The earlier [audit](testing/5.3-mobile-key-audit.md) remains a historical record of the missing foundation features.

## Implementation sequence and exit criteria

1. **Native key protection and recovery first.** Specify a device-bound random data-key wrapper, non-synchronizing passcode-required Keychain storage and Groot credential authorization under ADR 0097. Legacy user-presence items remain readable and may need one final owner approval. Bitcoin signing remains in short-lived zeroized Rust memory. Review passcode/biometric changes, backgrounding, lock, reinstall and backup/restore behavior. Define compatibility before changing storage; no silent conversion or discard. Add native backup verification, not merely an acknowledgement that words were displayed. No secrets in screenshots, logs or renderer state.
2. **Phone software wallet.** Port the native iOS sheets and worker-safe handoff; reuse the existing WalletPort and software domain. Prove create, wrong credential, backup verification, restore, independently configured Testnet4 sync, permanent labelled receive, transaction review/signing, cancellation, restart and retry. Derive and compare the same public identity after restore. Enable only this capability once its own checks pass; pairing is not inherently required for a standalone wallet.
3. **Offline multisig pairing and recovery.** Record the retained BIP129 construction, limits and threat model under a unique ADR number. Port authenticated setup rounds, exact signer proof, user comparison, complete public policy validation and atomic staging reconciliation. Preserve the retained bounds rather than silently widening them. Prove two fresh installs, tampering, expiry, replay, wrong network/policy, duplicate completion, cancellation and process kill at each commit boundary. Restore from the written phone words plus public policy and match the exact signer and first address. Losing the phone must leave the remaining threshold usable.
4. **Phone signing and desktop merge.** Bind native review to exact PSBT bytes/revision and the selected wallet. Reject foreign inputs, false change, missing UTXOs, non-ALL sighashes, final scripts and modified/stale proposals. Verify a funded native Core round trip, then a physical Testnet4 desktop-to-phone-to-desktop signing round trip with independent signers. Phone multisig mode returns signatures; desktop finalizes/broadcasts. Communication revocation cannot remove a signer from the onchain policy.
5. **Public wallet view and metadata.** QR import conveys descriptors, names and origins with privacy consent; the phone independently verifies balance/history through its configured backend. Hardware wallets remain watch-only on the phone. General label/history synchronization needs a separate authority/conflict model: BIP329 is interchange, not live sync. Do not let two devices independently allocate receive indexes under an undefined synchronization scheme.
6. **Exact-candidate regression and handoff.** Test desktop 1180×780 and mobile 390×844, light/dark, portrait/landscape, keyboard, safe areas, accessibility, camera denial/resume, wrong credential, lock/background/restart and offline retry. Capture non-secret screenshots/videos bound to source and binaries. Run mandatory validation, Rust lint/tests, isolated real Core and applicable CI gates. Resolve independent review before refreshing reviewed source pins. Package the next numbered internal candidate only after recording its actual capabilities and blockers.

## Boundaries

No wholesale branch merge, new cloud service, proprietary recovery, dependency update, source-pin refresh or public authorization is implied. Do not port the separate continuity/Miniscript branch as part of this work. Android needs its own native secret UI, platform protection and device evidence; public Mainnet mobile support remains gated.

The candidate adds the device envelope for new iOS secrets and restores the retained test-network BIP129/174 implementation. Existing desktop and retained testnet data remain untouched. Future storage changes require a compatibility assessment and fixtures; breaking changes require ADR 0035 approval. Native safety guards stay until the relevant capability has implementation, tests and review; UI options alone do not establish support.
