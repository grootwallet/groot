# Wallet and coordinator flows

This document describes user-visible state transitions. The product specification owns behavior; Rust owns wallet truth; these flows own presentation and navigation.

## Single-key onboarding

`welcome → Generate software wallet → private recovery-word reveal → verify all 24 words now or defer → wallet passphrase → created → overview`

The generated words remain hidden until the user confirms their surroundings are private. After writing them down, the user is strongly encouraged to reconstruct all 24 from a shuffled pool in the exact original order, but may choose **Verify later** without blocking creation. The deterministic browser fixture supports tap/click and drag-and-drop. Production macOS performs the same challenge in a native sheet so recovery words never cross Tauri IPC or enter webview state. A deferred wallet carries a persistent **Recovery backup not verified** warning on Overview and in Settings.

- The wallet-type chooser uses three equal decision cards: software, hardware, and shared/recovery. Each card keeps its icon, title, one consequence-focused subtitle, and complexity cue inside the same target; helper copy is not detached below the action.
- Software onboarding keeps a persistent, labeled three-stage progress indicator visible on every step: **Generate → Back up → Protect**. Completed, current, and upcoming stages are distinct, so users can estimate what remains before beginning.
- Hardware-wallet onboarding uses the same persistent component with stages **Connect signer → Review identity → Protect app**. The labels distinguish importing public account data, reviewing the signer fingerprint, and setting Groot's local app PIN. Single-key hardware setup asks for one wallet name only and reuses it as the initial internal signer label; a cable import defaults the empty name to the detected device model. Settings later exposes the wallet name and hardware-signer name separately, because the signer name identifies the key on signing and verification screens. Renaming either is local metadata and never changes fingerprints, public keys, descriptors, or wallet identity. The final step asks only for the Groot app PIN and explains that sending still requires the hardware signer. A Ledger Nano does not display its master fingerprint for an independent comparison, so its review explains that a seed or passphrase change selects a different fingerprint, binds the imported identity without claiming device-screen verification, and requires first-address verification on Ledger before use. If the same public descriptor is already registered, creation fails without mutation and the final step presents a prominent duplicate-wallet explanation with a direct route back to the existing wallet.
- Software create always uses 256 bits of OS randomness to generate exactly 24 BIP39 words and one credential as BIP39 passphrase plus app unlock/signing PIN. An optional collapsed advanced panel accepts 128–256 recorded physical coin flips or 50–100 physical six-sided-die rolls. It shows bounded progress and recent outcomes, permits undo/clear, explains that the OS source remains mandatory, and clears the transcript after every generation attempt.
- **Use hardware signer** is a separate single-key path. It imports only public account data and never generates or accepts the hardware device's seed.
- Recover requires exactly 24 words and the original credential.
- Generated words stay in a zeroized Rust pending session. A secret-free native privacy gate first requires confirmation that no person, camera, or screen sharing can observe the display; only then does the attached native sheet reveal the words. The three columns read vertically as 1–8, 9–16, and 17–24. Browser fixture words exist only for deterministic UI testing and follow the same concealed-first interaction.
- Failure stays on the current step with an inline error. A successful operation clears credential/recovery input before navigation.
- When any wallet already exists, every add-wallet step has a close action that returns to the selected wallet without consuming the pending onboarding session.
- `unverified Overview/Settings CTA → wallet passphrase → native shuffled-word challenge → exact match → verified`. The later flow never re-reveals the ordered words. Cancellation and mismatch preserve the unverified marker and do not restrict receiving or spending in this milestone.

## Multiple wallets

`current wallet → Add wallet → create/recover → selected and unlocked`

`wallet selector → choose profile → reuse its unexpired session or unlock that profile → kind-appropriate home`

Each profile owns a UUID-isolated directory and unlock session. Switching never lets one wallet authorize another, but it also does not revoke the wallet being left. Returning before that wallet's independent inactivity deadline opens it directly; an expired or never-unlocked wallet shows its own credential screen. The duration is one global preference for every wallet, defaults to five minutes, and is configurable under **Settings → Security → Automatic lock**. Activity in one wallet does not refresh another. Background polling does not count as activity. Deleting the selected profile chooses another remaining profile and returns to that profile's unlock state, or returns to onboarding if no wallets remain.

Desktop exposes the selector in the persistent sidebar. Mobile exposes it beside Overview's overflow action; both use the same shell-owned registry and selection flow, and their popup menus stay inside the visible viewport.

Wallet is the common top-level container. Software-key, hardware-key, shared multisig, and recovery/inheritance policies all use the same Overview, Activity, and Coins destinations. Policy is an additional detail destination for wallets with multiple signing paths; it is not a separate balance-bearing vault. Notifications are scoped to the selected wallet. If a received transaction is first discovered after it already has a confirmation, Groot combines receipt and confirmation into one toast instead of presenting two events for the same transaction; a sync that finishes after selection changed cannot emit into the newly selected wallet.

## Unlock and deletion

`wallet list → select wallet → focused unlock card → credential check in Rust → wallet` or `invalid_credential → focused unlock card`

The locked screen's central card names only the selected profile. The persistent desktop sidebar retains the wallet list, **Add wallet**, theme, and network status so another profile can be selected without carrying credential state. Wallet-scoped navigation and Settings remain absent until unlock. Hover, focus, or activation of network status shows only data Groot can verify: public fee policy is available while locked, while node height, backend, and transport are checked after unlock. There is no Back or second add-wallet action inside the unlock card; **Add wallet** in the sidebar is the sole creation entry when profiles exist. Direct fresh-install onboarding redirects back to unlock unless that explicit add-wallet route is active. Software-key wallets call the credential **Wallet passphrase** and explain that it is the BIP39 passphrase that must remain with the recovery words. External-hardware and multisig wallets call it **App PIN** and explain that it protects local Groot data only, not the hardware seed or hidden wallet. Credential fields across onboarding, unlock, signing, descriptor export, recovery, and deletion have explicit show/hide controls.

`unlocked wallet → Settings → wallet details / Lock now / backup information / recovery controls / wallet node / appearance`

Settings clearly labels scope. **Wallet details → Wallet name** updates the selected unlocked wallet's local display name and immediately refreshes the title and wallet switcher; it never rewrites cryptographic identity or recovery artifacts. **Lock now** affects only the selected wallet. **Automatic lock** is global and sets the shared duration used by every wallet's independent inactivity clock. Appearance is also global. Backup, credential, and node controls apply to the selected wallet; backup rows explain requirements only because Groot never re-displays recovery words or a wallet passphrase after creation. Wallet switching and **Add wallet** stay in the persistent wallet list, and policy creation/recovery starts from that add-wallet flow rather than a generic Settings section.

`settings → delete warning → credential + type DELETE → Rust verification/deletion → unlock next wallet / welcome`

For a selected locked disposable regtest wallet: `locked → delete warning → type RESET REGTEST → Rust deletion → next wallet or welcome`. This works for either profile kind and is unavailable on public networks.

Deletion is device-local. It never implies that transaction history disappeared from Bitcoin. Multisig deletion additionally requires an in-session successful recovery drill for the exact current descriptor, the wallet PIN, and its exact name.

## Receive

`recovery-gap check → mandatory permanent label → atomic reveal+label → QR/copy`

Multiple unused addresses may await payment concurrently within the configured recovery gap. The prospective index is checked in the same transaction as reveal and label persistence; exceeding the gap reveals nothing, and the setting cannot be lowered below the already-required run. Each request may transition independently to `discarded` and remains monitored. Any observed payment transitions that address to `used`, after which discard is impossible.

## Single-key send

`Intent: permanent label+recipient → Amount & fee: amount+privacy strategy or exact coins+fee rate → persist Rust PSBT+label → Review funding privacy → Review & sign: authoritative review+credential → sign+broadcast → durable labeled success`

The review includes Rust-derived input/output counts and verified wallet-owned change. Review and signing fail closed if the recipient or fee differs from persisted intent or if any remaining output is not controlled by the selected wallet. Multisig PSBTs carry the policy's public account keys and origins so a hardware wallet can reconstruct the reviewed BIP48 policy. An older active proposal may receive that same deterministic public metadata only in the temporary device-signing copy; Groot removes it before merging so the persisted reviewed PSBT changes only when a valid new signature is added. A device that returns without its signature is reported as no signature added, never falsely as an already-used signer.

Every stage is named in the same three-step progress indicator. A compact signer summary identifies Groot on this device for software wallets, or the imported model/label and shortened public fingerprint for external hardware. Amount & fee defaults to Balanced automatic selection and offers More private, Lower fee, or exact manual inputs. Coin rows disclose known, mixed, unknown, and address-reuse provenance before selection. The review is derived from the persisted PSBT, while Rust normalizes and persists the mandatory outgoing label alongside that proposal. It states the authoritative funding-input count and shows a calm warning when selected inputs cross known labels/clusters, contain unknown provenance, or use a reused address. Every software, external-signer, and multisig review keeps only recipient, label, network, network fee, amount, and total visible by default. One consistently named **View more details** disclosure contains aggregate input value/count, output count, fee rate, change amount/address, locktime/RBF, and wallet policy where applicable. Exact input outpoints and sequences stay enforced by Rust without adding a second technical sub-section to the review. The recipient is shown as `prefix…suffix` and opens a complete grouped, copy-safe detail modal. A wrong credential clears the field and leaves the reviewed proposal available for retry. External-signer and multisig routes reload the exact active proposal after restart; the generic single-key route does not yet expose a post-restart proposal selector, although Rust preserves and revalidates its persisted PSBT/intent binding. No route rebuilds transaction intent from UI fields. PSBT export opens the native file picker, validates a bounded PSBT at the Rust boundary, suggests the hardware-friendly `groot-xxxxxxxx.psbt` form instead of exposing a full proposal UUID, and reports a durable success or failure. Canceling first opens a destructive review of the payment and collected signatures; only the modal's confirmation calls the cancellation boundary. **Back to overview** opens a separate leave confirmation and preserves the proposal and signatures for later resumption. Broadcast emits a toast and returns an updated snapshot whose activity record uses the permanent outgoing label.

`pending transaction → Increase fee (RBF) or Spend output (CPFP) → persisted acceleration PSBT → normal review/sign/broadcast`

Acceleration never bypasses review or signer thresholds. Confirmed, non-replaceable, missing-output, insufficient-value, and confirmation-race states fail explicitly and remain retryable after sync.

`wallet-owned inputs → only wallet-owned value outputs → Rust classifies self_spend → activity shows Self-spend and fee debit → no counterparty row`

Transaction kind is authoritative snapshot data, not a UI guess from labels or zero amounts. Compact counterparty addresses and full grouped addresses are mutually exclusive presentation states.

## Multisig setup

`name+recipe or advanced M-of-N → add 3–7 signers → Rust validation/descriptor preview → saved descriptor → signer policy registration when required → app PIN → persisted coordinator`

Signer import paths:

- Desktop USB: Rust invokes Bitcoin Core HWI, enumerates a device, and requests the fixed BIP48 test-network account xpub.
- Mounted file: bounded Groot or compatible Coldcard-style JSON containing only a test-chain public origin, fingerprint, and BIP48 account tpub. Private/recovery material, wrong-network paths, and extended private keys are rejected. Manual entry remains available. PSBT signing also supports bounded `crypto-psbt` UR v2 animation/camera through a bundled local QR decoder, with file/text fallback.
- Virtual device: deterministic browser/CI fixture only; it must be visibly identified as a test device.

Selecting a draft or saved signer opens public device details. For USB/virtual sources, **Run health check** enumerates devices through `WalletPort` and passes only when a connected device has the saved fingerprint. QR/file/manual sources can only validate that the saved public fingerprint, account path, and xpub record are complete; the result explicitly says physical presence was not checked. The latest result, timestamp, and bounded recent log are presentation state for the current app session, not a durable certification record.

The saved Policy page renders one row per signer rather than a separate readiness list plus an identity list. Each row carries a compact policy-status badge. Opening the signer reveals its public identity, connection health, policy-registration requirement and evidence, plus the relevant setup or reverification action. A Coldcard that lacks Groot's durable acknowledgement is labeled **Setup not recorded** because Groot cannot infer whether the persistent policy is absent from the physical device.

The same Trezor PIN-matrix component is available from multisig transaction signing. Unlocking consumes the single-use native challenge and returns to a fresh signer scan without changing the reviewed proposal or its collected signatures.

Before a USB scan, the UI says that the hardware signer must already be initialized with a seed and backed up offline. Vendor companion apps must be fully quit because their USB session is not transferable to Groot. Most devices must also be unlocked and ready in their vendor-specific Bitcoin mode. Every pending hardware action—discovery, public-key import, device unlock, saved-identity health check, address approval, and signing—uses the same animated live-status panel with action-specific instructions, regardless of signer vendor. A locked Trezor Model One is the exception: selecting its detected card starts HWI's scrambled PIN matrix in Groot. The Trezor screen alone shows shuffled digits; Groot shows nine blank spatial cells. For each PIN digit, the user taps the blank Groot cell in the same location, so neither PIN digits nor the shuffled matrix are reproduced in the webview. Groot's blank grid never changes; requesting a fresh layout changes only the shuffled digits shown on Trezor. The single-use challenge expires after two minutes and a rejection requires a fresh device layout. A compact help view gives basic Coldcard, BitBox02, Ledger, Trezor, and Jade preparation steps. Detected-but-not-ready devices remain visible with a typed action. A Trezor warning that HWI selected its empty-passphrase standard wallet cannot be imported until the user explicitly chooses **Use standard wallet**; this does not alter any hidden wallet and the resulting fingerprint is bound to the signer. Host entry for a Trezor Model One hidden-wallet passphrase remains unsupported. BitBox02 requires a one-time pairing-code confirmation in BitBoxApp. The UI tells the user to enter the device password, wait until the wallet itself is visible rather than stopping at “See the BitBoxApp,” and only then quit BitBoxApp completely so Groot can own USB. Groot passes HWI only the canonical home directory needed to reuse that pairing cache. Ledger enumeration may expose a fingerprint while either Bitcoin app is open, so Groot labels it **Detected** until the account-key read proves the network-matching app—Bitcoin Test on Regtest, Signet, and testnet; Bitcoin on mainnet—is open. Groot reopens the exact enumerated device by fingerprint. Ledger passphrases are configured and activated only on the trusted device; Groot neither accepts nor transmits them. BIP48 may request on-device public-key export approval while a standard BIP84 single-key read may complete without a prompt. A failed read stays in a compact retry state with a stable device-specific explanation rather than raw HWI output. Jade login remains on-device. Groot never offers device initialization or asks for a hardware-wallet seed. When HWI returns no device, Groot cannot safely infer that an attached USB peripheral is a Coldcard; the empty state tells the user to sign in, enable the Coldcard USB port, reconnect, and rescan.

Opening the USB picker performs two bounded enumeration passes separated by a short settling interval and merges device identities, which catches signers that become ready just after the first pass without starting an unbounded monitor. A visible **Scan again** action remains available after results appear. Closing or replacing the dialog invalidates pending presentation updates, and nested dialog transitions use reference-counted page scroll locking so the underlying page is always restored.

Receive-address verification keeps the complete host-derived address visible in the modal before and throughout the hardware prompt. The derivation path, address index, and Regtest-only hardware-prefix explanation share one collapsed **Address details** disclosure so technical metadata does not compete with the primary comparison. While the signer call is pending, an animated live-status panel explicitly directs the user to compare the complete address and approve on the hardware device; reduced-motion preferences suppress its animation without removing the instruction. The user must compare every character with the trusted display and approve only an exact match; device communication never replaces or obscures the value being reviewed. After an exact match, the modal closes with a success toast, the address shows a compact green check and **Verified on hardware**, and Rust atomically appends a timestamped verification event tied to that address. Hover, keyboard focus, or mobile tap explains that the exact address matched a saved hardware signer and that the evidence is specific to this address. The latest verified time and signer fingerprint remain visible in address details across restarts; repeated checks append evidence rather than overwriting it. On Regtest, Ledger Bitcoin Test, Trezor, and BitBox02 render the same witness output with the testnet `tb1` prefix rather than Regtest's `bcrt1` prefix, which also changes the six-character Bech32 checksum. Rust supplies that exact testnet alias for the review UI and accepts it only when both decoded addresses produce the identical scriptPubKey; malformed addresses, different scripts, and non-Regtest cross-network aliases fail closed. Device recognition uses both the HWI label and model because vendors do not populate those fields consistently.

During hardware signing, the modal keeps the authoritative recipient, label, amount, network, fee, and total visible while the native signer call is waiting for on-device approval. If Ledger repeats policy authorization at the start of that call, Groot first keeps the saved policy reference visible; after approving that phase on-device, the user explicitly switches Groot to the transaction reference without restarting the call. Both references remain reachable until signing finishes, so neither device phase is reviewed against a hidden or stale host screen. The recipient opens into the standard grouped full-address presentation. On Regtest, Ledger Bitcoin Test and Trezor signing reviews use Rust-supplied `tb1` aliases for both recipient and change only after each alias has been reconstructed from and therefore bound to the exact PSBT output script; other signer families and ordinary reviews retain the canonical network address. The same collapsed **View more details** section used by every send review provides optional insight into the fee rate, exact change amount and address, aggregate input/output counts, locktime/RBF, and wallet threshold. These values come from the persisted, validated proposal PSBT so the signer can compare the host and hardware displays without closing or looking through a blurred backdrop. A scanned device whose public fingerprint is already present on every proposal input is marked **Already signed** and cannot be selected again; the native duplicate-signature rejection remains the fail-closed backstop. The primary action remains visible but disabled while the threshold is unmet and states exactly how many signatures are still required. Once the required signatures are verified, signing transport actions disappear and that action becomes **Finalize & broadcast** after the final review and app PIN.

The main multisig proposal review uses the same hierarchy: amount, recipient, permanent label, and network fee remain primary; a collapsed details section contains the change amount and address, transaction shape, fee rate, total debit, and wallet policy. Recipient and change addresses both open into the grouped full-address presentation.

During proposal collection on desktop, signer state sits in a separate side panel with one vertically stacked card per signer. The three-step progress indicator remains above the workspace and describes flow position only; signer cards describe threshold progress only. Narrow layouts return to one content column and keep the compact signer list separate from the step indicator.

Saving an unsigned PSBT, descriptor backup, or device-policy file on macOS adds a compact **Show in Finder** action to the success toast. The action uses a short-lived, single-use native reveal capability and never exposes the selected filesystem path to the webview.

Importing or returning a PSBT must increase the set of policy signers that validly signed every input. A duplicate signature, unchanged PSBT, or signature covering only a subset of inputs is rejected as **no new signatures** without mutating the persisted proposal or its existing valid signatures.

When a Trezor reports both PIN and passphrase requirements, Groot must resolve them in that order: PIN matrix, fresh enumeration/fingerprint, then explicit standard-wallet selection if applicable. Both multisig and external single-key setup implement the same sequence. A later hardware passphrase does not mutate an imported standard wallet; it derives an independent hidden wallet with a different fingerprint, xpub, descriptors, and addresses, which can be added as a separate Groot wallet.

The default recipe is 2-of-3; 3-of-5 is the larger-group recipe. Advanced mode permits 2 ≤ M ≤ N with 3 ≤ N ≤ 7. 1-of-N is excluded because it has no multisig theft protection. Duplicate fingerprints/xpubs, invalid origins, invalid test-network keys, private descriptors, and unsafe thresholds block review. Creation stores checksummed public descriptors, public signer metadata, a watch-only BDK database, and an encrypted app-PIN marker.

Coldcard signers are marked during USB import. Groot exports the public BIP-380 wallet policy with a normalized ASCII filename whose basename is at most 20 characters, because Coldcard firmware derives a descriptor policy's on-device name from that filename. Registration is recommended during creation but may be explicitly deferred because the coordinator is watch-only. Before the first Coldcard signature, Groot requires acknowledgement that the file was imported from **Settings → Multisig Wallets → Import** and that the normalized name, threshold, and fingerprints matched on-device. This registration lets Coldcard verify change instead of signing an unknown multisig wallet. The acknowledgement is durable but is not represented as cryptographic address-verification evidence.

Hardware policy readiness follows the device's actual model instead of presenting one generic **Ready** state:

- **Coldcard MK4:** import and verify the BIP-380 policy file during creation or before its first signature. Coldcard persists the wallet definition and uses it to verify change.
- **Ledger Nano S Plus:** compare the account name and threshold, then open each fingerprint, derivation path, and public key in Groot's standard large identifier view while reviewing the device screens. Groot derives and displays the exact first address before starting the device request; on Regtest it displays the script-equivalent `tb1` encoding used by Ledger Bitcoin Test. Interactive registration and signing receive a bounded five-minute review window. Groot persists descriptor-bound verification evidence. Ledger's protocol can return a wallet-policy HMAC for reuse, but Groot's current HWI CLI path does not retain that HMAC and therefore asks Ledger to authorize the policy again for each signing request. While that request runs, Groot keeps the saved policy reference visible until the user explicitly advances to the transaction reference; either reference can be reopened without interrupting the request.
- **BitBox02:** first-address verification registers the named multisig configuration and identifies the device's own key. Groot uses the same preflight and persists the successful first-address proof.
- **Blockstream Jade:** address display registers the multisig configuration over USB; Groot uses the same preflight and persists the successful first-address proof. QR registration remains a later transport path.
- **Trezor One:** no persistent wallet-registration state is claimed. Groot supplies the complete policy with the request, supports the PIN-matrix unlock flow, and relies on address/transaction review. On Regtest, Groot shows the Rust-verified script-equivalent `tb1` recipient and change encodings that Trezor displays.
- **BitBox02 Nova:** it shares the BitBox product and firmware family, but Groot does not claim HWI support or physical certification until the exact Nova model enumerates, registers a test policy, verifies receive/change, and signs in the release matrix.

Policy registration during setup is recommended but deferrable because coordinator creation is watch-only. Deferral is explicit and visually distinct from completion. An unfinished signer remains **Setup required** on Policy and in the signer strip; selecting it during signing opens its exact device-specific preparation before the transaction can be sent to that device. See [`hardware-policy-readiness.md`](hardware-policy-readiness.md) for the canonical matrix.

The guided recovery and inheritance recipes require exactly four independent keys. Keys 1–3 are the immediate 2-of-3 primary set; key 4 is recovery-only and is never counted in the immediate branch. The creation UI labels these roles before review, while Rust rejects any recovery template whose delayed signer overlaps the immediate signer set. The V2 policy lab cannot retrofit a recovery-only key onto a three-key wallet; it blocks compilation and directs the user to create a new four-key recovery wallet.

The V2 policy lab is analysis-only: compiling does not mutate, upgrade, or replace the selected wallet. Activating a compiled policy requires creating a distinct wallet, reviewing its complete descriptor, and backing it up.

Policy-wallet creation uses four focused stages: **Policy → Signers → Verify → Back up**. The shared progress component renders earlier stages with green checks, the current stage in blue, and later stages as neutral numbers. Policy selection and wallet naming happen before any device enrollment; moving backward preserves the draft. **Recover** is available only from Policy, before a new-wallet draft progresses. Hardware preparation help and device scanning appear only on Signers. While the signer draft is incomplete, setup presents neutral progress such as “1 of 3 signers added.” Validation failures appear only after **Review wallet** is attempted, then update as the draft is corrected. Each imported signer card labels the device fingerprint and connection/import source explicitly and wraps the complete public account key without truncating it. Final review explains descriptors through the shared insight control and leads with the portable multipath wallet descriptor when receive and change branches can be combined safely; the separate branches remain optional detail. Back up separates descriptor saving, optional device-policy registration, and coordinator-PIN creation into sequential shared task sections: completed work becomes compact, the next action receives blue emphasis, deferred policy checks remain visibly amber, and later controls remain disabled and muted until required prerequisites pass. A successful native descriptor save completes the backup gate; all device-policy preparation may be explicitly deferred until first signature. Save failures remain durable, and macOS success toasts offer the path-private Finder reveal action.

## Multisig payment target flow

This flow is implemented for regtest; see `docs/implementation-status.md` for certification limits.

`Intent: permanent label+recipient → Amount & fee: amount+coins+fee rate → persisted unsigned PSBT → Review & sign: authoritative review+collect any k signatures → Miniscript satisfaction/finalization → broadcast`

The three stages use the same labeled progress indicator as single-key sends. A compact signer summary shows the threshold, imported signer labels/models, and shortened public fingerprints; it marks signatures only from the authoritative proposal and does not claim physical connectivity. Each signer is `ready`, `awaiting`, `signing`, `signed`, `rejected`, or `unavailable`. USB, bounded `crypto-psbt` UR v2 QR, and file signatures converge on one Rust PSBT merge function. Imported data must match the proposal's unsigned transaction and descriptor identity. A collected signer row exposes an accessible **Discard local signature** action with confirmation. That action removes only the selected signer's partial signatures from Groot's canonical local PSBT and returns a ready proposal to collecting when needed; it is explicitly not revocation because previously exported or shared PSBT copies remain valid. Once the threshold is met, **Save signed PSBT** remains available beside the finalization controls so the complete signed artifact can be archived before broadcast. The app PIN unlocks coordinator data; it never substitutes for a hardware signature. While an active proposal exists, Overview shows its signature progress in a compact resume action without exposing its label, amount, recipient, or signer identities. A fully signed proposal changes that action to **Payment ready to broadcast**; opening either state resumes the exact persisted proposal.

The hardware-signing modal always offers an in-place rescan. A signer outside the wallet quorum, an unavailable fingerprint, or a rejected signing request remains as a durable inline modal error; the page behind the overlay is never the sole error surface. When Ledger repeats wallet-policy authorization as the first phase of an HWI signing request, Groot keeps the saved policy reference visible while the request runs. The user explicitly advances Groot to the authoritative transaction reference after approving the policy, and can reopen the policy reference without interrupting that request. Groot must never hide both references while Ledger is awaiting approval. When the current scan detects a connected Coldcard for a wallet with a Coldcard signer, the modal offers the same public registration descriptor, so an unknown-wallet failure is recoverable without rebuilding the coordinator. Coldcard-specific help is absent when only another signer family is connected.

## Descriptor backup and recovery scan

`app PIN authorization → BSMS recommended or Groot JSON → copy/download/one-page printable QR backup → named file ready → first-address drill → offline storage`

BSMS is the interoperable public standard for a standard sortedmulti wallet. The recovery picker also accepts public `.txt` descriptor exports containing a BIP-389 multipath descriptor, an explicit receive/change pair, or a standard receive descriptor from which the matching change branch can be reconstructed without ambiguity. Groot JSON retains custom recovery-policy metadata and labels. Every format is bounded, parsed, network checked, and first-address derived in Rust; portable and explicit branches must agree. The app PIN authorizes export but is not a file-encryption password: the exported watch-only record cannot spend, yet should stay private because it reveals address derivation and wallet activity. Explicit export re-authentication accepts the correct wallet app PIN even after an idle-session timeout, then refreshes that session. The printable view is a single A4 sheet with wallet name, a legible UTC creation date, policy, network, signer fingerprints, and vertically stacked receive/change descriptor QR codes; the native print sheet provides PDF saving without a separate PDF dependency. Loading a drill file visibly retains its filename. A recovery drill against the currently selected wallet must compare descriptor identity, not merely validate syntax, and its inline state, toast, and deletion gate all use that one authoritative comparison. Export, recovery-drill, and deletion failures render inside their own sections so one action cannot appear to fail another.

`Settings → birthday+gap draft → credential → persist → asynchronous Core rescan with block progress → complete or cancel safely → durable balance/history`

Editing is draft-only until authenticated save. Height `0` is safest; a birthday after the first payment can omit history. Gap limits are bounded from 20 through 1,000. While scanning, the modal cannot be dismissed or edited, reports processed and total blocks, and offers cancellation without waiting for the scan command to finish. Each applied block and its progress checkpoint are persisted. Cancellation, failure, or process interruption remains visible after the foreground task ends; retry reruns from the configured birthday rather than trusting a partial result.

## Freeze or unfreeze a coin

`Coins → select Freeze or Unfreeze → confirm the named coin or selection → persist the new eligibility state → inline state + toast`

The confirmation explains only the practical effect: frozen coins cannot be selected for automatic or manual spending until unfrozen. It never shows the technical outpoint unless the user separately opens coin details.

Address reuse never blocks selection or spending. Every affected row inherits its immutable receive label and carries a compact amber reuse marker. Expanding that coin's details reveals its compact address/outpoint, explains the public link, and identifies the other linked coins by amount and shortened outpoint. Unknown or unavailable addresses are never treated as a reuse match.

## Notifications

- Broadcast: immediately after accepted broadcast, including updated balance.
- Payment received: first observation only, including updated balance.
- First confirmation: zero-to-one confirmation transition only, including updated balance.

The page/list is durable truth. Unique markers persist in Rust until explicitly acknowledged. Delivery is at-least-once across a crash before acknowledgement and consumers use stable IDs idempotently; background/resume scheduling remains a platform integration gate.

While an unlocked desktop session is open, a single ten-second foreground loop syncs only the selected wallet. Returning to the app wakes it immediately. The returned authoritative snapshot updates the current Overview, Activity, Coins, or Receive view, and durable notification markers produce the receipt/confirmation toast once. Sync and notification reads validate the five-minute session but never refresh its idle deadline; an expired session stops polling and returns to that wallet's unlock screen. Sync pauses on onboarding or lock and never overlaps a previous native sync. Fully terminated push/background execution remains a later platform gate.
### Add a single hardware signer

1. Choose **Use hardware signer**.
2. Initialize and unlock the device; select its hidden/passphrase wallet on-device if used.
3. Import over cable, or load/paste a public BIP84 descriptor/xpub export from SD/QR.
4. Groot rejects private data and normalizes the test-chain account to `m/84'/1'/0'`.
5. Compare the master fingerprint with the device/export.
6. Name the wallet and set its independent Groot app PIN.
7. To spend, review the PSBT, sign by exact-fingerprint USB or offline PSBT, then enter the app PIN to broadcast.

Passport Core uses QR or microSD. Trezor Model One host passphrase entry is unavailable; do not fall back to an empty passphrase.

### Configure network services

1. Open **Settings → Wallet activity sync** and explicitly choose Bitcoin Core or compact filters.
2. Compact filters disclose confirmed-only behavior. Public discovery requires at least two peers. Manual mode accepts numeric `IP:port` peers and never falls back; adding a loopback Tor proxy also disables discovery so DNS cannot escape locally.
3. Open **Settings → Fee and broadcast node** to configure Bitcoin Core independently. Choosing compact filters never changes this service and never silently uses it for wallet discovery.
4. On wallet overview startup, compact-filter mode shows sanitized connection/scan/apply progress. Failure leaves the prior balance visible and names the last verified block height. In the pinned engine, public filters are memory-only and download again after app restart; wallet checkpoints and history remain in SQLite.
5. Test Core authentication and availability separately. Groot reports full/pruned history, prune height, IBD, disk use, and filter-index state. Core RPC activity sync does not require `blockfilterindex`; a pruned node must retain all blocks needed after the wallet checkpoint. A compact-filter refresh fails visibly if its selected peers cannot reach a verified tip.

The later recovery, durable-cache, direct-P2P-broadcast, adversarial-peer, public-network, and platform work is explicitly gated by [`compact-filter-deferred-work.md`](compact-filter-deferred-work.md). None is an implicit fallback from this flow.

Payjoin V2 BIP21 requests are parsed and network-checked only inside Rust. Until ADR 0031's encrypted-session, transport, fresh-review, fallback-consent, and interoperability gates are met, Groot does not advertise or initiate Payjoin sessions.

## Sort coins

`Coins → compact sort control → newest/oldest, largest/smallest, or label A–Z/Z–A`

Newest source transaction is the default. Sorting is presentation-only and never changes selection, freeze state, labels, or spend eligibility. Date sorting leaves coins without a known source-transaction timestamp after dated coins.
