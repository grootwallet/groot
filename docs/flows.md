# Wallet and coordinator flows

## App logs

1. Open **Settings → App logs → View app logs**. It appears immediately before wallet
   deletion. App logs is not a separate navigation destination, but the regular
   unlocked rail or mobile tabs remain visible with Settings selected.
2. Groot reads only sanitized app-level records; wallet snapshot, descriptor, node,
   signer, transaction, and address APIs are not called.
3. Optionally expand the complete allowlisted event-category inventory. Search event
   names or safe context, select any combination of event types and outcomes, and order the result
   newest or oldest first. Inspect timestamp,
   event, outcome, trigger, compiled network, platform, build, wallet kind, sync
   source, coarse progress/count, export format, source commit, and safe error detail
   when present. A pruned recovery failure states the requested birthday, required
   anchor, earliest retained full block, and earliest usable birthday. Receive
   generation exposes only the number of permanent labels assigned,
   never label text; a successful eligible-address discard is its own event.
4. Switch to **Raw JSON** to inspect or explicitly copy the exact sanitized records
   in the current result. Choose **Export CSV** or **Export JSON** to save the complete
   log through a native location chooser.
   Cancellation changes nothing; success appends one sanitized export event.
5. Error detail is fixed and structured. Groot never copies arbitrary backend, RPC,
   hardware-device, or user-authored strings into app logs.

This document describes user-visible state transitions. The product specification owns behavior; Rust owns wallet truth; these flows own presentation and navigation.

## Single-key onboarding

`welcome → Generate software wallet → private recovery-word reveal → verify all 24 words now or defer → wallet passphrase → master fingerprint → overview`

Under ADR 0064, software, hardware, and standard-multisig creation/recovery can
create an empty encrypted profile without asking for Bitcoin Core credentials.
Chain-derived Mainnet wallet data remains unavailable until Rust authenticates
the selected wallet's loopback-HTTP or direct-HTTPS Core setup and verifies the
exact Mainnet genesis. A ready same-network setup from another unlocked wallet
may be revalidated and encrypted as an independent copy for the new profile.

In multisig creation, a saved but locked source remains visible. Selecting it
requires unlocking the source before finishing; a failed selected copy leaves
the draft intact rather than creating an unexpectedly offline profile. The
checkbox can be cleared for intentional offline creation. For an already-created
offline wallet, Settings can copy from a ready, unlocked source. The Policy page
then shows one actionable network failure rather than cascading status toasts,
and it never calls a found hardware signer missing because a separate wallet
status read failed.

The generated words remain hidden until the user confirms their surroundings are private. After writing them down, the user is strongly encouraged to reconstruct all 24 from a shuffled pool in the exact original order, but may choose **Verify later** without blocking creation. Deferred verification offers two freshly authenticated native paths: users with the written backup go directly to the shuffled proof, while users who did not finish writing it down first revisit the privacy gate and ordered native backup sheet and then continue to the same proof. Merely viewing the words never marks the backup verified. The deterministic browser fixture supports tap/click and drag-and-drop. Production macOS performs presentation and challenge in native sheets so recovery words never cross Tauri IPC or enter webview state. A deferred wallet carries a persistent **Recovery backup not verified** warning on Overview and in Settings.

- The wallet-type chooser uses three equal decision cards: software, hardware, and shared/recovery. Each card keeps its icon, title, one consequence-focused subtitle, and complexity cue inside the same target; helper copy is not detached below the action.
- Software onboarding keeps a persistent, labeled three-stage progress indicator visible on every step: **Generate → Back up → Protect**. Completed, current, and upcoming stages are distinct, so users can estimate what remains before beginning.
- Hardware-wallet onboarding uses the same persistent component with stages **Connect signer → Review identity → Protect app**. The labels distinguish importing public account data, reviewing the signer identity, and setting Groot's local app PIN. Single-key hardware setup asks for one wallet name only and reuses it as the initial internal signer label; a cable import defaults the empty name to the detected device model. Settings later exposes the wallet name and hardware-signer name separately, because the signer name identifies the key on signing and verification screens. Renaming either is local metadata and never changes fingerprints, public keys, descriptors, or wallet identity. The final step asks only for the Groot app PIN and explains that sending still requires the hardware signer. Ledger Nano and Trezor devices do not display their master fingerprint during this import for an independent comparison, so their reviews bind the public identity returned by the connected device without claiming a device-screen match and require first-address verification on the signer before use. Coldcard retains the explicit fingerprint comparison because Mk4 exposes its eight-character Master Key Fingerprint under **Advanced/Tools → View Identity**; the review provides those steps behind an optional disclosure before enabling the existing confirmation action. Other devices may retain a fingerprint comparison action only when that value is actually available on-device or through an independently trusted export. If the same public descriptor is already registered, creation fails without mutation and the final step presents a prominent duplicate-wallet explanation with a direct route back to the existing wallet.
- Software create always uses 256 bits of OS randomness to generate exactly 24 BIP39 words and one credential as BIP39 passphrase plus app unlock/signing PIN. The protection step uses one compact required acknowledgement covering backup, reset, and different-wallet consequences. Deferred-backup status is omitted from this step and remains persistently visible on Overview and in Settings. An optional collapsed advanced panel accepts 128–256 recorded physical coin flips or 50–100 physical six-sided-die rolls. It shows bounded progress and recent outcomes, permits undo/clear, explains that the OS source remains mandatory, and clears the transcript after every generation attempt.
- Successful software creation pauses on a confirmation screen showing the eight-character BIP32 master fingerprint returned by trusted Rust. The screen uses the shared progress, readable-identifier, insight, and button primitives at the standard confirmation scale. The user is told to record the fingerprint with the recovery words and exact passphrase and can copy it directly. An optional insight tooltip beside its label explains that the public identifier can be matched after recovery but cannot restore the wallet or spend bitcoin. The screen also offers the checksummed BIP389 receive/change multipath descriptor as public watch-only data, with an explicit warning that it reveals every wallet address. A matching fingerprint during later recovery confirms the same words/passphrase wallet, but does not replace either secret.
- **Use hardware signer** is a separate single-key path. It imports only public account data and never generates or accepts the hardware device's seed.
- Recover requires exactly 24 words and the original credential.
- Generated words stay in a zeroized Rust pending session. A secret-free native privacy gate first requires confirmation that no person, camera, or screen sharing can observe the display; only then does the attached native sheet reveal the words. The three columns read vertically as 1–8, 9–16, and 17–24. Browser fixture words exist only for deterministic UI testing and follow the same concealed-first interaction.
- Failure stays on the current step with an inline error. A successful operation clears credential/recovery input before navigation.
- When any wallet already exists, every add-wallet step has a close action that returns to the selected wallet without consuming the pending onboarding session.
- `unverified Overview/Settings CTA → wallet passphrase → direct native shuffled-word challenge → exact match → verified`, or `… → native privacy gate → ordered backup sheet → native shuffled-word challenge → exact match → verified`. Cancellation, merely viewing the words, and mismatch preserve the unverified marker and do not restrict receiving or spending in this milestone.

## Multiple wallets

`current wallet → Add wallet → create/recover → selected and unlocked`

Hardware-wallet duplicate detection compares the exact canonical public receive descriptor inside Rust. Equal short descriptor checksums are only an integrity signal and do not establish equality. A true duplicate returns the immutable existing wallet ID; **Open wallet** selects only that profile through the normal shell selection flow, and no shortcut is shown when an authoritative ID is unavailable. Reusing another wallet's network setup remains a later, independent copy and never participates in identity matching.

`wallet selector → choose profile → reuse its unexpired session or unlock that profile → kind-appropriate home`

The app shell observes the native session independently of network sync and immediately replaces authenticated route content with the selected wallet's unlock screen after expiry. That transition requests cancellation of any native foreground scan and treats the resulting cancellation/lock responses as navigation rather than route failures. A hardware transaction already under active device review retains its separate bounded review window; once that review returns, an elapsed idle deadline locks the wallet without changing the proposal or collected signatures.

Each profile owns a UUID-isolated directory and unlock session. Switching never lets one wallet authorize another, but it also does not revoke the wallet being left. Returning before that wallet's independent inactivity deadline opens it directly; an expired or never-unlocked wallet shows its own credential screen. The duration is one global preference for every wallet, defaults to five minutes, and is configurable under **Settings → Security → Automatic lock**. Activity in one wallet does not refresh another. Background polling does not count as activity. Deleting the selected profile chooses another remaining profile and returns to that profile's unlock state, or returns to onboarding if no wallets remain.

Desktop exposes the selector in the persistent sidebar. Mobile exposes it beside Overview's overflow action; both use the same shell-owned registry and selection flow, and their popup menus stay inside the visible viewport. The desktop sidebar also shows the native semantic version and short source commit below network status, including while the selected wallet is locked. Activating that build identity copies only its displayed public version-and-commit text and reports success or failure inline and in a toast.

Wallet is the common top-level container. Software-key, hardware-key, multisig, and recovery/inheritance policies all use the same Overview, Activity, and Coins destinations. Policy is an additional detail destination for wallets with multiple signing paths; it is not a separate balance-bearing vault. Balances use the global sats/BTC denomination; Groot does not request or display fiat prices. Notifications are scoped to the selected wallet. If a received transaction is first discovered after it already has a confirmation, Groot combines receipt and confirmation into one toast instead of presenting two events for the same transaction; a sync that finishes after selection changed cannot emit into the newly selected wallet.

## Unlock and deletion

`wallet list → select wallet → focused unlock card → credential check in Rust → wallet` or `invalid_credential → focused unlock card`

For a mainnet candidate profile, unlock asks only for the selected wallet's existing
passphrase or app PIN and focuses that credential field after the profile loads. Rust
uses the credential to open the authentication throttle and decrypt the persisted
per-wallet Core setup. Overview then authenticates Core, verifies sync state and the
exact genesis, and only then permits wallet-data database reads. No remote or
compact-filter fallback is offered.

For a legacy disposable Regtest hardware or multisig profile missing current public metadata or its local PIN verifier: `select profile → explicit unsupported-format explanation → recreate/recover guidance or explicit delete`. Credential entry is disabled. Groot does not infer missing identity metadata, reset the PIN, or mutate the saved files before deletion.

The locked screen's central card names only the selected profile. The persistent desktop sidebar retains the wallet list, **Add wallet**, theme, and network status so another profile can be selected without carrying credential state. Wallet-scoped navigation and Settings remain absent until unlock. Hover, focus, or activation of network status shows the selected wallet's saved non-secret backend type, transport, and activity-sync method plus its last successfully verified public priority fee and network tip. Fresh authenticated checks require unlock because the RPC password remains sealed; missing observations stay unavailable instead of being invented. There is no Back or second add-wallet action inside the unlock card; **Add wallet** in the sidebar is the sole creation entry when profiles exist. Direct fresh-install onboarding redirects back to unlock unless that explicit add-wallet route is active. Software-key wallets call the credential **Wallet passphrase** and explain that it is the BIP39 passphrase that must remain with the recovery words. External-hardware and multisig wallets call it **App PIN** and explain that it protects local Groot data only, not the hardware seed or hidden wallet. Credential fields across onboarding, unlock, signing, descriptor export, recovery, and deletion have explicit show/hide controls.

`unlocked wallet → Settings → wallet details / Lock now / backup information / recovery controls / wallet node / appearance`

Settings clearly labels scope. **Wallet details → Wallet name** updates the selected unlocked wallet's local display name and immediately refreshes the title and wallet switcher; it never rewrites cryptographic identity or recovery artifacts. **Lock now** and the desktop Command/Ctrl+L shortcut affect only the selected wallet. Once accepted, the shortcut blocks concurrent wallet selection, cancels coordinated hardware and sync work, and invokes the same native lock boundary before showing the unlock route. It remains inert in editable fields and dialogs and is neither shown nor active in browser prototypes or mobile builds. **Automatic lock** is global and sets the shared duration used by every wallet's independent inactivity clock. Appearance is also global. Backup, credential, and node controls apply to the selected wallet; Groot never displays the wallet passphrase, and it re-presents recovery words only after fresh authentication through the trusted native privacy gate and backup sheet. Wallet switching and **Add wallet** stay in the persistent wallet list, and policy creation/recovery starts from that add-wallet flow rather than a generic Settings section.

The native lock boundary requests ordinary sync cancellation and performs any wait
for the serialized wallet-operation lock on a blocking worker, keeping the macOS
window event loop responsive. A cancelled sync leaves the last successfully
committed snapshot and timestamp unchanged.

`settings → delete warning → credential + type DELETE → Rust verification/deletion → unlock next wallet / welcome`

For a selected locked disposable regtest wallet: `locked → delete warning → type RESET REGTEST → Rust deletion → next wallet or welcome`. This works for either profile kind and is unavailable on public networks.

Deletion is device-local. It never implies that transaction history disappeared from Bitcoin. Multisig settings opens a dedicated deletion page rather than embedding deletion in backup export. That page links to wallet-backup export and presents the recovery test as an explicit first step, retains an already successful in-session test for the exact current descriptor, and then requires the wallet PIN plus the exact wallet name shown in quotation marks.

## Receive

Opening Receive or Send first pauses and cancels automatic sync. Snapshot and proposal reads wait on a blocking worker rather than the native window thread, so the route remains responsive while an in-flight sync reaches its cancellation boundary. Receive retains one explicit manual refresh action: it runs a single selected-wallet sync, displays local progress, and replaces the current and historical address state from the returned snapshot so an observed mempool payment is visible without leaving the route. It does not restart automatic polling.

`unlock-scoped recent labels or typed full-history matches → choose one to five new/reused labels → recovery-gap check → atomic reveal+permanent assignments → QR/copy`

Multiple unused addresses may await payment concurrently within the configured recovery gap. The prospective index is checked in the same transaction as reveal and label persistence; exceeding the gap reveals nothing, and the setting cannot be lowered below the already-required run. Each request may transition independently to `discarded` and remains monitored. Any observed payment transitions that address to `used`, after which discard is impossible.

Suggestions never prefill a field. Choosing one adds a removable token inside the input and removes it from the available suggestion list; removing the token restores the suggestion. Enter, Tab, comma, and semicolon commit typed text as an in-field token. With empty draft text, Backspace first selects the final token and only a second Backspace removes it. Up to five distinct labels may be selected before submission; existing and provenance-derived records may display more. Every submitted assignment remains immutable. Suggestions disappear with the unlocked wallet surface and come only from that profile's isolated database.

## Single-key send

The global sats/BTC preference applies to the amount field, balance, fees, review, errors, and success copy; BTC is always eight decimals while the wallet boundary remains integer satoshis. In both single-key and multisig amount entry, the visible `sats` or `BTC` unit is a button that converts the current valid input exactly and updates the global preference; invalid text is never reinterpreted under another unit. **Max** asks the native builder for an exact, non-persisted drain preview with the active fee choice and coin-selection policy. Single-key and multisig sends share Economy, Standard, Priority, and Custom fee choices. Fee provenance is shown once in plain language as **Bitcoin Core**; RPC method names stay hidden.

`Intent: one to five explicit new/reused permanent labels+recipient → Amount & fee: amount+privacy strategy or exact coins+fee rate → persist Rust PSBT+assignments → Review funding privacy → Review & sign: authoritative review+credential → sign+broadcast → durable labeled success`

Intent suggestions are read only from the selected unlocked profile and never preselect or overwrite input. A stable single-row strip shows at most four recent labels; typed input filters the complete wallet-scoped history with exact normalized matches first without resizing the surrounding flow when nothing matches. Reusing normalized text binds the new immutable payment intent to the existing stable label entity. This records an intentional relationship for provenance and selection; it does not suppress warnings when the actual PSBT joins distinct public clusters.

The review includes Rust-derived input/output counts and verified wallet-owned change. Review and signing fail closed if the recipient or fee differs from persisted intent or if any remaining output is not controlled by the selected wallet. Multisig PSBTs carry the policy's public account keys and origins so a hardware wallet can reconstruct the reviewed BIP48 policy. An older active proposal may receive that same deterministic public metadata only in the temporary device-signing copy; Groot removes it before merging so the persisted reviewed PSBT changes only when a valid new signature is added. A device that returns without its signature is reported as no signature added, never falsely as an already-used signer.

Every stage is named in the same three-step progress indicator. A compact signer summary identifies Groot on this device for software wallets, or the imported model/label and shortened public fingerprint for external hardware. Its final-height region renders immediately with an accessible wallet-identity loading state, so asynchronous signer metadata never inserts a late card or shifts the payment form. Amount & fee defaults to Balanced automatic selection and offers More private, Lower fee, or exact manual inputs. Coin rows disclose mixed, unknown, and address-reuse provenance before selection and render every authoritative provenance label as a compact tag; change from co-spent A- and B-labeled inputs therefore shows both inherited tags. The manual preview leads with selected amount and funding labels. Weight units remain collapsed under **Input details**. If Rust reports that the manual set links groups even though one existing group can fund the payment, **Use privacy-first selection** clears the manual set and switches explicitly to **More private** automatic selection. The review is derived from the persisted PSBT, while Rust normalizes and persists the mandatory outgoing label alongside that proposal. It states the authoritative funding-input count and shows a calm warning when selected inputs cross known labels/clusters, contain unknown provenance, or use a reused address. Every software, external-signer, and multisig review keeps only recipient, label, network, network fee, amount, and total visible by default. One consistently named **View more details** disclosure contains aggregate input value/count, output count, fee rate, change amount/address, locktime/RBF, and wallet policy where applicable. Exact input outpoints and sequences stay enforced by Rust without adding a second technical sub-section to the review. The recipient is shown as `prefix…suffix` and opens a complete grouped, copy-safe detail modal. Software-wallet authorization keeps that same complete transaction review visible while the user enters the wallet passphrase. External-hardware signing keeps the review on the primary page while the user chooses cable, QR, or file transport, and repeats it after signature before broadcast; the transport modal is an additional trusted-display reference, not the only visible review. Its signed signer row exposes **Discard local signature** with the same non-revocation warning as multisig. Rust removes only the saved external signer's verified partial signatures through an exact-PSBT compare-and-swap, preserves every reviewed transaction and metadata field, and returns the proposal to hardware signing. A wrong credential clears the field and leaves the reviewed proposal available for retry. Software, external-signer, and multisig routes reload the exact active proposal after restart and expose the same compact Overview resume surface; no route rebuilds transaction intent from UI fields. PSBT export opens the native file picker, validates a bounded PSBT at the Rust boundary, suggests the hardware-friendly `groot-xxxxxx-sN.psbt` form instead of exposing a full proposal UUID, and uses `N` as the authoritative collected-signature count so unsigned, partial, and threshold-complete copies remain distinct. It reports a durable success or failure. Canceling any prepared proposal first opens the same destructive review of the payment and collected signatures; only the modal's confirmation calls the wallet-appropriate cancellation boundary. Leaving for Overview preserves the proposal and signatures for later resumption. Broadcast emits a toast and returns an updated snapshot whose activity record uses the permanent outgoing label.

`pending wallet-originated replaceable transaction → Increase fee (RBF) → persisted acceleration PSBT → normal review/sign/broadcast`

`pending transaction with a wallet-controlled output → Spend output (CPFP) → persisted acceleration PSBT → normal review/sign/broadcast`

Acceleration never bypasses review or signer thresholds. Confirmed, non-replaceable, missing-output, insufficient-value, and confirmation-race states fail explicitly and remain retryable after sync.

`wallet-owned inputs → only wallet-owned value outputs → Rust classifies self_spend → activity shows Self-spend and fee debit → no counterparty row`

Transaction kind is authoritative snapshot data, not a UI guess from labels or zero amounts. Compact counterparty addresses and full grouped addresses are mutually exclusive presentation states.

Signer-specific discovery is scoped before HWI touches a device. A health or policy check scans only the selected signer’s saved device type. Single-key receive verification admits only that wallet’s saved signer; multisig receive verification admits any saved signer in that policy and excludes connected signers outside it. If multiple locked devices of the same eligible type cannot yet be distinguished, Groot asks the user to disconnect the extra device instead of choosing one.

`name+recipe or advanced M-of-N → add 3–7 signers → Rust validation/descriptor preview → saved descriptor → signer policy registration when required → app PIN → persisted coordinator`

Signer import paths:

- Desktop USB: Rust invokes the exact reviewed HWI packaged inside the signed macOS app, enumerates a device, and requests the fixed BIP48 test-network account xpub. The user does not install HWI separately, and a packaged public-network build never falls back to a system copy.
- Mounted file: bounded Groot or compatible Coldcard **Export XPUB** JSON containing only a test-chain public origin, fingerprint, and BIP48 account tpub. Both field-based exports and current `p2wsh_desc` key expressions are normalized to the canonical `m/48'/1'/0'/2'` account origin. Private/recovery material, wrong-network paths, mainnet xpubs, and extended private keys are rejected. The inline warning identifies the mismatch and gives the exact safe re-export path instead of exposing a parser error. Manual entry remains available. PSBT signing also supports bounded `crypto-psbt` UR v2 animation/camera through a bundled local QR decoder, with file/text fallback.
- Virtual device: deterministic browser/CI fixture only; it must be visibly identified as a test device.

Selecting a draft or saved signer opens public signer details. The same modal can rename the signer’s local display label; draft changes are persisted with setup progress and saved-wallet changes atomically update local public metadata without changing the fingerprint, xpub, descriptors, policy evidence, or hardware device. **Check signer** always requires the physical signer, regardless of whether its public key originally arrived by USB, QR, file, or manual entry. One explicit aggregate discovery supplies an opaque path hint. The native health operation then opens that exact path and, under one exclusive lease, freshly matches the device type, BIP48 derivation, and complete account xpub. An identified device must also match its live fingerprint. A uniquely path-addressable locked BitBox02, Jade, or Ledger instead starts its vendor login with an exact-path account-key request and must match exactly one saved complete identity; Rust associates that identity's authoritative saved fingerprint. A missing, locked, duplicate-path, or mismatched signer fails with an actionable result. Reading and matching the device-derived account key proves that the connected signer holds the expected wallet identity; it does not create a transaction or replace policy registration, address verification, or an end-to-end PSBT signing test. Rust alone persists the latest result and timestamp per signer fingerprint; the renderer cannot author a health result, and no history is retained.

Trezor Model One PIN entry exists only while a live native PIN challenge is idle and error-free. Starting a fresh layout immediately invalidates the prior challenge and removes its blank position grid. A timeout, rejected challenge, I/O failure, or disconnected device keeps the grid removed, clears the selected positions, and requires a newly requested device layout before Groot accepts more input. KeepKey is unsupported and is rejected by trusted discovery rather than entering this flow.

The saved Policy page renders one row per signer rather than a separate readiness list plus an identity list. Each row carries a compact policy-status badge. Opening the signer reveals its public identity, connection health, policy-registration requirement and evidence, plus the relevant setup or reverification action. A Coldcard that lacks Groot's durable acknowledgement is labeled **Setup not recorded** because Groot cannot infer whether the persistent policy is absent from the physical device. This acknowledgement remains available when the Coldcard public key was added through its XPUB file; import transport must not prevent recording the later on-device policy check.

Opening any USB picker performs one bounded aggregate HWI enumeration. Rust validates the complete response and filters eligible saved identities afterward; three or seven saved device families still produce one subprocess `enumerate`. ## Multisig payment target flow

When Rust proves that the recipient output belongs to the selected wallet, every proposal and hardware review labels it **Self-transfer**, states that only the network fee leaves the wallet, and exposes its receive key-origin path alongside the input and change paths. Rust sums every wallet-controlled PSBT output and presents the result as **Consolidating** so the user can compare Groot directly with the hardware signer. The renderer never infers ownership or calculates this total from labels, address text, amount, or change.

This flow is implemented for regtest; see `docs/implementation-status.md` for certification limits.

`Intent: permanent label+recipient → Amount & fee: amount+coins+fee rate → persisted unsigned PSBT → Review & sign: authoritative review+collect any k signatures → Miniscript satisfaction/finalization → broadcast`

Before a PSBT exists, completing Intent atomically saves one bounded, wallet-scoped payment draft through the authenticated Rust boundary. Leaving Amount & fee for Coins or fully restarting Groot therefore preserves the recipient, permanent labels, amount, fee choice, and eligible coin-selection preference; returning to Send after unlock resumes the same stage after revalidating selected coins against the fresh snapshot. Overview exposes both **Resume** and **Discard draft** on the unfinished-intent callout, and resumed Send keeps **Discard draft** beside Back. The destructive confirmation names the saved fields and states that no transaction or signature exists. Confirming clears the selected wallet's draft and suppresses Send's route-exit auto-save so the removed draft is not recreated. Preparing the authoritative proposal also clears the draft and hands continuity to Rust's persisted exact-PSBT boundary. Payment drafts never contain credentials, private keys, PSBTs, device paths, or hardware prompt state and never cross wallet profiles. The optional versioned owner-only file is additive; no wallet database, registry, proposal, profile, or backup format changes.

The three stages use the same labeled progress indicator as single-key sends. A compact signer summary shows the threshold, imported signer labels/models, and shortened public fingerprints; it marks signatures only from the authoritative proposal and does not claim physical connectivity. Each signer is `ready`, `awaiting`, `signing`, `signed`, `rejected`, or `unavailable`. USB, bounded `crypto-psbt` UR v2 QR, and file signatures converge on one Rust PSBT merge function. Imported data must match the proposal's unsigned transaction and descriptor identity. Closing any signed-PSBT import dialog clears its transient file contents and validation state before the next opening; a rejection remains durable on the transaction page in the standard inline error panel without retaining the rejected PSBT. A collected signer row exposes an accessible **Discard local signature** action with confirmation. That action removes only the selected signer's partial signatures from Groot's canonical local PSBT and returns a ready proposal to collecting when needed; it is explicitly not revocation because previously exported or shared PSBT copies remain valid. Once the threshold is met, **Save signed PSBT** remains available beside the finalization controls so the complete signed artifact can be archived before broadcast. The app PIN unlocks coordinator data; it never substitutes for a hardware signature. While an active proposal exists, Overview shows its signature progress in a compact resume action without exposing its label, amount, recipient, or signer identities. A fully signed proposal changes that action to **Payment ready to broadcast**; opening either state resumes the exact persisted proposal. Confirmed **Cancel payment** deletes the local proposal and then returns to the selected wallet Overview; it never leaves the user in a fresh send form that could be mistaken for the canceled proposal.

The hardware-signing modal offers one explicit in-place rescan. Duplicate requests share a native aggregate single flight, and the coordinator permits only one active HWI operation plus one coalesced discovery. Every explicit opening and rescan performs fresh aggregate enumeration; a prior opaque capability cannot keep a disconnected signer visible. Discovery's absolute deadline is 90 seconds including admission because aggregate HWI enumeration may itself contain BitBox password entry; selected-device prompts retain five minutes, block scans, receive priority, and excess work fails with `hardware_busy`. Dismissing the modal, navigating, or switching wallets cancels native queued/running work and prevents a late prompt or stale persistence. A signer outside the wallet quorum, an unavailable fingerprint, or a rejected signing request remains as a durable inline modal error; the page behind the overlay is never the sole error surface. A recent scan path is only an opaque hint: immediately before signing Groot freshly matches the live device type, fingerprint, derivation, and complete saved account xpub, then signs under the same exclusive lease. When a hardware request reaches either a success or error result, Groot closes any recipient or change-address detail overlay that was opened from the signing modal. A failure keeps the parent signing modal open with its durable result and recovery action directly visible; a success continues through the normal signed-proposal transition. Direct hardware responses may normalize or replace public PSBT metadata. Groot first requires the exact reviewed unsigned transaction and rejects finalized inputs and conflicting returned prevout or fee-source data. It does not merge any returned metadata and cryptographically verifies only the returned partial signatures against its untouched canonical PSBT. When Ledger repeats wallet-policy authorization as the first phase of an HWI signing request, Groot keeps the saved policy reference visible while the request runs. The user explicitly advances Groot to the authoritative transaction reference after approving the policy, and can reopen the policy reference without interrupting that request. Groot must never hide both references while Ledger is awaiting approval. When the current scan detects a connected Coldcard for a wallet with a Coldcard signer, the modal offers the same public registration descriptor, so an unknown-wallet failure is recoverable without rebuilding the coordinator. Coldcard-specific help is absent when only another signer family is connected.

Only transaction signing receives a ten-minute absolute device deadline for complete policy, output, fee, and confirmation review. Other selected-device interactions remain bounded at five minutes and discovery remains bounded at 90 seconds. Before a new scan and after any `wallet_locked` hardware response, the UI consults the non-renewing native session; expiry closes all hardware overlays and routes directly to unlock.

## Descriptor backup and recovery scan

`one app PIN authorization → prepare both public BSMS and Groot JSON in memory → switch formats without repeating the PIN → copy/download/one-page printable QR backup → named file ready → first-address drill → offline storage`

The format selector remains available after export. Switching restores the corresponding authorized public record and its correct download format, and clears a previous recovery-drill result; an imported file remains separate from the generated formats. The PIN is cleared after the request, and leaving the route discards both in-memory exports. Activating the receive-descriptor QR opens the regular focus-contained large-QR modal without authorizing another operation.

BSMS is the interoperable public standard for a standard sortedmulti wallet. The recovery picker also accepts public `.txt` descriptor exports containing a BIP-389 multipath descriptor, an explicit receive/change pair, or a standard receive descriptor from which the matching change branch can be reconstructed without ambiguity. Groot JSON retains custom recovery-policy metadata and signer display labels. It does not export transaction history, receive/payment assignments, proposals, provenance, or suggestions from the isolated wallet database. Every format is bounded, parsed, network checked, and first-address derived in Rust; portable and explicit branches must agree. The app PIN authorizes export but is not a file-encryption password: the exported watch-only record cannot spend, yet should stay private because it reveals address derivation and wallet activity. Explicit export re-authentication accepts the correct wallet app PIN even after an idle-session timeout, then refreshes that session. The PDF view is a single A4 sheet with wallet name, a legible UTC creation date, policy, network, signer fingerprints, and vertically stacked receive/change descriptor QR codes. Groot keeps the normal Export & verify screen visible throughout: after a destination is chosen, an isolated hidden WebKit renderer creates the public sheet and Rust writes it without returning the path to the main webview. The normal path-private Finder action confirms a successful macOS save. Loading a recovery-test file visibly retains its filename. A recovery test against the currently selected wallet must compare descriptor identity, not merely validate syntax, and its inline state, toast, and deletion gate all use that one authoritative comparison. Export, recovery-test, and deletion failures render inside their own sections so one action cannot appear to fail another.

`First Bitcoin Core open → choose new-wallet tip, birthday block, or full history → default gap 20 → credential → persist → asynchronous resumable Core scan → lock/reopen reattaches → durable verified balance/history`

`Settings → birthday+gap draft → credential → persist → asynchronous Core rescan with block progress → complete or cancel safely → durable balance/history`

Before the first Core scan Groot shows no numeric verified balance and does not let the normal scheduler silently start from genesis. **New wallet** uses the tested node tip only after the user confirms there is no earlier activity; **Existing wallet** requires a birthday block before the earliest possible payment; **Full history** uses height `0` and warns that it can take tens of minutes. Editing is draft-only until authenticated save. A birthday after the first payment can omit history. Gap limits are bounded from 20 through 1,000; 20 is standard and affects derived-address discovery, not block-range speed. Groot waits while Core is in initial block download or below the wallet's last verified checkpoint. A recovery scan anchors immediately before its birthday, so a pruned node rejects a birthday at or below its retained prune height with an actionable archival-node alternative. Each applied block and its progress checkpoint are persisted. Inactivity may lock the wallet UI without cancelling the already-authorized scan. Re-unlock reattaches to its live status. Cancellation, failure, or process interruption remains visible; retry continues after the last persisted block only when that checkpoint still agrees with Core and otherwise restarts from the configured birthday.

Core's block percentage stays below 100% while its pending-transaction pass
reconciles unconfirmed spends and receipts. The UI names that phase instead
of showing an apparently finished scan; 100% belongs to a committed result.
Settings saves and cancellation run outside the native UI thread, and the
explicit rescan pauses automatic sync until its terminal state. Cancelling
checks between remote RPC calls, with one in-flight request still bounded by
the node timeout. Existing verified history is not presented as a new scan
result until the entire reconciliation succeeds.

## Coin privacy insight

`Coins → detect two or more UTXOs at one known address → mark each affected coin → optional linked-coin detail`

An address displayed only as a multisig hardware-policy verification reference is not a payment request. The review explicitly says not to fund it and directs the user to create a permanently labeled Receive request after wallet creation. If an external payment nevertheless reaches such an address, Groot keeps **Unknown source** until the user chooses the exceptional one-time recovery flow:

`Coins → expand exact unlabeled received multisig output → Add first permanent label → Rust verifies current external output + absent metadata → atomically persist used address + immutable receive label + known provenance`

The action is unavailable for change, an already labeled address, a spent or foreign output, discreet mode, and non-multisig wallets. It assigns initial metadata once; it never edits or reuses a label.

## Freeze or unfreeze a coin

`Coins → select Freeze or Unfreeze → confirm the named coin or selection → persist the new eligibility state → inline state + toast`

The confirmation explains only the practical effect: frozen coins cannot be selected for automatic or manual spending until unfrozen. It never shows the technical outpoint unless the user separately opens coin details.

### Add a single hardware signer

1. Choose **Use hardware signer**.
2. Initialize and unlock the device; select its hidden/passphrase wallet on-device if used.
3. Import over cable, or load/paste a public BIP84 descriptor/xpub export from SD/QR.
4. Groot rejects private data and normalizes the test-chain account to `m/84'/1'/0'`.
5. Compare the master fingerprint with the device/export.
6. Name the wallet and set its independent Groot app PIN.
7. To spend, review the PSBT, sign by exact-fingerprint USB or offline PSBT, then enter the app PIN to broadcast.

Passport Core uses QR or microSD. Trezor Model One host passphrase entry is unavailable; do not fall back to an empty passphrase.

### Configure network services

1. During software, hardware, or multisig wallet creation, keep the default **Use [wallet]’s network setup** choice or turn it off. Groot copies the saved Core connection and activity-sync method from that unlocked wallet; wallet history and scan state remain separate. Software and multisig creation do not publish the new profile or show their success state until the native copy attempt has completed. If the source locks or fails validation before creation, the new wallet is still created offline and the UI directs the user to Settings.
2. For an existing wallet on every compiled network, including Mainnet, open **Settings → Use an existing network setup**. Saved source wallets remain listed, but a locked source is marked **Unlock first** and cannot be adopted until the user opens and unlocks it. Return to the destination wallet, choose the ready source, and enter the current wallet's credential. Groot verifies Core before protecting an independent copy for the current wallet. Later edits never change the source wallet. When Overview detects a missing or unusable setup, the manual sync and retry actions open this reuse dialog directly when a source exists, or the existing Core configuration dialog otherwise.
3. Open **Settings → Wallet activity sync** and explicitly choose Bitcoin Core or compact filters.
4. Compact filters disclose confirmed-only behavior. Public discovery requires at least two peers. Manual mode accepts numeric `IP:port` peers and never falls back; adding a loopback Tor proxy also disables discovery so DNS cannot escape locally.
5. Open **Settings → Fee and broadcast node** to configure Bitcoin Core independently. Choosing compact filters never changes this service and never silently uses it for wallet discovery.
6. On wallet overview startup, compact-filter mode shows sanitized connection/scan/apply progress. Failure leaves the prior balance visible and names the last verified block height. In the pinned engine, public filters are memory-only and download again after app restart; wallet checkpoints and history remain in SQLite.
7. Test Core authentication and availability separately. Groot reports full/pruned history, prune height, IBD, disk use, and filter-index state. The health test retries a bounded transient transport interruption but fails immediately for the wrong chain or a missing required RPC permission. Core RPC activity sync does not require `blockfilterindex`; a pruned node must retain all blocks needed after the wallet checkpoint. Consecutive background-sync failures back off instead of continuously contending with manual checks. A compact-filter refresh fails visibly if its selected peers cannot reach a verified tip.
8. A Bitcoin Core wallet that has never synced shows **0** as a non-authoritative placeholder and **Never synced**. Without a ready saved Core connection, **Connect Bitcoin Core** opens Settings instead of the first-history modal. With Core ready, **New wallet** is preselected; existing-wallet birthday/full-history choices and the address gap limit are disclosed only on request.
9. A mainnet existing wallet's lock screen requests only its wallet passphrase or app PIN. Rust checks and updates only the persisted authentication throttle through its separate native database permit. After authentication, Overview asks Rust to decrypt and verify that wallet's saved admitted loopback HTTP or direct HTTPS Core setup before its first wallet-data database read. Failure stays on Overview with retry and Settings available; the user does not re-enter saved RPC fields during routine lock, inactivity, or relaunch recovery. In Settings, **Remote TLS** selects direct HTTPS with username/password and system certificate trust; Mainnet still hides Tor and rejects remote plaintext HTTP.

The later recovery, durable-cache, direct-P2P-broadcast, adversarial-peer, public-network, and platform work is explicitly gated by [`compact-filter-deferred-work.md`](compact-filter-deferred-work.md). None is an implicit fallback from this flow.

Plain-address and BIP21 payment QR requests are parsed and network-checked only inside Rust before Send prefills the reviewed recipient, optional amount, and an editable label suggestion. Unknown required parameters fail closed. Payjoin V2 BIP21 requests are recognized, but until ADR 0031's encrypted-session, transport, fresh-review, fallback-consent, and interoperability gates are met, Groot rejects them rather than advertising, initiating, or silently downgrading a Payjoin session.

## Sort coins

`Coins → compact sort control → newest/oldest, largest/smallest, or label A–Z/Z–A`

Newest source transaction is the default. Sorting is presentation-only and never changes selection, freeze state, labels, or spend eligibility. Date sorting leaves coins without a known source-transaction timestamp after dated coins.

## External-signer health check

An explicit scan performs one aggregate HWI enumeration, then Rust filters the validated result to the saved signer. Unrelated families may be observed by HWI but are never offered for the wallet or used as identity. The opaque ephemeral path is not persisted and is only a hint. The native health operation opens that path and freshly checks the saved type, fingerprint, BIP84 derivation, and full account xpub under one lease.

## Fee acceleration and label interchange

`pending wallet-originated replaceable transaction → Rust quotes exact minimum and safe default → Groot leads with “spend X sats more” while recipient and payment amount stay unchanged → user continues or optionally changes the rate / opens fee details → Rust returns the persisted higher-fee PSBT → normal review/sign/broadcast → “Transaction accelerated” confirmation with prominent amount, copyable compact transaction ID, aligned wallet/activity actions, and a privacy-disclosed explorer action when supported → transaction details show earlier transaction — fee increased → newer transaction, with compact IDs and optional accounting insight → active transaction keeps its normal sent amount; superseded original is struck through and excluded → newer transaction links backward and original links forward`

`pending transaction with spendable wallet output → Rust quotes the combined parent/child package → Groot leads with “spend X sats more” → user continues or optionally changes the package rate / opens fee details → Rust computes and persists the child PSBT → normal review/sign/broadcast → “Transaction accelerated” confirmation`

Confirmed, non-replaceable, below-minimum, insufficient-value, stale-node-policy, and confirmation-race states fail explicitly without changing lineage. If a replacement cannot preserve the recipient amount because neither available change nor another spendable wallet coin can cover the higher fee, the rate remains empty instead of displaying zero and the durable error explains the funding shortfall and next safe actions. Groot never silently subtracts an RBF fee increase from a normal recipient output. The default acceleration and proposal-review surfaces show the additional satoshi cost rather than protocol-policy metrics; **Change fee rate**, **View fee details**, and the normal **View more details** disclosure retain optional control and exact authoritative values. For CPFP the editable value is explicitly the package target, while the child fee is derived and reviewed as the added cost. Overview and Activity collapse a completed RBF conflict set into one normal payment row: the canonical newer transaction when it wins, the confirmed original if it wins the race, or the broadcast newer transaction while pending. Opening that row shows a short honest outcome first; **View fee increase details** reveals the original-to-newer journey, rates, identifiers, and accounting explanation. Hardware review and thresholds remain unchanged.

`Settings → Import or export wallet labels → privacy warning → native JSONL picker → Rust BIP329 validation/export → durable inline result + toast`

Export orders the representable permanent label subset deterministically. Import preflights the entire bounded file, appends only new immutable assignments, treats duplicates as unchanged, and commits label plus coin-spendability changes atomically. Cancellation changes nothing; foreign-wallet/network, private-material, schema, signer-name, spendability, and capacity conflicts change nothing. The file creates no live phone/desktop synchronization state.

`Transaction details → privacy disclosure → View on mempool.space → Rust validates txid and constructs allowlisted public-test-network URL → OS browser or durable failure`

`Overview → More wallet actions → Health check` and `Settings → Hardware signer identity & health` open the same public identity detail used by multisig signers. Groot requires the physical device and an explicit recent scan, then uses exact-path HWI `getkeypool` to obtain a single response containing the live fingerprint, requested BIP84 derivation, and full account xpub. Rust compares all fields with authoritative saved metadata, revalidates the selected wallet, and persists the result atomically. Overview and Settings mirror that native wallet-scoped result, which survives app restart; no result history is retained. The Settings row labels that state **Checked**, **Attention**, or **Not checked** and shows the locally formatted time of the latest attempt when one exists. A health result does not replace receive-address verification or an end-to-end signing test.
