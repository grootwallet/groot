# Wallet and coordinator flows

This document describes user-visible state transitions. The product specification owns behavior; Rust owns wallet truth; these flows own presentation and navigation.

## Single-key onboarding

`welcome → Generate software wallet → private recovery-word reveal → verify all 24 words now or defer → wallet passphrase → created → overview`

The generated words remain hidden until the user confirms their surroundings are private. After writing them down, the user is strongly encouraged to reconstruct all 24 from a shuffled pool in the exact original order, but may choose **Verify later** without blocking creation. Deferred verification offers two freshly authenticated native paths: users with the written backup go directly to the shuffled proof, while users who did not finish writing it down first revisit the privacy gate and ordered native backup sheet and then continue to the same proof. Merely viewing the words never marks the backup verified. The deterministic browser fixture supports tap/click and drag-and-drop. Production macOS performs presentation and challenge in native sheets so recovery words never cross Tauri IPC or enter webview state. A deferred wallet carries a persistent **Recovery backup not verified** warning on Overview and in Settings.

- The wallet-type chooser uses three equal decision cards: software, hardware, and shared/recovery. Each card keeps its icon, title, one consequence-focused subtitle, and complexity cue inside the same target; helper copy is not detached below the action.
- Software onboarding keeps a persistent, labeled three-stage progress indicator visible on every step: **Generate → Back up → Protect**. Completed, current, and upcoming stages are distinct, so users can estimate what remains before beginning.
- Hardware-wallet onboarding uses the same persistent component with stages **Connect signer → Review identity → Protect app**. The labels distinguish importing public account data, reviewing the signer identity, and setting Groot's local app PIN. Single-key hardware setup asks for one wallet name only and reuses it as the initial internal signer label; a cable import defaults the empty name to the detected device model. Settings later exposes the wallet name and hardware-signer name separately, because the signer name identifies the key on signing and verification screens. Renaming either is local metadata and never changes fingerprints, public keys, descriptors, or wallet identity. The final step asks only for the Groot app PIN and explains that sending still requires the hardware signer. Ledger Nano and Trezor devices do not display their master fingerprint during this import for an independent comparison, so their reviews bind the public identity returned by the connected device without claiming a device-screen match and require first-address verification on the signer before use. Other devices may retain a fingerprint comparison action only when that value is actually available on-device or through an independently trusted export. If the same public descriptor is already registered, creation fails without mutation and the final step presents a prominent duplicate-wallet explanation with a direct route back to the existing wallet.
- Software create always uses 256 bits of OS randomness to generate exactly 24 BIP39 words and one credential as BIP39 passphrase plus app unlock/signing PIN. An optional collapsed advanced panel accepts 128–256 recorded physical coin flips or 50–100 physical six-sided-die rolls. It shows bounded progress and recent outcomes, permits undo/clear, explains that the OS source remains mandatory, and clears the transcript after every generation attempt.
- **Use hardware signer** is a separate single-key path. It imports only public account data and never generates or accepts the hardware device's seed.
- Recover requires exactly 24 words and the original credential.
- Generated words stay in a zeroized Rust pending session. A secret-free native privacy gate first requires confirmation that no person, camera, or screen sharing can observe the display; only then does the attached native sheet reveal the words. The three columns read vertically as 1–8, 9–16, and 17–24. Browser fixture words exist only for deterministic UI testing and follow the same concealed-first interaction.
- Failure stays on the current step with an inline error. A successful operation clears credential/recovery input before navigation.
- When any wallet already exists, every add-wallet step has a close action that returns to the selected wallet without consuming the pending onboarding session.
- `unverified Overview/Settings CTA → wallet passphrase → direct native shuffled-word challenge → exact match → verified`, or `… → native privacy gate → ordered backup sheet → native shuffled-word challenge → exact match → verified`. Cancellation, merely viewing the words, and mismatch preserve the unverified marker and do not restrict receiving or spending in this milestone.

## Multiple wallets

`current wallet → Add wallet → create/recover → selected and unlocked`

`wallet selector → choose profile → reuse its unexpired session or unlock that profile → kind-appropriate home`

Each profile owns a UUID-isolated directory and unlock session. Switching never lets one wallet authorize another, but it also does not revoke the wallet being left. Returning before that wallet's independent inactivity deadline opens it directly; an expired or never-unlocked wallet shows its own credential screen. The duration is one global preference for every wallet, defaults to five minutes, and is configurable under **Settings → Security → Automatic lock**. Activity in one wallet does not refresh another. Background polling does not count as activity. Deleting the selected profile chooses another remaining profile and returns to that profile's unlock state, or returns to onboarding if no wallets remain.

Desktop exposes the selector in the persistent sidebar. Mobile exposes it beside Overview's overflow action; both use the same shell-owned registry and selection flow, and their popup menus stay inside the visible viewport.

Wallet is the common top-level container. Software-key, hardware-key, multisig, and recovery/inheritance policies all use the same Overview, Activity, and Coins destinations. Policy is an additional detail destination for wallets with multiple signing paths; it is not a separate balance-bearing vault. Balances use the global sats/BTC denomination; Groot does not request or display fiat prices. Notifications are scoped to the selected wallet. If a received transaction is first discovered after it already has a confirmation, Groot combines receipt and confirmation into one toast instead of presenting two events for the same transaction; a sync that finishes after selection changed cannot emit into the newly selected wallet.

## Unlock and deletion

`wallet list → select wallet → focused unlock card → credential check in Rust → wallet` or `invalid_credential → focused unlock card`

For a legacy disposable Regtest hardware or multisig profile missing current public metadata or its local PIN verifier: `select profile → explicit unsupported-format explanation → recreate/recover guidance or explicit delete`. Credential entry is disabled. Groot does not infer missing identity metadata, reset the PIN, or mutate the saved files before deletion.

The locked screen's central card names only the selected profile. The persistent desktop sidebar retains the wallet list, **Add wallet**, theme, and network status so another profile can be selected without carrying credential state. Wallet-scoped navigation and Settings remain absent until unlock. Hover, focus, or activation of network status shows only data Groot can verify: public fee policy is available while locked, while node height, backend, and transport are checked after unlock. There is no Back or second add-wallet action inside the unlock card; **Add wallet** in the sidebar is the sole creation entry when profiles exist. Direct fresh-install onboarding redirects back to unlock unless that explicit add-wallet route is active. Software-key wallets call the credential **Wallet passphrase** and explain that it is the BIP39 passphrase that must remain with the recovery words. External-hardware and multisig wallets call it **App PIN** and explain that it protects local Groot data only, not the hardware seed or hidden wallet. Credential fields across onboarding, unlock, signing, descriptor export, recovery, and deletion have explicit show/hide controls.

`unlocked wallet → Settings → wallet details / Lock now / backup information / recovery controls / wallet node / appearance`

Settings clearly labels scope. **Wallet details → Wallet name** updates the selected unlocked wallet's local display name and immediately refreshes the title and wallet switcher; it never rewrites cryptographic identity or recovery artifacts. **Lock now** affects only the selected wallet. **Automatic lock** is global and sets the shared duration used by every wallet's independent inactivity clock. Appearance is also global. Backup, credential, and node controls apply to the selected wallet; Groot never displays the wallet passphrase, and it re-presents recovery words only after fresh authentication through the trusted native privacy gate and backup sheet. Wallet switching and **Add wallet** stay in the persistent wallet list, and policy creation/recovery starts from that add-wallet flow rather than a generic Settings section.

`settings → delete warning → credential + type DELETE → Rust verification/deletion → unlock next wallet / welcome`

For a selected locked disposable regtest wallet: `locked → delete warning → type RESET REGTEST → Rust deletion → next wallet or welcome`. This works for either profile kind and is unavailable on public networks.

Deletion is device-local. It never implies that transaction history disappeared from Bitcoin. Multisig settings opens a dedicated deletion page rather than embedding deletion in backup export. That page links to wallet-backup export and presents the recovery test as an explicit first step, retains an already successful in-session test for the exact current descriptor, and then requires the wallet PIN plus the exact wallet name shown in quotation marks.

## Receive

Opening Receive or Send first pauses and cancels automatic sync. Snapshot reads wait on a blocking worker rather than the native window thread, so the route remains responsive while an in-flight sync reaches its cancellation boundary.

`recovery-gap check → mandatory permanent label → atomic reveal+label → QR/copy`

Multiple unused addresses may await payment concurrently within the configured recovery gap. The prospective index is checked in the same transaction as reveal and label persistence; exceeding the gap reveals nothing, and the setting cannot be lowered below the already-required run. Each request may transition independently to `discarded` and remains monitored. Any observed payment transitions that address to `used`, after which discard is impossible.

## Single-key send

The global sats/BTC preference applies to the amount field, balance, fees, review, errors, and success copy; BTC is always eight decimals while the wallet boundary remains integer satoshis. **Max** asks the native builder for an exact, non-persisted drain preview with the active fee choice and coin-selection policy. Single-key and multisig sends share Economy, Standard, Priority, and Custom fee choices. Fee provenance is shown once in plain language as **Bitcoin Core**; RPC method names stay hidden.

`Intent: permanent label+recipient → Amount & fee: amount+privacy strategy or exact coins+fee rate → persist Rust PSBT+label → Review funding privacy → Review & sign: authoritative review+credential → sign+broadcast → durable labeled success`

The review includes Rust-derived input/output counts and verified wallet-owned change. Review and signing fail closed if the recipient or fee differs from persisted intent or if any remaining output is not controlled by the selected wallet. Multisig PSBTs carry the policy's public account keys and origins so a hardware wallet can reconstruct the reviewed BIP48 policy. An older active proposal may receive that same deterministic public metadata only in the temporary device-signing copy; Groot removes it before merging so the persisted reviewed PSBT changes only when a valid new signature is added. A device that returns without its signature is reported as no signature added, never falsely as an already-used signer.

Every stage is named in the same three-step progress indicator. A compact signer summary identifies Groot on this device for software wallets, or the imported model/label and shortened public fingerprint for external hardware. Its final-height region renders immediately with an accessible wallet-identity loading state, so asynchronous signer metadata never inserts a late card or shifts the payment form. Amount & fee defaults to Balanced automatic selection and offers More private, Lower fee, or exact manual inputs. Coin rows disclose mixed, unknown, and address-reuse provenance before selection and render every authoritative provenance label as a compact tag; change from co-spent A- and B-labeled inputs therefore shows both inherited tags. The manual preview leads with selected amount and funding labels. Weight units remain collapsed under **Input details**. If Rust reports that the manual set links groups even though one existing group can fund the payment, **Use privacy-first selection** clears the manual set and switches explicitly to **More private** automatic selection. The review is derived from the persisted PSBT, while Rust normalizes and persists the mandatory outgoing label alongside that proposal. It states the authoritative funding-input count and shows a calm warning when selected inputs cross known labels/clusters, contain unknown provenance, or use a reused address. Every software, external-signer, and multisig review keeps only recipient, label, network, network fee, amount, and total visible by default. One consistently named **View more details** disclosure contains aggregate input value/count, output count, fee rate, change amount/address, locktime/RBF, and wallet policy where applicable. Exact input outpoints and sequences stay enforced by Rust without adding a second technical sub-section to the review. The recipient is shown as `prefix…suffix` and opens a complete grouped, copy-safe detail modal. Software-wallet authorization keeps that same complete transaction review visible while the user enters the wallet passphrase. External-hardware signing keeps the review on the primary page while the user chooses cable, QR, or file transport, and repeats it after signature before broadcast; the transport modal is an additional trusted-display reference, not the only visible review. Its signed signer row exposes **Discard local signature** with the same non-revocation warning as multisig. Rust removes only the saved external signer's verified partial signatures through an exact-PSBT compare-and-swap, preserves every reviewed transaction and metadata field, and returns the proposal to hardware signing. A wrong credential clears the field and leaves the reviewed proposal available for retry. Software, external-signer, and multisig routes reload the exact active proposal after restart and expose the same compact Overview resume surface; no route rebuilds transaction intent from UI fields. PSBT export opens the native file picker, validates a bounded PSBT at the Rust boundary, suggests the hardware-friendly `groot-xxxxxxxx.psbt` form instead of exposing a full proposal UUID, and reports a durable success or failure. Canceling any prepared proposal first opens the same destructive review of the payment and collected signatures; only the modal's confirmation calls the wallet-appropriate cancellation boundary. Leaving for Overview preserves the proposal and signatures for later resumption. Broadcast emits a toast and returns an updated snapshot whose activity record uses the permanent outgoing label.

`pending wallet-originated replaceable transaction → Increase fee (RBF) → persisted acceleration PSBT → normal review/sign/broadcast`

`pending transaction with a wallet-controlled output → Spend output (CPFP) → persisted acceleration PSBT → normal review/sign/broadcast`

Acceleration never bypasses review or signer thresholds. Confirmed, non-replaceable, missing-output, insufficient-value, and confirmation-race states fail explicitly and remain retryable after sync.

`wallet-owned inputs → only wallet-owned value outputs → Rust classifies self_spend → activity shows Self-spend and fee debit → no counterparty row`

Transaction kind is authoritative snapshot data, not a UI guess from labels or zero amounts. Compact counterparty addresses and full grouped addresses are mutually exclusive presentation states.

## Multisig setup

Signer-specific discovery is scoped before HWI touches a device. A health or policy check scans only the selected signer’s saved device type. Single-key receive verification admits only that wallet’s saved signer; multisig receive verification admits any saved signer in that policy and excludes connected signers outside it. If multiple locked devices of the same eligible type cannot yet be distinguished, Groot asks the user to disconnect the extra device instead of choosing one.

`name+recipe or advanced M-of-N → add 3–7 signers → Rust validation/descriptor preview → saved descriptor → signer policy registration when required → app PIN → persisted coordinator`

Signer import paths:

- Desktop USB: Rust invokes the exact reviewed HWI packaged inside the signed macOS app, enumerates a device, and requests the fixed BIP48 test-network account xpub. The user does not install HWI separately, and a packaged public-network build never falls back to a system copy.
- Mounted file: bounded Groot or compatible Coldcard **Export XPUB** JSON containing only a test-chain public origin, fingerprint, and BIP48 account tpub. Both field-based exports and current `p2wsh_desc` key expressions are normalized to the canonical `m/48'/1'/0'/2'` account origin. Private/recovery material, wrong-network paths, mainnet xpubs, and extended private keys are rejected. The inline warning identifies the mismatch and gives the exact safe re-export path instead of exposing a parser error. Manual entry remains available. PSBT signing also supports bounded `crypto-psbt` UR v2 animation/camera through a bundled local QR decoder, with file/text fallback.
- Virtual device: deterministic browser/CI fixture only; it must be visibly identified as a test device.

Selecting a draft or saved signer opens public signer details. The same modal can rename the signer’s local display label; draft changes are persisted with setup progress and saved-wallet changes atomically update local public metadata without changing the fingerprint, xpub, descriptors, policy evidence, or hardware device. **Check signer** always requires the physical signer, regardless of whether its public key originally arrived by USB, QR, file, or manual entry. One explicit aggregate discovery supplies an opaque path hint. The native health operation then opens that exact path and, under one exclusive lease, freshly matches the device type, BIP48 derivation, and complete account xpub. An identified device must also match its live fingerprint. A uniquely path-addressable locked BitBox02, Jade, or Ledger instead starts its vendor login with an exact-path account-key request and must match exactly one saved complete identity; Rust associates that identity's authoritative saved fingerprint. A missing, locked, duplicate-path, or mismatched signer fails with an actionable result. Reading and matching the device-derived account key proves that the connected signer holds the expected wallet identity; it does not create a transaction or replace policy registration, address verification, or an end-to-end PSBT signing test. Rust alone persists the latest result and timestamp per signer fingerprint; the renderer cannot author a health result, and no history is retained.

Trezor and KeepKey PIN entry exists only while a live native PIN challenge is idle and error-free. Starting a fresh layout immediately invalidates the prior challenge and removes its blank position grid. A timeout, rejected challenge, I/O failure, or disconnected device keeps the grid removed, clears the selected positions, and requires a newly requested device layout before Groot accepts more input.

The saved Policy page renders one row per signer rather than a separate readiness list plus an identity list. Each row carries a compact policy-status badge. Opening the signer reveals its public identity, connection health, policy-registration requirement and evidence, plus the relevant setup or reverification action. A Coldcard that lacks Groot's durable acknowledgement is labeled **Setup not recorded** because Groot cannot infer whether the persistent policy is absent from the physical device. This acknowledgement remains available when the Coldcard public key was added through its XPUB file; import transport must not prevent recording the later on-device policy check.

The same Trezor PIN-matrix component is available from multisig transaction signing. Unlocking consumes the single-use native challenge and returns to a fresh signer scan without changing the reviewed proposal or its collected signatures.

Before a USB scan, the UI says that the hardware signer must already be initialized with a seed and backed up offline. If a vendor companion app is open, it must be fully quit because its USB session is not transferable to Groot. Devices should be ready in their vendor-specific Bitcoin mode when possible. A uniquely detected locked BitBox02, Jade, or Ledger remains selectable as **Unlock & continue**: selection starts one interactive account-key request, Groot waits while the user completes the trusted-device prompt, and Rust requires the resulting complete account key to select exactly one saved identity before continuing. Jade starts its on-device login, BitBox02 requests its on-device password, and Ledger waits for the user to unlock it and open the network-matching Bitcoin app; Groot never accepts those secrets. Every pending hardware action—discovery, public-key import, device unlock, saved-identity health check, address approval, and signing—uses the same animated live-status panel with action-specific instructions, regardless of signer vendor. A locked Trezor Model One uses its dedicated path: selecting its detected card starts HWI's scrambled PIN matrix in Groot. The Trezor screen alone shows shuffled digits; Groot shows nine blank spatial cells. For each PIN digit, the user taps the blank Groot cell in the same location, so neither PIN digits nor the shuffled matrix are reproduced in the webview. Groot's blank grid never changes; requesting a fresh layout changes only the shuffled digits shown on Trezor. The single-use challenge expires after two minutes and a rejection requires a fresh device layout. A compact help view gives basic Coldcard, BitBox02, Ledger, Trezor, and Jade preparation steps. Detected-but-not-ready devices remain visible with a typed action. A Trezor warning that HWI selected its empty-passphrase standard wallet cannot be imported until the user explicitly chooses **Use standard wallet**; this does not alter any hidden wallet and the resulting fingerprint is bound to the signer. Host entry for a Trezor Model One hidden-wallet passphrase remains unsupported. HWI 3.2.0 can return a BitBox02 or Nova model and exact USB path without a fingerprint because it samples the lock state before on-device password entry finishes. Groot treats that result as **Detected**, but does not reuse the cached HID path for initial single-key import. HWI rediscovers and opens the BitBox inside the account-key process; a known fingerprint is the selector, while a fingerprint-less selection requires exactly one scanned BitBox family row. That live operation obtains and matches the complete account key after unlock, preserving initial-import identity binding without trusting renderer-supplied identity metadata. BitBoxApp is required only for first-time pairing and must be quit before returning to Groot. Groot passes HWI only the canonical home directory needed to reuse an existing pairing cache. Ledger enumeration may expose a fingerprint while either Bitcoin app is open, so Groot labels it **Detected** until the account-key read proves the network-matching app—Bitcoin Test on Regtest, Signet, and testnet; Bitcoin on mainnet—is open. Groot reopens the exact enumerated device by fingerprint. Ledger passphrases are configured and activated only on the trusted device; Groot neither accepts nor transmits them. BIP48 may request on-device public-key export approval while a standard BIP84 single-key read may complete without a prompt. A failed read stays in a compact retry state with a stable device-specific explanation rather than raw HWI output. Jade login remains on-device, and a PIN-saved Jade must use its Testnet network family for Groot Regtest; network mismatch and canceled login are sanitized into separate actions. Groot never offers device initialization or asks for a hardware-wallet seed. When HWI returns no device, Groot cannot safely infer that an attached USB peripheral is a Coldcard; the empty state tells the user to sign in, enable the Coldcard USB port, reconnect, and rescan.

Opening any USB picker performs one bounded aggregate HWI enumeration. Rust validates the complete response and filters eligible saved identities afterward; three or seven saved device families still produce one subprocess `enumerate`. HWI 3.2.0 can start BitBox device-password entry while opening clients inside `enumerate`, before Groot receives a selectable row, so aggregate discovery allows 90 seconds and initial account-key import allows a five-minute human-interaction window. Process isolation closes the enumeration connection before account-key import; BitBox may therefore request its password again, and Groot says so while treating a fingerprint-less BitBox row as detected rather than proven locked. A visible **Scan again** action is the only way to start a new user scan and remains available when a scan finds other devices but not the signer the user is preparing. Selecting an actionable fingerprint-less row redeems its existing opaque capability into an interactive operation. BitBox single-key import does not reopen Groot's cached HID path after discovery: HWI rediscovers and opens the signer inside the account-key process, using the scanned fingerprint when available or requiring exactly one fingerprint-less BitBox family row. Its canonical BIP84 keypool response must bind the live fingerprint, exact account origin, and account key from that same client before Groot accepts it. Cancellation and all network, descriptor, ambiguity, or identity failures remain terminal. Coldcard readiness still requires preparation and an explicit rescan. Closing or replacing the dialog cancels native queued/running work, clears its opaque capabilities, and invalidates pending presentation updates. If an address is already awaiting approval on a trusted display, Groot instead keeps the dialog visible and asks the user to reject that request on-device; HWI 3.2.0 cannot remotely dismiss Jade's active address screen, and killing its process would strand the prompt and its pending reply. Nested dialog transitions use reference-counted page scroll locking so the underlying page is always restored.

Receive-address verification keeps the complete host-derived address visible in the modal before and throughout the hardware prompt. The derivation path, address index, and Regtest-only hardware-prefix explanation share one collapsed **Address details** disclosure so technical metadata does not compete with the primary comparison. While the signer call is pending, an animated live-status panel explicitly directs the user to compare the complete address and approve on the hardware device; reduced-motion preferences suppress its animation without removing the instruction. If the user requests close through the X, Escape, or backdrop while the trusted-device decision is active, Groot keeps the live operation bound to the modal, changes the panel to the on-device cancellation instruction, and gives the modal a brief repeatable attention response; reduced-motion mode uses a temporary outline instead. The modal closes without verification only after the user rejects on-device and HWI returns that response. The user must compare every character with the trusted display and approve only an exact match; device communication never replaces or obscures the value being reviewed. After an exact match, the modal closes with a success toast, the address shows a compact green check and **Verified on hardware**, and Rust atomically appends a timestamped verification event tied to that address. Hover, keyboard focus, or mobile tap explains that the exact address matched a saved hardware signer and that the evidence is specific to this address. The latest verified time and signer fingerprint remain visible in address details across restarts; repeated checks append evidence rather than overwriting it. On Regtest, Ledger Bitcoin Test, Trezor, and BitBox02 render the same witness output with the testnet `tb1` prefix rather than Regtest's `bcrt1` prefix, which also changes the six-character Bech32 checksum. Rust supplies that exact testnet alias for the review UI and accepts it only when both decoded addresses produce the identical scriptPubKey; malformed addresses, different scripts, and non-Regtest cross-network aliases fail closed. Device recognition uses both the HWI label and model because vendors do not populate those fields consistently.

A successful Trezor PIN submission continues through one bounded native rediscovery so Groot can replace the locked, fingerprint-less capability with the unlocked identity. If the transport still reports the old locked state during that handoff, Groot waits briefly and retries the bounded discovery once without surfacing a false device-unavailable error. A Trezor standard wallet opens the explicit **Use standard wallet** confirmation immediately; confirming then starts the address operation, where Rust freshly proves the complete saved signer identity before display. The user never has to select the Trezor row or press **Scan again** between PIN entry and verification.

During hardware signing, the modal keeps the authoritative recipient, label, amount, network, fee, and total visible while the native signer call is waiting for on-device approval. If Ledger repeats policy authorization at the start of that call, Groot first keeps the saved policy reference visible; after approving that phase on-device, the user explicitly switches Groot to the transaction reference without restarting the call. Both references remain reachable until signing finishes, so neither device phase is reviewed against a hidden or stale host screen. The recipient opens into the standard grouped full-address presentation. On Regtest, Ledger Bitcoin Test and Trezor signing reviews use Rust-supplied `tb1` aliases for both recipient and change only after each alias has been reconstructed from and therefore bound to the exact PSBT output script; other signer families and ordinary reviews retain the canonical network address. The same collapsed **View more details** section used by every send review provides optional insight into the fee rate, exact change amount and address, PSBT key-origin paths for wallet inputs/change, aggregate input/output counts, locktime/RBF, and wallet threshold. These values come from the persisted, validated proposal PSBT so the signer can compare the host and hardware displays without closing or looking through a blurred backdrop. A scanned device whose public fingerprint is already present on every proposal input is marked **Already signed** and cannot be selected again; the native duplicate-signature rejection remains the fail-closed backstop. The primary action remains visible but disabled while the threshold is unmet and states exactly how many signatures are still required. Once the required signatures are verified, signing transport actions disappear and that action becomes **Finalize & broadcast** after the final review and app PIN.

The main multisig proposal review uses the same hierarchy: amount, recipient, permanent label, and network fee remain primary; a collapsed details section contains the change amount and address, transaction shape, fee rate, total debit, and wallet policy. Recipient and change addresses both open into the grouped full-address presentation.

During proposal collection on desktop, signer state sits in a separate side panel with one vertically stacked card per signer. The three-step progress indicator remains above the workspace and describes flow position only; signer cards describe threshold progress only. Narrow layouts return to one content column and keep the compact signer list separate from the step indicator.

Saving an unsigned PSBT, descriptor backup, PDF backup, or device-policy file on macOS adds a compact **Show in Finder** action to the success toast. The action uses a short-lived, single-use native reveal capability and never exposes the selected filesystem path to the webview.

Importing or returning a PSBT must increase the set of policy signers that validly signed every input. A duplicate signature, unchanged PSBT, or signature covering only a subset of inputs is rejected as **no new signatures** without mutating the persisted proposal or its existing valid signatures.

When a Trezor reports both PIN and passphrase requirements, Groot must resolve them in that order: PIN matrix, fresh enumeration/fingerprint, then explicit standard-wallet selection if applicable. The PIN modal keeps one concise rule—match each digit's device-screen position to the same blank Groot cell—and does not repeat explanations around the grid. While the device PIN challenge is active, X, backdrop, and Escape must keep the modal open and acknowledge the blocked dismissal. Because Trezor One provides no on-device cancel control on its PIN matrix, Groot instructs the user to unplug it before explicitly confirming closure. Both multisig and external single-key setup implement the same sequence. A later hardware passphrase does not mutate an imported standard wallet; it derives an independent hidden wallet with a different fingerprint, xpub, descriptors, and addresses, which can be added as a separate Groot wallet.

The default recipe is 2-of-3; 3-of-5 is the larger-group recipe. Advanced mode permits 2 ≤ M ≤ N with 3 ≤ N ≤ 7. 1-of-N is excluded because it has no multisig theft protection. Duplicate fingerprints/xpubs, invalid origins, invalid test-network keys, private descriptors, and unsafe thresholds block review. Creation stores checksummed public descriptors, public signer metadata, a watch-only BDK database, and an encrypted app-PIN marker.

Coldcard signers are marked during USB import or recognized from their public **Export XPUB** file fields. Groot exports the public BIP-380 wallet policy with a normalized ASCII filename whose basename is at most 20 characters, because Coldcard firmware derives a descriptor policy's on-device name from that filename. The setup copy directs the user to save it to microSD or Coldcard Virtual Disk, then import it from **Settings → Multisig Wallets → Import**. Registration is recommended during creation but may be explicitly deferred because the coordinator is watch-only. Before the first Coldcard signature, Groot requires acknowledgement that the normalized name, threshold, and fingerprints matched on-device. This registration lets Coldcard verify change instead of signing an unknown multisig wallet. The acknowledgement is durable but is not represented as cryptographic address-verification evidence.

Policy creation automatically saves one local public draft after meaningful changes. Returning after route navigation, app shutdown, or restart restores Policy, Signers, Verify, or Back up with imported signers and completed descriptor-bound setup evidence intact. The app shell exposes one stable generic notice above every locked-wallet screen because creation is app-level and independent of the selected wallet; after unlock, the notice may show the draft name, step, and signer count. The notice offers direct resume and confirmed discard actions without requiring an unrelated wallet unlock. Rust revalidates the complete draft and regenerates previews; the UI never restores an app PIN or transient hardware prompt. **Discard setup** requires confirmation, explains that signer imports must be repeated, and removes only the unfinished public draft. Creating the wallet clears the draft.

Hardware policy readiness follows the device's actual model instead of presenting one generic **Ready** state:

- **Coldcard MK4:** import and verify the BIP-380 policy file during creation or before its first signature. Coldcard persists the wallet definition and uses it to verify change.
- **Ledger Nano S Plus:** compare the account name and threshold, then open each fingerprint, derivation path, and public key in Groot's standard large identifier view while reviewing the device screens. Groot derives and displays the exact first address before starting the device request; on Regtest it displays the script-equivalent `tb1` encoding used by Ledger Bitcoin Test. Interactive registration and signing receive a bounded five-minute review window. Groot persists descriptor-bound verification evidence. Ledger's protocol can return a wallet-policy HMAC for reuse, but Groot's current HWI CLI path does not retain that HMAC and therefore asks Ledger to authorize the policy again for each signing request. While that request runs, Groot keeps the saved policy reference visible until the user explicitly advances to the transaction reference; either reference can be reopened without interrupting the request.
- **BitBox02:** Groot presents registration in the device's actual order. Before starting, it explains that the account name entered on BitBox02 is device-local, is separate from the Groot wallet name, and must not be the name of any existing multisig account or policy on that device. The user enters a new unused name, confirms the threshold and signer keys, then compares the first address shown after registration. Exact signer identifiers stay collapsed until the comparison step so the default view remains concise. HWI reports a reused account name as an otherwise generic BitBox error, so Rust recognizes only that known error shape and returns a stable name-conflict action without exposing vendor or device details. Groot never retries registration automatically: cancellation, naming failure, and every other device error remain final, and Groot still requires the device-returned address to match the Rust-derived output. Canceling or skipping the device account name is reported as incomplete registration rather than unsupported hardware. A successful first-address proof closes the modal immediately, updates the setup task, and persists descriptor-bound evidence.
- **Blockstream Jade:** address display registers the multisig configuration over USB; Groot uses the same preflight and persists the successful first-address proof. QR registration remains a later transport path.
- **Trezor One:** no persistent wallet-registration state is claimed. Groot supplies the complete policy with the request, supports the PIN-matrix unlock flow, and relies on address/transaction review. On Regtest, Groot shows the Rust-verified script-equivalent `tb1` recipient and change encodings that Trezor displays.
- **BitBox02 Nova:** HWI 3.2.0 places Nova in the BitBox02 USB family. Groot preserves the exact Nova model label and enables the established BitBox policy-registration flow for its dedicated certification scope. The exact model passed the local Regtest BIP84/BIP48 USB core journeys under self-review, including registration, address proof, funded rejection/retry, canonical signing, restart/interruption, hostile-PSBT checks, broadcast/accounting, and independent clean-profile Groot JSON recovery with the funded source preserved and reopened intact. It does not inherit original BitBox02 evidence or claim release certification: isolated cold-cache reset remains open, and Testnet4/package/independent-review/Whisper rows are separate.

Policy registration during setup is recommended but deferrable because coordinator creation is watch-only. Deferral is explicit and visually distinct from completion. An unfinished signer remains **Setup required** on Policy and in the signer strip; selecting it during signing opens its exact device-specific preparation before the transaction can be sent to that device. See [`hardware-policy-readiness.md`](hardware-policy-readiness.md) for the canonical matrix.

The guided Recovery recipe and compatible legacy Inheritance policies require exactly four independent keys. Keys 1–3 are the immediate 2-of-3 primary set; key 4 is recovery-only or heir-only and is never counted in the immediate branch. The creation UI labels the current Recovery roles before review, while Rust rejects any delayed template whose extra signer overlaps the immediate signer set. The V2 policy lab cannot retrofit an extra delayed key onto a three-key wallet; it blocks compilation and directs the user to create a new four-key Recovery wallet.

After funding, every coin has its own relative-block timeline. Overview summarizes security changes and links to Coins. Coins places one compact timeline note inside the list, then names the consequence on each coin directly: the wait starts after confirmation, the backup key is protected, it becomes available in an exact block count, or it can spend. Expanded detail leads with spending access and available actions; privacy/history and technical identifiers are separate collapsed disclosures. Policy keeps the same state calm by default with one explicit no-action-required status, two compact normal-key/next-change facts, a secondary link to Coins for optional action, and collapsed backup-key detail. Expanding that detail reveals the concerned coins with amount and status, without exposing identifiers or actions in the summary. All surfaces state that the immediate 2-of-3 keys stay valid. For an available key, no action is required; Coins offers either a one-coin recovery/heir-key sweep or a policy-specific wait restart with normal keys. The ordinary multisig Send flow keeps only the immediate signers in its signer summary and, when mature coins exist, offers an explicit route into the one-key recovery/heir flow without interrupting a normal 2-of-3 payment.

For one mature, unfrozen coin with a recent verified tip, Coins offers **Restart recovery wait** (legacy Inheritance: **Postpone heir access**) and **Use recovery/heir key**. Restart opens a dedicated wallet-maintenance flow: `one mature outpoint → Rust revalidation → one fresh internal drain output → normal 2-of-3 proposal/signing → broadcast → first confirmation starts the replacement coin's new wait`. The recovery/heir action instead drains exactly that coin to one reviewed external address and accepts only the bound delayed signer set. Fees are recommended and collapsed by default. Existing proposal review, PSBT transport, signature collection, cancellation, and broadcast controls remain authoritative.

`unconfirmed → first confirmation starts per-coin delay → immature → approaching warning → mature warning`

The warning boundary is `min(delay, max(1,008 blocks, ceil(delay / 10)))`; block counts are exact and time is approximate. A verified chain observation older than 30 minutes pauses countdown/time claims but leaves durable last-synced security state visible. Refresh and restart never duplicate a crossing notification. A reorg that moves a coin backward updates the inline state silently and rearms that boundary; crossing it forward again emits one new warning.

The V2 policy lab is analysis-only: compiling does not mutate, upgrade, or replace the selected wallet. Activating a compiled policy requires creating a distinct wallet, reviewing its complete descriptor, and backing it up.

Policy-wallet creation uses four focused stages: **Policy → Signers → Verify → Back up**. Policy itself has two sequential screens: **Choose a plan → Configure wallet**. The first screen contains Standard, Recovery, and disabled **Assisted recovery · Coming soon** cards. Recovery offers reviewed approximate one-, three-, and six-month presets backed by exact block counts and defaults to one month. Existing Inheritance drafts remain resumable but are not offered for new creation. Standard 2-of-3 includes an assisted-signing explanation. Delayed setup shows the approximate time, exact block delay, four-key separation, and recovery-only role while keeping descriptor mechanics optional. The shared progress component renders earlier stages with green checks, the current stage in blue, and later stages as neutral numbers. Moving backward preserves policy decisions and the draft. **Recover** is available only from Policy, before a new-wallet draft progresses. Hardware preparation help and device scanning appear only on Signers. Final review leads with the portable multipath descriptor when safe; separate branches remain optional detail. Back up keeps descriptor saving, optional device-policy registration, and coordinator-PIN creation sequential.

## Multisig payment target flow

This flow is implemented for regtest; see `docs/implementation-status.md` for certification limits.

`Intent: permanent label+recipient → Amount & fee: amount+coins+fee rate → persisted unsigned PSBT → Review & sign: authoritative review+collect any k signatures → Miniscript satisfaction/finalization → broadcast`

The three stages use the same labeled progress indicator as single-key sends. A compact signer summary shows the threshold, imported signer labels/models, and shortened public fingerprints; it marks signatures only from the authoritative proposal and does not claim physical connectivity. Each signer is `ready`, `awaiting`, `signing`, `signed`, `rejected`, or `unavailable`. USB, bounded `crypto-psbt` UR v2 QR, and file signatures converge on one Rust PSBT merge function. Imported data must match the proposal's unsigned transaction and descriptor identity. Closing any signed-PSBT import dialog clears its transient file contents and validation state before the next opening; a rejection remains durable on the transaction page in the standard inline error panel without retaining the rejected PSBT. A collected signer row exposes an accessible **Discard local signature** action with confirmation. That action removes only the selected signer's partial signatures from Groot's canonical local PSBT and returns a ready proposal to collecting when needed; it is explicitly not revocation because previously exported or shared PSBT copies remain valid. Once the threshold is met, **Save signed PSBT** remains available beside the finalization controls so the complete signed artifact can be archived before broadcast. The app PIN unlocks coordinator data; it never substitutes for a hardware signature. While an active proposal exists, Overview shows its signature progress in a compact resume action without exposing its label, amount, recipient, or signer identities. A fully signed proposal changes that action to **Payment ready to broadcast**; opening either state resumes the exact persisted proposal. Confirmed **Cancel payment** deletes the local proposal and then returns to the selected wallet Overview; it never leaves the user in a fresh send form that could be mistaken for the canceled proposal.

The hardware-signing modal offers one explicit in-place rescan. Duplicate requests share a native aggregate single flight, and the coordinator permits only one active HWI operation plus one coalesced discovery. Discovery's absolute deadline is 90 seconds including admission because aggregate HWI enumeration may itself contain BitBox password entry; selected-device prompts retain five minutes, block scans, receive priority, and excess work fails with `hardware_busy`. Dismissing the modal, navigating, or switching wallets cancels native queued/running work and prevents a late prompt or stale persistence. A signer outside the wallet quorum, an unavailable fingerprint, or a rejected signing request remains as a durable inline modal error; the page behind the overlay is never the sole error surface. A recent scan path is only an opaque hint: immediately before signing Groot freshly matches the live device type, fingerprint, derivation, and complete saved account xpub, then signs under the same exclusive lease. When a hardware request reaches either a success or error result, Groot closes any recipient or change-address detail overlay that was opened from the signing modal. A failure keeps the parent signing modal open with its durable result and recovery action directly visible; a success continues through the normal signed-proposal transition. Direct hardware responses may normalize or replace public PSBT metadata. Groot first requires the exact reviewed unsigned transaction and rejects finalized inputs and conflicting returned prevout or fee-source data. It does not merge any returned metadata and cryptographically verifies only the returned partial signatures against its untouched canonical PSBT. When Ledger repeats wallet-policy authorization as the first phase of an HWI signing request, Groot keeps the saved policy reference visible while the request runs. The user explicitly advances Groot to the authoritative transaction reference after approving the policy, and can reopen the policy reference without interrupting that request. Groot must never hide both references while Ledger is awaiting approval. When the current scan detects a connected Coldcard for a wallet with a Coldcard signer, the modal offers the same public registration descriptor, so an unknown-wallet failure is recoverable without rebuilding the coordinator. Coldcard-specific help is absent when only another signer family is connected.

## Descriptor backup and recovery scan

`app PIN authorization → BSMS recommended or Groot JSON → copy/download/one-page printable QR backup → named file ready → first-address drill → offline storage`

BSMS is the interoperable public standard for a standard sortedmulti wallet. The recovery picker also accepts public `.txt` descriptor exports containing a BIP-389 multipath descriptor, an explicit receive/change pair, or a standard receive descriptor from which the matching change branch can be reconstructed without ambiguity. Groot JSON retains custom recovery-policy metadata and labels. Every format is bounded, parsed, network checked, and first-address derived in Rust; portable and explicit branches must agree. The app PIN authorizes export but is not a file-encryption password: the exported watch-only record cannot spend, yet should stay private because it reveals address derivation and wallet activity. Explicit export re-authentication accepts the correct wallet app PIN even after an idle-session timeout, then refreshes that session. The PDF view is a single A4 sheet with wallet name, a legible UTC creation date, policy, network, signer fingerprints, and vertically stacked receive/change descriptor QR codes. Groot keeps the normal Export & verify screen visible throughout: after a destination is chosen, an isolated hidden WebKit renderer creates the public sheet and Rust writes it without returning the path to the main webview. The normal path-private Finder action confirms a successful macOS save. Loading a recovery-test file visibly retains its filename. A recovery test against the currently selected wallet must compare descriptor identity, not merely validate syntax, and its inline state, toast, and deletion gate all use that one authoritative comparison. Export, recovery-test, and deletion failures render inside their own sections so one action cannot appear to fail another.

`Settings → birthday+gap draft → credential → persist → asynchronous Core rescan with block progress → complete or cancel safely → durable balance/history`

Editing is draft-only until authenticated save. Height `0` is safest; a birthday after the first payment can omit history. Gap limits are bounded from 20 through 1,000. While scanning, the modal cannot be dismissed or edited, reports processed and total blocks, and offers cancellation without waiting for the scan command to finish. Each applied block and its progress checkpoint are persisted. Cancellation, failure, or process interruption remains visible after the foreground task ends; retry reruns from the configured birthday rather than trusting a partial result.

## Coin privacy insight

`Coins → detect two or more UTXOs at one known address → mark each affected coin → optional linked-coin detail`

An address displayed only as a multisig hardware-policy verification reference is not a payment request. The review explicitly says not to fund it and directs the user to create a permanently labeled Receive request after wallet creation. If an external payment nevertheless reaches such an address, Groot keeps **Unknown source** until the user chooses the exceptional one-time recovery flow:

`Coins → expand exact unlabeled received multisig output → Add first permanent label → Rust verifies current external output + absent metadata → atomically persist used address + immutable receive label + known provenance`

The action is unavailable for change, an already labeled address, a spent or foreign output, discreet mode, and non-multisig wallets. It assigns initial metadata once; it never edits or reuses a label.

## Freeze or unfreeze a coin

`Coins → select Freeze or Unfreeze → confirm the named coin or selection → persist the new eligibility state → inline state + toast`

The confirmation explains only the practical effect: frozen coins cannot be selected for automatic or manual spending until unfrozen. It never shows the technical outpoint unless the user separately opens coin details.

Address reuse never blocks selection or spending. Every affected row inherits its immutable receive label and carries a compact amber reuse marker. Expanding that coin's details reveals its compact address/outpoint, explains the public link, and identifies the other linked coins by amount and shortened outpoint. Unknown or unavailable addresses are never treated as a reuse match.

## Notifications

- Broadcast: immediately after accepted broadcast, including updated balance.
- Payment received: first observation only, including updated balance.
- First confirmation: zero-to-one confirmation transition only, including updated balance.

The page/list is durable truth. Unique markers persist in Rust until explicitly acknowledged. Delivery is at-least-once across a crash before acknowledgement and consumers use stable IDs idempotently; background/resume scheduling remains a platform integration gate.

While an unlocked desktop session is open, a single ten-second foreground loop syncs only the selected wallet. Returning to the app wakes it immediately. The returned authoritative snapshot updates the current Overview, Activity, Coins, or Receive view, and durable notification markers produce the receipt/confirmation toast once. Sync and notification reads validate the five-minute session but never refresh its idle deadline; an expired session stops polling and returns to that wallet's unlock screen. Sync pauses on onboarding or lock and never overlaps a previous native sync. Fully terminated push/background execution remains a later platform gate.

### Add a single hardware signer

1. Choose **Use hardware signer**.
2. Initialize and unlock the device; select its hidden/passphrase wallet on-device if used.
3. Import over cable, or load/paste a public BIP84 descriptor/xpub export from SD/QR.
4. Groot rejects private data and normalizes the test-chain account to `m/84'/1'/0'`.
5. Compare the master fingerprint with the device/export.
6. Name the wallet and set its independent Groot app PIN.
7. To spend, review the PSBT, sign by exact-fingerprint USB or offline PSBT, then enter the app PIN to broadcast.

Passport Core uses QR or microSD. Trezor Model One host passphrase entry is unavailable; do not fall back to an empty passphrase.

### Configure network services

1. During software, hardware, or multisig wallet creation, keep the default **Use [wallet]’s network setup** choice or turn it off. Groot copies the saved Core connection and activity-sync method from that unlocked wallet; wallet history and scan state remain separate.
2. For an existing wallet, open **Settings → Use an existing network setup**, choose an unlocked source wallet, and enter the current wallet's credential. Groot verifies Core before protecting an independent copy for the current wallet. Later edits never change the source wallet.
3. Open **Settings → Wallet activity sync** and explicitly choose Bitcoin Core or compact filters.
4. Compact filters disclose confirmed-only behavior. Public discovery requires at least two peers. Manual mode accepts numeric `IP:port` peers and never falls back; adding a loopback Tor proxy also disables discovery so DNS cannot escape locally.
5. Open **Settings → Fee and broadcast node** to configure Bitcoin Core independently. Choosing compact filters never changes this service and never silently uses it for wallet discovery.
6. On wallet overview startup, compact-filter mode shows sanitized connection/scan/apply progress. Failure leaves the prior balance visible and names the last verified block height. In the pinned engine, public filters are memory-only and download again after app restart; wallet checkpoints and history remain in SQLite.
7. Test Core authentication and availability separately. Groot reports full/pruned history, prune height, IBD, disk use, and filter-index state. The health test retries a bounded transient transport interruption but fails immediately for the wrong chain or a missing required RPC permission. Core RPC activity sync does not require `blockfilterindex`; a pruned node must retain all blocks needed after the wallet checkpoint. Consecutive background-sync failures back off instead of continuously contending with manual checks. A compact-filter refresh fails visibly if its selected peers cannot reach a verified tip.

The later recovery, durable-cache, direct-P2P-broadcast, adversarial-peer, public-network, and platform work is explicitly gated by [`compact-filter-deferred-work.md`](compact-filter-deferred-work.md). None is an implicit fallback from this flow.

Payjoin V2 BIP21 requests are parsed and network-checked only inside Rust. Until ADR 0031's encrypted-session, transport, fresh-review, fallback-consent, and interoperability gates are met, Groot does not advertise or initiate Payjoin sessions.

## Sort coins

`Coins → compact sort control → newest/oldest, largest/smallest, or label A–Z/Z–A`

Newest source transaction is the default. Sorting is presentation-only and never changes selection, freeze state, labels, or spend eligibility. Date sorting leaves coins without a known source-transaction timestamp after dated coins.

## External-signer health check

An explicit scan performs one aggregate HWI enumeration, then Rust filters the validated result to the saved signer. Unrelated families may be observed by HWI but are never offered for the wallet or used as identity. The opaque ephemeral path is not persisted and is only a hint. The native health operation opens that path and freshly checks the saved type, fingerprint, BIP84 derivation, and full account xpub under one lease.

`Overview → More wallet actions → Health check` and `Settings → Hardware signer identity & health` open the same public identity detail used by multisig signers. Groot requires the physical device and an explicit recent scan, then uses exact-path HWI `getkeypool` to obtain a single response containing the live fingerprint, requested BIP84 derivation, and full account xpub. Rust compares all fields with authoritative saved metadata, revalidates the selected wallet, and persists the result atomically. Overview and Settings mirror that native wallet-scoped result, which survives app restart; no result history is retained. The Settings row labels that state **Checked**, **Attention**, or **Not checked** and shows the locally formatted time of the latest attempt when one exists. A health result does not replace receive-address verification or an end-to-end signing test.
