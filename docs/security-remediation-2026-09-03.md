An AI-assisted read-only verification inspected exact commit `3fb1bff54d2d6969491968483b3a738406ce9bd0` against `ccca877a5a00128acea4f13f4a08a24cedd20a83`. One Playwright skeleton-loading assertion at `e2e/wallet-flows.spec.ts:316` failed once under suite contention and passed on an isolated rerun; the exact final candidate still requires a clean pinned-runtime acceptance run. This is supporting evidence, not the independent human reviewer conclusion or packaged-candidate evidence.

The follow-up found and corrected two present-day contract/presentation gaps: `hardware_not_approved` and `unsupported_wallet_policy` now remain typed across the frontend IPC contract, and active UI, preflight, security, flow, and certification copy no longer presents rejected KeepKey hardware as supported. Literal KeepKey/Digital BitBox rejection, optional/computed logging, stdout/stderr, renamed telemetry dependency, and cancellation-before-policy-evidence tests protect those boundaries.

A fresh read-only review of that follow-up caught two issues before commit: npm aliases and additional valid Cargo alias/table forms could bypass the telemetry-name tripwire, and dormant KeepKey-specific DTO, error, and PIN-command branches contradicted the rejection policy. The gate now inspects dependency names and specifications plus quoted Cargo aliases/tables; unsupported legacy devices fail closed before discovery caching and cannot enter the PIN flow.

Three dormant items remain mandatory in the separately reviewed mainnet-enablement diff:

1. `multisig_recover` and `multisig_recover_bsms` must require the same recent live-HWI admission as every other new mainnet hardware-backed profile.
2. A zero-external-recipient CPFP must prove wallet ownership of its child output rather than accepting script equality alone.
3. The configured Core endpoint must pass local-loopback validation before any genesis RPC, and exact mainnet genesis verification must still precede the first mainnet database open.

Mainnet remains disabled, so no test-only or alternate activation mechanism was introduced to exercise these dormant paths prematurely.

The isolated mainnet preparation branch subsequently closed the command-level
parts of all three items while preserving the disabled gate: both standard
multisig recovery formats now reconcile every cosigner with recent live-HWI
admission before profile creation; mainnet CPFP final validation requires a
descriptor-derived single wallet output; and the loopback-only, plain-HTTP backend
rule now runs before client construction or a genesis RPC.
The broader exact-genesis-before-database invariant remains open because initial
profile creation/recovery currently precedes per-wallet protected Core setup. Its
required pre-wallet, native-only admission flow is recorded in
[`mainnet-enablement-preparation-2026-09-03.md`](mainnet-enablement-preparation-2026-09-03.md).

## Compatibility and BIP impact

No registry, wallet database, proposal, backup, descriptor, node-settings, or secret-envelope schema changes. No migration is required. Previously valid same-network recovery templates remain valid; malformed wrong-network metadata now fails closed. Existing v2 envelopes keep the documented authenticated, atomic migration behavior.

BIP84/BIP48/BIP174 support is narrowed only at the future mainnet hardware-policy boundary: unlisted or ambiguously identified devices cannot inherit certification. Transaction construction and finalization now enforce the already documented recipient, frozen-coin, replacement, and CPFP constraints at an additional trusted boundary. There is no new BIP or network support.

The follow-up changes only stable error classification, unsupported-device presentation, release gates, and tests. They do not change wallet, registry, proposal, backup, descriptor, or secret-envelope formats and have no additional BIP impact.

## Residual risks and deferred architecture

The release owner accepted the review's limited-release Argon2id decision without a persisted-format migration. Copied profiles permit offline guessing; onboarding now explains that lockout cannot protect a stolen copy and recommends a unique long passphrase. Release-mode calibration and packaged unlock latency remain exact-candidate evidence. A versioned per-envelope KDF design is required before raising the cap, expanding custody scope, or considering general availability.

Other review-listed residuals remain explicit: same-user filesystem TOCTOU opportunities, encrypted crash-temporary files, the process-lock inode lifetime, trust in a user-controlled loopback Core's mempool report, renderer composition of public export bytes, deliberate OS screenshot capability, and the installed-app HWI verify-to-exec race. The manual-outpoint self-DoS and recovery pre-bound CPU issue were removed; SBOM ordering is now locale independent. None of these records enables mainnet.
