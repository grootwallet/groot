# Groot product specification

Status: canonical for the current prototype and first live integration build.

## Product

Groot is an onchain-only Bitcoin wallet and multisig coordinator. It prioritizes the smallest understandable flows for receiving, sending, reviewing activity, inspecting coins, and coordinating descriptor-based hardware signers. There are no cloud backups, Lightning, address books, or editable labels in the first release.

The distributed macOS application includes Groot's exact reviewed Bitcoin Core HWI dependency for USB hardware signers. A user does not install HWI, Homebrew, or a privileged helper separately. Groot verifies the bundled executable and containing signed app before use and fails closed rather than searching the host system.

## Settled decisions

- 24-word BIP39 mnemonic.
- BIP84 native SegWit receive/change descriptors.
- Descriptor-first Miniscript multisig using native-SegWit `wsh(sortedmulti())` in coordinator v1.
- Default coordinator policy is 2-of-3 with BIP48 test-network account origins.
- A Groot-generated software wallet uses one BIP39 wallet passphrase: it is required with the 24 recovery words and also unlocks/signs in Groot. Hardware-only and multisig wallets instead use a device-local app PIN that is never part of a signer seed or hardware passphrase.
- Explicit local verifier rejects an incorrect credential before wallet loading.
- Signet is the first remote integration network.
- Regtest creates deterministic high-volume histories in automated tests.
- Testnet4 is used for final public-network rehearsal before any mainnet work.
- Mainnet is not a supported selectable network. It requires ADR 0012, the threat model, physical hardware certification, reproducible release evidence, and the release checklist to be independently approved first.
- Core RPC endpoints are configurable. Regtest uses an explicit deterministic test fee policy; public-network builds request economy, standard, and priority estimates from the configured, authenticated, exact-chain-verified Core node. If Core has insufficient estimation data, presets remain unavailable and the user may enter a validated custom sat/vB rate. Remote Core requires non-redirecting direct HTTPS or an explicit numeric loopback Tor SOCKS5 proxy for a v3 `.onion` endpoint. RPC operations and responses are bounded; neither transport silently falls back to another endpoint, route, or fee. Connection tests retry a bounded transient transport failure, but wrong-chain and missing-permission results fail immediately. Repeated background-sync failures use bounded exponential backoff so an unavailable or long-recovering node is not probed every ten seconds indefinitely.

## Onboarding

The entry screen uses **Add wallet** as the umbrella for creating a Groot software wallet, connecting or importing an existing hardware wallet, and creating a multisig policy. **Recover software wallet** is a separate explicit action for the currently supported BIP39 recovery flow; public hardware-backup import remains under **Add wallet**.

### Create

1. Choose **Generate software wallet**. This is a single-key wallet whose seed is generated by Groot; it is distinct from the public-only external hardware-signer path.
2. Explain self-custody and backup responsibility.
3. Request exactly 256 bits from the native operating-system CSPRNG in trusted Rust code and map them directly to 24 BIP39 words. An unavailable or failed OS entropy source aborts creation with `entropy_unavailable`; there is no time-, browser-, user-input-, or user-space-PRNG fallback. Advanced users may optionally record at least 128 physical coin flips or 50 physical six-sided-die rolls. Rust validates and domain-separates that bounded transcript, then hashes it together with the independently requested OS entropy. Supplemental input never replaces the OS source and is cleared after the attempt. The entropy buffer and pending mnemonic session are zeroized, and neither crosses into the webview.
4. Before displaying any word during creation, show a separate native privacy gate that asks the user to confirm they are in a private place without people, cameras, or screen sharing. Only then display the words in a compact platform-native backup sheet attached to Groot and return no mnemonic through Tauri IPC. The grid reads vertically by column—1–8, 9–16, 17–24—with consistently aligned numbers and words.
5. After the user records the words, strongly encourage them to reconstruct all 24 in exact order from a shuffled pool. Tapping/clicking is mandatory when verifying; drag-and-drop is an additional desktop interaction. Duplicate word values remain independently selectable by position. A mismatch must retain the challenge and show a durable error. The user may choose **Verify later** without blocking wallet creation. Groot then persists a per-wallet **recovery backup not verified** state and keeps a compact Overview warning plus Settings CTA until verification succeeds.
6. User creates and confirms a **wallet passphrase** and must acknowledge that it is the BIP39 passphrase required with the 24 words and also the credential that unlocks/signs in Groot. It cannot be reset. The UI does not call this value an app PIN.
7. Derive BIP84 external/change descriptors and a separate credential verifier.
8. Atomically persist portable credential-encrypted secret material, public wallet state, and an isolated wallet profile. The encrypted profile does not depend on an operating-system Keychain or device key.

Deferred verification requires the wallet to be unlocked and requires fresh wallet-passphrase authentication. A user who already has the written backup may open the native shuffled-word challenge directly. A user who did not finish writing it down may instead pass through the native privacy gate, view the ordered words in the trusted backup sheet, and then continue into the same native proof. Rust decrypts the mnemonic only inside the trusted boundary, and neither path returns any word through IPC. Only a successful exact-order challenge atomically changes the persisted profile marker to verified. Cancellation, an incorrect passphrase, platform unavailability, merely viewing the words, or a mismatched order leaves it unverified. Recovered wallets count as verified because recovery itself requires supplying the complete ordered mnemonic; wallets created before this marker existed retain their formerly mandatory verified state during migration.

Software-wallet recovery collects the 24 words in a platform-native window owned by the trusted application boundary. The webview submits only the wallet name and wallet passphrase; no mnemonic string is retained in Svelte state or sent through Tauri IPC. A platform without certified native recovery entry fails closed instead of falling back to a web form.

## Multiple wallets

Wallets have immutable UUID identities, editable local display names, network and kind metadata, and isolated databases. Renaming an unlocked wallet changes only its registry profile; descriptors, signer identity, recovery data, and exported public backups remain unchanged. An external-signer wallet also has a separately editable local hardware-signer name used on signing and verification screens. Renaming that signer changes only its presentation label; the fingerprint, public keys, descriptors, and wallet identity remain unchanged. Creating or recovering a wallet selects it. Each wallet has an independent unlock session: switching away does not lock it, and returning before its idle deadline does not ask for the credential again. Deleting one wallet selects another remaining profile or returns to onboarding when none remain. Legacy fixed regtest directories migrate atomically with rollback.

When another unlocked wallet has a saved protected network setup, new software, hardware, and multisig wallets offer to reuse its Bitcoin Core connection and activity-sync method by default. The user may opt out. Groot rechecks the exact Core chain before copying, keeps wallet databases and scan state isolated, and re-encrypts any RPC password with the new wallet credential inside Rust; node credentials never enter the webview. A new multisig profile is not selected or exposed to automatic refresh until this protected copy attempt finishes. Copy failure still creates the wallet offline and surfaces one setup action. Existing wallets may perform the same explicit action in Settings. The result remains a per-wallet copy, so either wallet can later choose a different node or sync method without changing the other.

Desktop navigation lists wallet profiles directly instead of hiding them in a native select. The active profile is visually identified; choosing another profile immediately removes the previous wallet's balance, activity, coins, and addresses from presentation, then shows the target wallet's loading, unlock, empty, or populated state. A late sync result from the wallet being left must never update the newly selected wallet's routes.

A registered watch-only or multisig profile counts as an existing wallet even though it intentionally has no software-wallet secret file. Startup loads the registry and exposes the existing wallet selector; it must never route such a profile set to first-run onboarding.

An older Regtest-only watch-only or standard multisig profile whose database and registry identity remain intact but whose public metadata or app-PIN verifier is missing enters an explicit repair state instead of pretending the wallet is absent. Rust reconstructs public-only metadata from the exact BDK receive/change descriptors, checks the registered descriptor checksum, and round-trips the supported BIP84 or `wsh(sortedmulti())` policy before writing anything. If the verifier is missing, the UI states that the previous PIN cannot be checked and asks for the PIN that should protect the repaired local profile; history, labels, proposals, and descriptors remain in the existing database. This bounded convenience is unavailable on public networks, which fail closed and require public-backup recovery. A partial or conflicting profile never silently repairs.

“Wallet” is the top-level user concept. A wallet can use one software key, one external hardware key, a shared threshold policy, or a reviewed recovery/inheritance policy. “Vault” is not a separate account container. Every selected wallet exposes the same Overview, Activity, and Coins information architecture; multisig and recovery wallets additionally expose Policy for signing keys, backup, and spending-path controls. Multisig creation separates choosing the spending-policy family from naming and configuring the wallet; signer enrollment never shares the first decision screen.

An unfinished multisig setup is one resumable local draft. Groot atomically persists only public policy material and progress: wallet name, template, threshold, signer labels/fingerprints/account xpubs, current step, descriptor-backup acknowledgement, and descriptor-bound hardware-policy evidence. App PINs, hardware credentials, device paths, PIN challenges, and transient modal state are never persisted. Reaching the Signers step before adding the first signer is valid persisted progress. Signer insertion rejects a duplicate normalized fingerprint or account xpub immediately for every import transport; connected devices already present in the draft remain visible in USB discovery with a disabled **Already added** state. Removing an imported signer requires confirmation naming that signer; cancellation leaves the draft unchanged. On startup, the app shell shows a durable app-level unfinished-wallet notice with direct resume and confirmed discard actions. It remains stable above every locked-wallet screen; the locked shell keeps the notice generic, while unlocked screens may include the saved name, step, and signer count. Resuming does not require unlocking an unrelated existing wallet. Reopening creation restores the last valid step and re-derives the authoritative descriptor preview in Rust. The user may move backward or forward without losing imported signers, or explicitly discard the draft after confirmation; confirmed discard exits creation and returns to the selected wallet surface. Successful wallet creation clears it.

### Recover

1. Accept exactly 24 valid BIP39 words and the original wallet passphrase.
2. Restore descriptors and verify the expected wallet identity where local metadata exists.
3. Full scan from a configurable birthday with a bounded descriptor gap limit. Height `0` is the safest default. A later birthday is an explicit performance/privacy tradeoff and can omit older history. The scan runs outside the UI thread, reports persisted block progress, and can be cancelled between blocks. Cancellation or process interruption preserves already-committed wallet state and is presented as an explicit safe-to-retry terminal state; retry starts a fresh authoritative pass from the configured birthday.

### Unlock

Receive and Send are foreground-action routes. Entering either route cancels and pauses automatic sync before wallet data or metadata is read. Snapshot reads that may wait for serialized wallet access run off the native window thread, so navigation remains responsive while cancellation finishes.

Incorrect entry uses the credential term appropriate to the selected wallet without revealing verifier details. It does not reveal whether a guessed software-wallet passphrase maps to another BIP39 wallet. Rate limiting covers every credential-verification command, persists per wallet across restarts, and has a monotonic floor while the process remains open. Unlock state is isolated per wallet. One global, persisted inactivity preference applies to every wallet (default 5 minutes; supported values 1, 5, 15, 30, and 60 minutes), while each wallet keeps its own last-user-activity clock. Activity in one wallet never extends another wallet's session. Background sync and notification polling never extend a deadline. Automatic sync must not monopolize foreground wallet operations: opening Settings pauses it, and saving node configuration cancels an in-flight normal sync between bounded network requests before validating and persisting the replacement connection. Explicit lock, reset, and deletion revoke the affected wallet immediately without changing another wallet's session.

The locked screen names only the selected wallet in its central card. The persistent desktop wallet list remains available for profile switching, but wallet-scoped Overview, Activity, Coins, Policy, and Settings navigation is hidden until authentication. Saved descriptors, signer xpubs, transaction data, and node configuration cannot be read while locked. Only profile switching/creation, theme selection, and a privacy-preserving network status control remain available. The status control may show public fee policy while locked, but node connection details and credentials stay sealed until unlock; unsupported metrics are never invented. A wallet that has never saved a node configuration has no encrypted RPC credential and must still unlock normally. Once username/password node settings are saved, a missing encrypted RPC secret fails closed and requires explicit reconnection. The unlock card has no redundant Back or add-wallet action: adding or recovering another wallet starts from **Add wallet** in the persistent wallet list. The fresh-install chooser is inaccessible once at least one wallet exists unless that explicit add-wallet route is active. Existing-wallet setup can be closed from every step without completing or replacing the selected wallet. A software wallet labels its credential **Wallet passphrase** and explains that it belongs with the recovery words; multisig and external-hardware wallets label theirs **App PIN** and explain that it is local protection only. Every credential field has an explicit show/hide control.

Hardware and multisig profiles created before the current UUID-scoped public-metadata and encrypted-PIN-verifier format are unsupported disposable Regtest data. Groot identifies that incompatibility before credential entry, does not guess the missing metadata or reset the verifier, and leaves the profile files untouched until explicit deletion. Persisted-format compatibility changes require an approved ADR and migration-versus-discard decision before implementation.

The persistent wallet-list title includes the number of profiles. On unlock, the selected wallet name—not a generic greeting—is the primary heading. Settings puts **Lock now** first, describes backup/credential requirements without offering to reveal secrets, and clearly distinguishes selected-wallet actions from global preferences. The automatic-lock duration and appearance are global. Profile management and new-wallet policy choices remain in the persistent wallet list and its **Add wallet** flow.

Regtest builds expose a locked-screen deletion action for the selected disposable local wallet. It requires typing `RESET REGTEST`, works for single-key and multisig test profiles, and is not available on public networks.

## Overview

Show confirmed and total balance using the global sats/BTC preference; accounting stays in integer satoshis. The Overview total balance itself toggles that global preference on click, tap, Space, or Enter. Do not fetch or display fiat prices or market data. Explain mempool accounting rather than collapsing it into one ambiguous pending number: unconfirmed incoming outputs, wallet-controlled change, and outgoing amount plus fee are distinct labels. Show sync recency and the latest three transactions. Receive and Send are the primary actions. When the selected multisig or external-signer wallet has a persisted proposal that is still collecting signatures or is fully signed but not broadcast, show a compact status above those actions. It exposes only signature progress, distinguishes **Signing in progress** from **Payment ready to broadcast**, and resumes the exact proposal when opened.

A persisted global discreet mode hides wallet amounts across Overview and activity surfaces. It remains available as a quick desktop-shell control and from the balance card; it does not alter wallet accounting or transaction data.

## Receive

1. User requests a new address.
2. A non-empty label of at most 48 characters is mandatory.
3. Address revelation and immutable label persistence are atomic.
4. Multiple addresses may await payment concurrently, up to the configured recovery gap. Address revelation fails closed before it would create an index that a scan using that gap could miss; lowering the gap below the wallet's revealed receive/change requirement is rejected. The receive view lists every active payment request and lets the user inspect each address independently.
5. Creating a new address never retires another awaiting address.
6. Any awaiting address with no observed transaction may be discarded independently for privacy.
7. A discarded address is retired from presentation but monitored forever.
8. Any address with an observed transaction cannot be discarded.

## Send

Single-key and multisig payments use the same **Economy**, **Standard**, **Priority**, and **Custom** fee selector. Public-network presets come only from the connected Bitcoin Core node. When its current mempool is empty or fits comfortably within one block, the presets may correctly share the same current low rate instead of repeating stale high historical estimates. The UI names Bitcoin Core as the source without exposing RPC method names. The global **sats** or **BTC** display preference applies across balances, coins, activity, send flows, alerts, errors, and notifications. The `sats` unit is always lowercase and `BTC` is always uppercase. BTC always displays eight decimals; accounting and IPC remain integer satoshis.

1. A labeled three-stage progress indicator keeps every send flow consistent: **Intent**, **Amount & fee**, and **Review & sign**. Intent asks for the mandatory permanent payment label first, then a network-valid recipient address, so the user names the purpose before choosing how to fund it. Amount & fee contains the integer satoshi amount, coin selection, and fee rate. Rust stores the label with the proposal and resulting outgoing transaction; it is not editable or reused.
2. Choose economy, standard, priority, or validated custom sat/vB rate.
3. Use **Balanced** automatic coin selection by default, excluding frozen coins. **More private** prioritizes avoiding address reuse, unknown provenance, and new label/cluster merges; **Lower fee** prioritizes fewer, larger inputs. The user may instead select one or more unfrozen UTXOs exactly. Manual selection shows the funding labels and selected amount by default, while input weight stays in optional detail. If the chosen coins would link existing privacy groups and one group can fund the payment alone, Groot offers an explicit switch to **More private** automatic selection; it never rewrites the manual set silently. Review discloses the selected input count and warns before signing when the resulting funding set combines permanent labels, contains unknown provenance, or spends an address-reused coin. **Max** comes from a non-persisted native drain preview using the active fee rate and exact coin-selection policy; the webview never guesses the spendable amount.
4. Prepare a real unsigned transaction in Rust and return its authoritative review summary, including every input outpoint, authenticated input amount and sequence, network, locktime, RBF state, output count, and effective fee rate estimated from the descriptor's signed satisfaction weight.
5. Review the permanent label, recipient, amount, fee, total, and network by default. One **View more details** disclosure consistently contains fee rate, aggregate input value/count, output count, locktime/RBF state, change amount/address, and the exact PSBT key-origin derivation paths for wallet inputs and change. Exact outpoints and sequences remain bound to and validated from the persisted PSBT in Rust, but are not repeated in the general transaction review. Rust rejects missing, foreign, or duplicate inputs, impossible input/output totals, and any non-recipient output not controlled by the selected wallet. Long recipient and change addresses use `prefix…suffix`; activating one opens the complete grouped, copy-safe address view. On Regtest, a Ledger Bitcoin Test or Trezor review replaces the canonical `bcrt1` recipient/change presentation with a Rust-supplied `tb1` alias only when both encodings decode to the identical PSBT output script.
6. Enter the wallet-specific credential: **Wallet passphrase** for a software-key wallet, or **App PIN** for an external-hardware or multisig wallet. The software-wallet authorization form keeps the authoritative recipient, label, amount, network, fee, total, and optional transaction details visible beside the credential action. Every prepared software, external-hardware, or multisig payment remains visible through the same Overview resume surface after navigation or restart and reloads its exact persisted proposal. Canceling any prepared payment uses the same destructive confirmation, reviews the payment and collected-signature count, and only then marks the proposal canceled. After external signatures satisfy the wallet, hide now-irrelevant signing transports and repeat the signed transaction review before authorizing broadcast. A signed external-hardware or multisig signer row may discard that signer's signature from Groot's local proposal after an explicit warning and confirmation. This preserves the reviewed transaction and is not revocation: any exported or shared PSBT copy may still contain the signature. Rust verifies, signs or authorizes broadcast as appropriate, persists, and clears secrets.
7. Show a durable success state plus a transaction-broadcast toast that explicitly labels the updated figure as the **remaining wallet balance**, never as the payment amount.
8. A pending wallet-originated transaction may be accelerated through RBF when it signals replacement. An incoming or outgoing pending transaction may use CPFP when it has a spendable wallet-controlled output. Incoming transaction details never offer sender-side RBF merely because the transaction signals replaceability. Both paths create a new authoritative PSBT and return to the same review and signing flow. Preparing the same acceleration again after a route remount resumes its one active persisted proposal instead of creating duplicates; successful broadcast cancels any stale legacy drafts for that original transaction and method.
9. After a successful RBF broadcast, Activity retains the original transaction as **Replaced**, links it to the replacement transaction ID, and explicitly excludes it from accounting. A rejected or raced replacement never changes the original status. Acceleration success states name an RBF replacement or CPFP fee-only child explicitly; CPFP must never be described as a zero-satoshi payment.

The send surface includes a compact public signer summary throughout the flow. Software wallets identify Groot on the current device as the signer. External-hardware and multisig wallets show imported signer labels/models and shortened master fingerprints plus the required threshold; a signer is marked signed only from authoritative proposal data. Imported identity never implies that a device is currently connected or healthy.

After a PSBT, public-backup, or PDF backup file is saved on macOS, the success toast offers **Show in Finder**. The webview receives only a short-lived, single-use reveal token; the saved filesystem path remains inside the trusted Rust boundary.

Transaction history details use the same progressive-disclosure pattern as transaction review. Status, amount, label, date, confirmations, fee, and destination remain immediately visible. Rust derives actual signed-transaction input/output counts, wallet-side input/output amounts, fee rate, locktime, and RBF state for **View more details**, alongside transaction IDs, block/replacement identifiers, self-spend classification, and explorer controls. Metadata unavailable for a legacy synthetic replacement is omitted rather than inferred in the webview.

## Activity and transaction details

Search matches the transaction title, payment-intent label, and inherited provenance labels. Direction filters combine with deterministic latest/earliest and largest/smallest sorting without changing wallet state. Time sorting keeps active pending transactions above confirmed history for **Latest first** and below it for **Earliest first**, then orders each group by its timestamp; this prevents a miner-supplied block timestamp from placing a newly seen mempool payment below older confirmed activity.

List received/sent transactions with an authoritative typed classification, label, amount, date, and pending/confirmation state. A fee-only transaction whose value outputs all remain wallet-controlled is a **Self-spend**: its displayed wallet debit is the network fee and it has no counterparty address. Optional details show the transaction ID, block/replacement metadata, self-spend classification, and a network-correct explorer link on supported public test networks. Opening a third-party explorer carries a short privacy warning; local regtest transactions never receive a dead public-explorer link. Compact addresses always preserve both identifying ends as `prefix…suffix`; opening one replaces that compact value with the complete grouped, copy-safe view rather than displaying both at once.

An empty activity view explicitly says that the wallet has no transactions yet. Filtered empty states distinguish no received transactions from no sent transactions.

## UTXOs

Coins default to the newest source transaction first. A compact sort control allows newest/oldest, largest/smallest, and permanent label A–Z/Z–A. Date sorting leaves coins without a known source-transaction timestamp after dated coins. Sorting is presentation-only and never changes selection, freeze state, labels, or spend eligibility.

Show amount, every immutable provenance label as a compact tag, confirmations, and frozen state by default. An exact incoming output inherits only the permanent label assigned to its receive address. Change inherits the deduplicated known provenance-label union of every spent wallet input: co-spending labels A and B produces change carrying both A and B. It is explicitly **Mixed** or **Unknown** when a single source cannot be claimed; an outgoing payment-intent label remains separate and never becomes change provenance. Coin details expose the Rust-derived source transaction, source payment intent when one exists, and the count of wallet inputs in change lineage. Address and outpoint are optional technical details, compacted as `prefix…suffix` until the user opens the full detail view. Users can select UTXOs and begin a manual-input send for either single-key or multisig wallets. Freeze and unfreeze require a brief confirmation that names the affected coin or selection and explains the spending-selection effect without exposing an outpoint. Freeze/unfreeze is persisted; frozen coins are excluded from automatic and manual spending until unfrozen. When two or more spendable outputs share a known receive address, mark each affected coin with a calm address-reuse privacy notice without blocking spending. Technical linkage, affected addresses, outpoints, provenance labels, privacy clusters, and totals stay collapsed until the user requests the optional detail. Discreet and locked states never reveal permanent-label text or coin amounts, including accessibility names and filters.

An externally funded descriptor-derived multisig address that Groot never created as a receive request remains honestly **Unknown source**. If that address now controls an observed unspent external output and has never had local address metadata or a label assignment, Coins may offer one explicit initial-label action. Rust binds it to the exact current wallet output and derivation index, atomically creates the used address record and receive-origin label, and rematerializes provenance. It rejects change, spent/foreign/arbitrary outputs, an existing address record or label, and normalized label reuse. This is initial metadata recovery, not editable labels: the assigned label can never be changed. Hardware-policy verification addresses are labeled as verification references and tell users to create a labeled Receive request before funding.

## Notifications

Durable in-app notification events are produced for:

- local transaction broadcast, with updated balance;
- newly observed incoming transaction, with updated balance;
- first confirmation, with updated balance.

Later confirmations do not create events. Delivery is explicitly acknowledged and may repeat after a crash before acknowledgement; stable event IDs and persistent transaction state make handling idempotent. Persistent transaction state remains the source of truth.

The first successful sync of a newly created or recovered local profile establishes a notification baseline. Existing transaction history is restored silently instead of replaying old receipt and confirmation toasts; only changes observed after that baseline produce new events.

While the unlocked desktop app is running, one centralized foreground scheduler syncs the selected wallet every ten seconds and immediately when the app returns to the foreground. Sync commands never overlap: slow or offline nodes coalesce wake-ups instead of building a queue. If selection changes during an active sync, exactly one immediate follow-up sync runs for the newly selected wallet. Successful update events carry the immutable wallet ID, and routes accept them only while that ID remains selected. A successful sync updates visible balance, activity, coins, and receive-address status without navigation or a manual refresh. Offline polling remains quiet; explicit user-requested sync continues to show a durable error. Fully terminated background delivery is out of scope.

## Delete wallet

Require the selected wallet credential, explicit typed confirmation, and a backup warning. Close handles, zeroize/clear in-memory keys, remove encrypted secret material and local wallet database, and return to onboarding. Multisig settings opens a dedicated deletion page that links to wallet-backup export, quotes the exact-name prompt, and makes a successful recovery test for the exact current descriptor an explicit prerequisite rather than a hidden disabled-button condition. Deletion affects only this device and cannot recall broadcast transactions or guarantee physical flash erasure.

## Multisig coordinator

1. User names the wallet and chooses a recommended 2-of-3 or 3-of-5 recipe, or opens advanced M-of-N controls within the safe v1 envelope of 2–7 signatures and 3–7 signers. Groot does not offer 1-of-N because one stolen key could spend alone; users who want one key should create a single-key wallet.
2. Add each signer through a Rust hardware transport or import its master fingerprint and BIP48 account tpub through bounded mounted file/manual flows. Coldcard file import accepts its public **Export XPUB** JSON, including descriptor-style `p2wsh_desc` output, but rejects private material, mainnet xpubs, and noncanonical origins with an actionable re-export instruction. Air-gapped PSBT exchange supports bounded `crypto-psbt` UR v2 animation and camera scanning through Groot's bundled local decoder; text and file fallback remain available until every target platform is certified.
   Draft progress is neutral before review. Missing-field and policy errors appear only after the user attempts **Review wallet**. Imported-key cards identify the device fingerprint and connection/import method and make the complete public account key readable without horizontal overflow.
3. Reject duplicate fingerprints, duplicate account xpubs, wrong-network keys, private descriptors, and nonstandard origins.
4. Rust constructs canonical checksummed external/change `wsh(sortedmulti())` descriptors and BDK derives the verification address. Interchange presents the standard multipath `/<0;1>/*` form when the two branches are provably identical apart from branch number; separate receive and change descriptors remain available as optional detail and remain BDK's internal representation.
5. User verifies connected devices where supported and confirms an offline descriptor backup before the wallet can receive funds. Receive addresses remain visibly **not verified on hardware** until a capable saved signer returns the exact descriptor-derived output. Rust then appends an address-specific event containing the verified time, signer fingerprint, device type, and returned public address; only the latest timestamp and fingerprint cross into the UI. A successful result never implies permanent firmware/device trust and **Verify again** appends a new event rather than replacing history. Coldcard signers receive a BIP-380 descriptor export and explicit on-device name, threshold, and fingerprint acknowledgement. Ledger, BitBox02 including Nova, and Jade receive an interactive policy-and-first-address verification task. All device-policy setup is optional during watch-only coordinator creation but must be explicitly deferred; every unfinished signer remains **Setup required**, and first signing opens its device-specific preparation before any transaction request. Before an interactive request begins, Groot shows the Rust-derived first address in the same readable format used by address review and lets every fingerprint, derivation path, and account xpub open in the standard large identifier view. Interactive evidence is descriptor- and fingerprint-bound and append-only. Coldcard's durable file-import acknowledgement uses a distinct scope and is never presented as address proof. Trezor One and Safe 3 have no persistent registration state, so they are marked **No setup needed**, not registered. BitBox02 Nova's pinned-HWI desktop USB path has exact-model local Regtest core and independent clean-profile recovery evidence, with a documented shared-pairing-cache limitation; no original BitBox02 result is inherited, and Testnet4, packaged-candidate, independent-review, and Whisper/Bluetooth rows remain separate. See [`hardware-policy-readiness.md`](hardware-policy-readiness.md).
   Selecting a signer during setup or from a saved wallet reveals its public fingerprint, BIP48 account path, import source, public account key, connection capability, and latest persisted health-check result. The signer’s local display name is editable from this shared detail surface, including filename-derived labels; renaming persists locally but cannot modify signer identity, descriptors, verification evidence, or the hardware wallet. A health check always requires the physical signer, even when its public key was imported by QR, file, or manual entry. One explicit aggregate discovery supplies an opaque, short-lived path hint. Under one exclusive native lease, Groot opens that path, obtains a fresh BIP48 account key with HWI `getkeypool`, and requires the live type, fingerprint, derivation, and complete account xpub to match the saved identity before Rust persists the result. The renderer cannot submit a health record. Groot keeps only the latest result and timestamp per signer fingerprint; no health-check history is retained. Initial public-key import uses the same exact-path keypool proof before any identity has been saved. A format-only public-record check is not a health check and must not be offered as one. Before USB scanning, Groot states that a signer must already be initialized with a seed and offline backup and that vendor companion apps must be fully quit before Groot can own the USB session. Most devices must also be unlocked and ready in their vendor-specific Bitcoin mode; a locked Trezor Model One instead exposes Groot's PIN-position flow. When HWI reports PIN and passphrase requirements together, PIN unlock always precedes standard/hidden wallet selection and fingerprint import in both multisig and external single-key setup. A standard Trezor wallet remains valid if passphrase support is enabled later; the resulting hidden wallet is a separate identity that must be added as a separate Groot wallet. An already-paired BitBox02-family device unlocks directly through Groot after scanning; BitBoxApp is used only when Groot explicitly reports that one-time pairing is required, and must then be quit before Groot takes the USB session. Ledger import visibly waits for on-device public-key export approval. Concise Coldcard, BitBox02, Ledger, Trezor, and Jade preparation help is available without exposing advanced descriptor details.
6. Send uses the same labeled **Intent → Amount & fee → Review & sign** stages as single-key wallets and presents the wallet threshold, signer labels/models, and shortened public fingerprints before proposal creation. It then creates and persists an authoritative PSBT. Partial signatures may arrive in any order over hardware, bounded `crypto-psbt` UR v2 QR, or file. A signed row may discard that signer's signature from Groot's local proposal after a warning and confirmation; this is not revocation, and the UI states that previously exported or shared PSBT copies may still contain the signature. PSBT export uses a native save dialog, validates the payload before writing, and suggests a short ASCII `groot-xxxxxxxx.psbt` filename suitable for hardware-wallet removable-media flows. Canceling a proposal requires a destructive confirmation that reviews the payment and states how many collected signatures will be discarded; the initial cancel action never deletes directly. Leaving the signing page also requires confirmation and explicitly preserves the proposal and collected signatures for resumption.
7. Rust validates every imported ECDSA partial signature against the actual PSBT input sighash and signer public key before it can count, merge, persist, or appear in progress. Matching valid PSBTs merge without changing any reviewed non-signature field, and broadcast remains unavailable until the descriptor is satisfied and the transaction is finalized. Hardware discovery can be refreshed without closing the modal; identity and signing failures stay visible inside that modal with a recovery action. A terminal hardware-signing result closes any address-detail overlay opened from that modal so the durable parent success or error state cannot remain hidden. A connected Ledger, BitBox02, or Jade without saved policy evidence cannot jump directly to transaction signing: Groot first shows the expected threshold and every full fingerprint, BIP48 origin, and public account key, then verifies the device-returned first address. Ledger may repeat its wallet-policy approval during the later signing request because the current HWI boundary does not preserve Ledger's host-side wallet HMAC between CLI calls.
8. Hardware-only wallets use an app PIN verifier but have no coordinator-held mnemonic or private key.
9. Setup offers visual standard, delayed-recovery, and inheritance templates on a dedicated policy-choice screen, followed by a separate wallet-name and policy-configuration screen. Standard means the selected threshold is always required. A standard 2-of-3 can be assigned assisted-signing roles: two independent owner keys and one trusted-helper key let either owner sign with the helper or both owners sign together, while the helper can never spend alone. This is guidance for the standard descriptor, not a distinct persisted policy type. Recovery and inheritance use the same four-independent-key structure—an immediate 2-of-3 primary branch plus one delayed key—but present different intent and delay: a shorter emergency fallback versus a longer planned handoff. Approximate time is always secondary to the exact block delay. Descriptor logic is hidden by default but available before creation. Recovery/inheritance templates compile and persist real Miniscript descriptors in Rust; coordinator-assisted spending through a matured delayed branch remains a V2 release gate.
   Guided delayed-recovery templates require four independent keys: three primary keys form the immediate 2-of-3 branch and a fourth recovery-only key is excluded from that branch. Reusing any primary signer as the sole delayed recovery key is rejected in both UI policy construction and Rust validation. The delayed key is an independent single-key spending branch, not a co-signer: after an individual received output has aged through its relative block delay, that key can spend the matured output without either normal 2-of-3 signature. Every newly received output starts its own delay. Setup states this consequence visibly and offers optional plain-language detail for Recovery and Inheritance.
   Funded delayed-policy operation is deferred until the Testnet4 hardware-signing targets are certified. Before that phase can ship, Groot must track every output's exact remaining blocks and projected time, distinguish immature, approaching-maturity, and mature states across Overview, Coins, and Policy, and notify the user early enough to review or move funds with the immediate 2-of-3 path. Copy must say that the delayed branch **matures**, not that a coin expires: maturity leaves the 2-of-3 path valid while adding the independent single-key path and therefore changing the coin's security model. Countdown and notification state must derive from the authoritative chain tip, remain correct across restart and reorg, avoid duplicate alerts, and never imply that an approximate date overrides the exact relative block delay. This UX and its funded Testnet4/reorg/recovery tests begin only after the physical hardware campaign is complete.

Every explicit USB discovery request invokes HWI `enumerate` exactly once, because HWI 3.2.0 walks all backends even when a device type is supplied. Rust validates the aggregate response, rejects duplicate or conflicting non-empty paths, caches all valid devices behind opaque short-lived capabilities, and only then filters the result to eligible saved families and fingerprints. HWI's BitBox02 adapter can start the device-password interaction while opening clients inside that aggregate enumeration, before it can return a path-only row, so both aggregate discovery and subsequent account-key import use a bounded five-minute human-interaction window. A uniquely path-addressable locked BitBox02, Jade, or Ledger row remains actionable without another scan: selecting it redeems the opaque capability into one interactive operation, while Rust still requires a fresh full identity match before accepting any result. Multiple unresolved paths for the same family fail closed. Trezor retains its PIN flow and Coldcard remains prepare-then-rescan. Concurrent callers share one native discovery flight, and the explicit **Scan again** action remains available after empty, failed, and partial discovery results so the user can refresh without closing the modal.

After discovery returns a fingerprint that exactly matches a saved signer, wallet-scoped device lists show that signer's current user-defined name. The HWI factory/model label remains the fallback for locked, unmatched, and initial-import devices and is never used to infer identity.

Testnet4 hardware commands use HWI's explicit `testnet4` chain except for Jade. HWI 3.2.0's Jade adapter has no Testnet4 mapping and uses its `test` selector for Jade's shared test-network family, so Groot applies that selector only to exact-device Jade operations; wallet derivation and every saved-identity check remain Testnet4 authoritative. Cached paths are hints rather than identity. Disconnect, timeout, cancellation, wallet switch, or scan-generation change revokes them; the user must explicitly scan again after reconnect. Groot never retries discovery or an interactive device request automatically.

## Interoperable backups

Standard multisig wallets export and recover the public four-line BIP129/BSMS 1.0 descriptor record. Recovery also accepts bounded public descriptor text used by Groot and hardware-wallet workflows: a BIP-389 multipath descriptor, an explicit receive/change pair, or a checksummed standard `/0/*` receive descriptor whose `/1/*` change branch is reconstructed and validated. Imports are size bounded, public-only, descriptor parsed, network checked, and verified by deriving their first address; conflicting explicit and portable branches fail closed. Groot JSON remains the complete format for immutable labels and custom recovery-policy metadata. The wallet app PIN re-authorizes export from protected local coordinator state even when the wallet view is already open; every failed export attempt participates in the persisted per-wallet throttle. It does not encrypt the exported public file. The export cannot spend, but exposes address derivation and wallet activity, so the UI labels it private financial metadata. Users can copy descriptors or save BSMS, JSON, and a human-readable QR PDF through explicit native save dialogs. A canceled dialog is silent; a successful macOS save offers **Show in Finder** without exposing the selected path to the webview. Deletion requires a successful recovery test, exact wallet name, app PIN, and a final irreversible confirmation modal. BIP129 encrypted coordinator/signer rounds are not implemented.

## Out of scope

Mainnet, Lightning, arbitrary custom Miniscript editing, editable labels, contacts, cloud sync, background push while fully terminated, Payjoin sender/receiver sessions, and fiat purchase/sale. Delayed-branch coordinator spending, decaying multisig, expanding multisig, and BIP129 encrypted signer rounds remain later work described in `docs/roadmap.md`. Optional compact-filter/P2P sync is a confirmed-only test-network feature gated by ADR 0031; Payjoin V2 URI parsing is foundation only and sends no protocol traffic.

## Language and local preferences

- English, French, and Spanish are selected in the global **App appearance** section of Settings. The preference is stored locally, survives app relaunches, is applied before first paint, and is never synchronized over the network.
- On launch, Groot renders only a neutral branded startup surface until Rust confirms the selected wallet's session state. Wallet balances, activity, actions, and other authenticated routes must never appear—even briefly—before the selected wallet is confirmed unlocked. A locked or expired session routes to the wallet lock screen before authenticated content mounts.
- The shared localization boundary covers all frontend product copy, including routes, modals, loading and error states, toasts, accessibility names, recurring statuses, and grammatical count labels. English source copy is the stable catalog key; the localization quality gate rejects uncatalogued rendered English. Native errors are localized by stable category or a localized safe fallback without changing wallet contracts or trusted Rust behavior.
- Wallet names, permanent labels, addresses, descriptors, transaction data, and user-entered text remain byte-for-byte user or protocol data and are never translated.
- A wallet may be software single-key, external-signer single-key, or descriptor multisig. Each profile has isolated storage, app credential, descriptor identity, proposals, labels, and node configuration.
- External-signer wallets store public BIP84 descriptors only. Their Groot app PIN is distinct from any optional hardware-wallet seed passphrase.
- External-signer Overview exposes **Health check** in the wallet actions menu, and Settings exposes the same **Hardware signer identity & health** detail. Both entry points share the latest wallet-scoped result. Settings shows an honest **Checked**, **Attention**, or **Not checked** badge and, after an attempt, its locally formatted event time. An explicit aggregate scan supplies only an opaque path hint; under one exclusive lease the native health operation freshly reads and matches the device type, fingerprint, BIP84 derivation, and complete account xpub, revalidates the selected wallet, and atomically persists the result. The device path is never persisted, and the renderer cannot author a health result.
- An unlocked external-signer wallet can export its checksummed public receive descriptor only after fresh app-PIN authentication. The native, user-mediated save path produces an importable watch-only backup; the UI warns that it cannot spend but reveals the wallet's complete activity. Importing that descriptor must reconstruct the same receive and change descriptors without access to the hardware seed.
- USB, SD-card/file, manual descriptor, and QR-text public imports converge on the same Rust validation. Hardware passphrases must be selected on the device where supported. A Trezor may use a hidden passphrase wallet for one Groot profile and its seed-only standard wallet for another; selecting the standard wallet requires an explicit confirmation and binds the imported fingerprint to that signer.
- A directly connected signer matched to the wallet may return vendor-normalized transaction or public PSBT metadata. Groot never adopts those returned fields: it extracts only partial signatures and accepts them only when their public keys, fingerprints, SIGHASH_ALL types, and cryptographic verification match the untouched reviewed proposal. A signature made for changed inputs, outputs, amounts, sequences, prevouts, or locktime therefore fails closed. File, text, and QR imports additionally require explicit transaction and fee-source equality before signature validation.
- Multisig signing PSBTs include the authenticated policy's public account keys and origins so hardware wallets can reconstruct the BIP48 policy. Groot may add the same public metadata to an older active proposal only in the temporary device-signing copy; the persisted reviewed PSBT accepts only valid new signatures. A device response without its signature leaves the proposal unchanged and must not be described as an already-used signer unless that signer was already present on every input.
