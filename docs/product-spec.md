# Groot product specification

An unavailable RBF or CPFP quote is a fail-closed warning state. The send flow
shows an amber inline explanation separated from adjacent controls, repeats that
severity in its bounded toast, and disables **Continue to sign** until a fresh
valid quote exists. A zero-balance full-value spend cannot fund a higher RBF fee;
CPFP is available only when the wallet still controls an eligible unspent child
output. Neither path may present a transaction for signing after quote failure.

The single-hardware signing dialog keeps the selected signer and its actionable
state visible beside the authoritative transaction review on desktop, stacking
them on narrow screens. If a Coldcard CPFP fee exceeds the device's default
maximum-network-fee percentage, Groot explains the expected rejection before the
user selects the device. Groot must not suppress or bypass that signer safety
check; a deliberate device-setting change remains the owner's decision.

Every modal backdrop covers the complete usable window, including the translucent
desktop title-bar overlap, while preserving visible padding around the panel. The
panel is bounded by that padded viewport and its body owns vertical scrolling, so
collapsed and expanded transaction details never escape the backdrop.

When an acceleration's original transaction confirms, a saved proposal remains
visible for review but cannot be signed, exported for signing, or broadcast.
The sole proposal action is explicit discard through native cancellation; the
confirmed payment is untouched. Reopening must preserve this read-only state,
and discarding must not regenerate a payment draft. Without a saved proposal,
the confirmed-original notice may simply offer an Overview exit.

Status: canonical for public v0.4.96, including the approved macOS Mainnet scope.

The base wallet application is Apache-2.0 under ADR 0080. That license does not
cover the Groot marks beyond customary attribution and does not automatically
cover future hosted, family, business, enterprise, or separately self-hosted
services. The free wallet must remain independently recoverable and spendable
without any such service.

## Product

Receive discard confirmation shows every assigned label and the compact target
address, with **Show address details** revealing the full copyable address and
derivation. It always uses the discard target, not the currently featured request.
Receive signer selection lists all discovered families; unrelated identities
remain disabled. A fingerprint-less device from a family absent from the saved
wallet is also disabled without initiating unlock. When passive inventory and
every eligible saved signer both expose an exact model, a different model is
disabled as **Not part of this wallet** and the matching model says **Select to
identify**. Otherwise an eligible same-family device remains unknown until
Rust proves its exact account identity.
Matching signers omit technical membership prose and show **Policy unverified**
only when required saved policy evidence is absent.

Address-reuse notices count external outputs in BDK's canonical transaction
history, including receipts that have since been spent. Retained replaced or
evicted transaction versions are not additional payments. Two outputs to the
same receive address in one valid transaction still count as reuse. Normal
reconciliation corrects derived flags without deleting any historical records
or changing permanent labels.

BitBox policy verification uses the same freshly identity-bound reconnect path
as receive verification. A failed account proof never proceeds to device display;
no automatic approval retry or pairing-state reset is performed.

Receive leaves Overview navigation to the shell and keeps Refresh payments as its
header action. Standard BIP48 addresses are labelled **Native SegWit · standard
multisig**; only recovery-template wallets use the Miniscript label. After a Trezor
PIN succeeds, receive verification refreshes discovery and asks for explicit signer
selection rather than redeeming the stale pre-unlock record. The address stays unchanged.
Both send routes consume wallet-scoped sync updates during fee acceleration. A
confirmed original produces a durable completion notice and blocks further
acceleration preparation, hardware signing, and broadcast. Confirmation comes from
the configured node, not an external explorer. Existing proposals are not deleted.

Hardware pickers for an existing wallet distinguish connection readiness from
wallet membership. A non-matching discovered fingerprint is unavailable and
labelled **Not part of this wallet**. A missing fingerprint remains unknown unless
exact passive model evidence can rule it out or identify it as the only compatible
saved model; compatibility is presented as **Select to identify**, never as
proof of membership or readiness.
A matching fingerprint is only a candidate: native full account-key proof remains
mandatory before address display, policy verification, or signing. Public backup
recovery accepts importable text/BSMS/JSON, not the human-readable PDF export.
Reopening receive verification may show the address's saved prior verifier
fingerprint as historical evidence, but a new scan cannot label a connected
device **Ready** from that evidence. Live identity is proved again on selection.

Groot is an onchain-only Bitcoin wallet and multisig coordinator. It prioritizes the smallest understandable flows for receiving, sending, reviewing activity, inspecting coins, and coordinating descriptor-based hardware signers. There are no cloud backups, Lightning, address books, or editable labels in the first release.

Groot keeps local sanitized **App logs** for materially useful lifecycle and
wallet-operation outcomes. Its normal entry is a standalone Settings section
immediately before wallet deletion; the standard unlocked navigation remains visible
while viewing it. Users can search safe context, combine event-type and outcome filters, order by
date, inspect and explicitly copy the exact sanitized JSON records in-app, or export
deterministic JSON or CSV. The log never
contains credentials, recovery material, descriptors, keys,
RPC authentication or endpoints, PSBT/raw transaction data, full wallet/onchain
identifiers, device identifiers, wallet names, labels, or amounts. The log is not an
authoritative wallet ledger and automatic polling ticks are not recorded. Events
cover durable user-visible state transitions plus bounded operation start,
coarse-progress, and terminal outcomes when failure diagnosis matters. Passive
reads, form edits, and identifiers are excluded. Receive generation records only
the permanent-label count, never its text; successful eligible-address discard is
recorded as a distinct event. Failed records include a stable allowlisted explanation
and operation-specific scalar details when available; arbitrary backend, RPC, signer,
or user-authored error strings are never persisted. A pruned recovery-scan failure
identifies the requested birthday, required anchor, earliest full block retained by
Bitcoin Core, and earliest usable birthday. The recovery form shows the same facts in
the standard durable inline error treatment. Before submission, the recovery form
also shows the live node's earliest retained full block and explains that the
birthday must follow it. Unavailable retention information is explicit, never
inferred from a cached chain tip. Checkpoint agreement uses active-chain hashes,
not old full-block bodies; the requested scan range still requires retained blocks.

The distributed macOS application includes Groot's exact reviewed Bitcoin Core HWI dependency for USB hardware signers. A user does not install HWI, Homebrew, or a privileged helper separately. Groot verifies the bundled executable and containing signed app before use and fails closed rather than searching the host system.

## Settled decisions

- 24-word BIP39 mnemonic.
- BIP84 native SegWit receive/change descriptors.
- Descriptor-first Miniscript multisig using native-SegWit `wsh(sortedmulti())` in coordinator v1.
- Default coordinator policy is 2-of-3 with BIP48 test-network account origins.
- A Groot-generated software wallet uses one BIP39 wallet passphrase: it is required with the 24 recovery words and also unlocks/signs in Groot. Hardware-only and multisig wallets instead use a device-local app PIN that is never part of a signer seed or hardware passphrase.
- Explicit local verifier rejects an incorrect credential before wallet loading.
- Signet is the first remote integration network.
- Regtest creates deterministic high-volume histories in automated tests.
- Testnet4 is used for final public-network rehearsal before any mainnet work.
- The intended macOS GA app lets a user choose Regtest, Testnet4, or Mainnet in Settings under ADR 0069. Global Settings remains reachable from first-run onboarding when the selected network has no wallets, and the active Bitcoin network, build identity, and cached public network status remain available while a selected wallet is locked; wallet-specific node configuration, sync configuration, credentials, and actions remain unavailable until unlock. The change is confirmation- and restart-bound, and every network owns a separate wallet/node-data namespace. Fixed network builds remain available for rehearsal and supporting evidence, but are not the intended GA artifact. Mainnet public distribution still requires ADR 0012, the threat model, physical hardware certification, multi-network isolation/restart evidence, reproducible release evidence, and the release checklist to be independently approved first.
- Core RPC endpoints are configurable. Regtest uses an explicit deterministic test fee policy; public-network builds request economy, standard, and priority estimates from the configured, authenticated, exact-chain-verified Core node. A Mainnet profile without saved node settings asks the fixed Groot gateway for a unique revocable principal inside native Rust, verifies that exact node, and encrypts the one-time password under the wallet credential without exposing it to the webview. Existing local, custom remote, Tor, or managed settings are never replaced. Enrollment failure leaves the wallet explicitly offline; it never selects an alternate node or fee source. If Core has insufficient estimation data, presets remain unavailable and the user may enter a validated custom sat/vB rate. Remote Core requires non-redirecting direct HTTPS or an explicit numeric loopback Tor SOCKS5 proxy for a v3 `.onion` endpoint. RPC operations and responses are bounded; neither transport silently falls back to another endpoint, route, or fee. A custom trusted remote Core uses its synced basic block-filter index through bounded `scanblocks`. The fixed managed service instead uses a private Fulcrum script-history index behind the same authenticated gateway, requires exact Core/index tip agreement, and verifies every claimed transaction against its full active-chain Core block. Local Core retains the complete full-block path. Connection tests retry a bounded transient transport failure, but wrong-chain and missing-permission results fail immediately. The foreground scheduler starts the next attempt on the normal 35-second cadence after every completed attempt, including a failure; it never creates overlapping requests or an unbounded queue.
- Mainnet node Settings separate **Groot managed**, **This Mac**, and **Custom remote**. The managed view never renders the generated RPC principal or password. An authenticated explicit **Renew managed access** action obtains and protects a new principal after revocation or when returning from a user-controlled node; it never runs as a fallback. An explicit unlock wakes sync immediately on every destination route, including Settings, and a never-synced wallet starts its saved safe first-history scan without depending on Overview being mounted.
- Mainnet transaction policy is enforced from the final authoritative PSBT:
  fees may not exceed 100,000 satoshis and recipient amount plus fee may not
  exceed 1,000,000 satoshis. The same limits apply to ordinary sends, RBF, and
  CPFP. Sparse fee estimates are capped rather than extrapolated without bound.

## Onboarding

The entry screen uses **Add wallet** as the umbrella for creating a Groot software wallet, connecting or importing an existing hardware signer, and creating a multisig policy. **Recover software wallet** is a separate explicit action for the currently supported BIP39 recovery flow; public hardware-signer backup import remains under **Add wallet**.

### Create

1. Choose **Generate software wallet**. This is a single-key wallet whose seed is generated by Groot; it is distinct from the public-only external hardware-signer path.
2. Explain self-custody and backup responsibility.
3. Request exactly 256 bits from the native operating-system CSPRNG in trusted Rust code and map them directly to 24 BIP39 words. An unavailable or failed OS entropy source aborts creation with `entropy_unavailable`; there is no time-, browser-, user-input-, or user-space-PRNG fallback. Advanced users may optionally record at least 128 physical coin flips or 50 physical six-sided-die rolls. Rust validates and domain-separates that bounded transcript, then hashes it together with the independently requested OS entropy. Supplemental input never replaces the OS source and is cleared after the attempt. The entropy buffer and pending mnemonic session are zeroized, and neither crosses into the webview.
4. Before displaying any word during creation, show a separate native privacy gate that asks the user to confirm they are in a private place without people, cameras, or screen sharing. Only then display the words in a compact platform-native backup sheet attached to Groot and return no mnemonic through Tauri IPC. The grid reads vertically by column—1–8, 9–16, 17–24—with consistently aligned numbers and words.
5. After the user records the words, strongly encourage them to reconstruct all 24 in exact order from a shuffled pool. Tapping/clicking is mandatory when verifying; drag-and-drop is an additional desktop interaction. Duplicate word values remain independently selectable by position. A mismatch must retain the challenge and show a durable error. The user may choose **Verify later** without blocking wallet creation. Groot then persists a per-wallet **recovery backup not verified** state and keeps a compact Overview warning plus Settings CTA until verification succeeds.
6. User creates and confirms a **wallet passphrase** of at least 16 Unicode characters and must acknowledge that the exact passphrase belongs with the 24 words, cannot be reset, and that a different value opens a different wallet. The same credential unlocks/signs in Groot. Keep this as one compact acknowledgement and do not repeat deferred-backup status on this step; Overview and Settings carry that persistent reminder. Letters-only passphrases are valid; Groot does not require digits, symbols, or mixed case. The UI does not call this value an app PIN. The minimum applies only to new-wallet creation: recovery, unlock, signing, and backup verification continue accepting the exact historical non-empty passphrase because changing a BIP39 passphrase selects a different wallet.
7. Derive BIP84 external/change descriptors and a separate credential verifier.
8. Atomically persist portable credential-encrypted secret material, public wallet state, and an isolated wallet profile. The encrypted profile does not depend on an operating-system Keychain or device key.
9. After successful creation, show the eight-character BIP32 master fingerprint derived in trusted Rust from the 24 words and exact wallet passphrase. Ask the user to record it with the recovery backup before opening the wallet, and provide an explicit copy control. A small accessible insight control beside the fingerprint label optionally explains what the identifier is, how to compare it after recovery, and that it cannot restore the wallet or spend bitcoin. The fingerprint is public identity metadata, not a replacement for the recovery words or passphrase; matching it during a later restoration confirms that both inputs selected the same wallet. Offer the checksummed BIP389 receive/change multipath descriptor and its privacy explanation behind the standard **View more details** disclosure so technical recovery control remains available without competing with the primary fingerprint instruction. State that it cannot spend but reveals every address in the wallet.

Deferred verification requires the wallet to be unlocked and requires fresh wallet-passphrase authentication. A user who already has the written backup may open the native shuffled-word challenge directly. A user who did not finish writing it down may instead pass through the native privacy gate, view the ordered words in the trusted backup sheet, and then continue into the same native proof. Rust decrypts the mnemonic only inside the trusted boundary, and neither path returns any word through IPC. Only a successful exact-order challenge atomically changes the persisted profile marker to verified. Cancellation, an incorrect passphrase, platform unavailability, merely viewing the words, or a mismatched order leaves it unverified. Recovered wallets count as verified because recovery itself requires supplying the complete ordered mnemonic; wallets created before this marker existed retain their formerly mandatory verified state during migration.

Software-wallet recovery collects the 24 words in a platform-native window owned by the trusted application boundary. The webview submits only the wallet name and wallet passphrase; no mnemonic string is retained in Svelte state or sent through Tauri IPC. A platform without certified native recovery entry fails closed instead of falling back to a web form.

The native generation and recovery sheets warn against digital storage but do not attempt to override an explicit operating-system screenshot initiated by the user. Deliberate capture remains possible by product decision; it transfers responsibility for the resulting secret-bearing image to the user and host. Groot must never trigger that capture, copy words to the clipboard, persist an image, log the words, or expose them through the webview or through accessibility metadata beyond the visible native word controls.

## Multiple wallets

Wallets have immutable UUID identities, editable local display names, network and kind metadata, and isolated databases. Renaming an unlocked wallet changes only its registry profile; descriptors, signer identity, recovery data, and exported public backups remain unchanged. An external-signer wallet also has a separately editable local hardware-signer name used on signing and verification screens. Renaming that signer changes only its presentation label; the fingerprint, public keys, descriptors, and wallet identity remain unchanged. Creating or recovering a wallet selects it. Each wallet has an independent unlock session: switching away does not lock it, and returning before its idle deadline does not ask for the credential again. Deleting one wallet selects another remaining profile or returns to onboarding when none remain. Legacy fixed regtest directories migrate atomically with rollback.

The native app version and short source commit remain visible through one shared build-identity control in the desktop rail, shell-less welcome/setup/recovery flows, and Settings. Activating it copies only that public build string with explicit feedback; it never includes wallet, signer, node, transaction, or profile information.

Wallet uniqueness is the exact canonical public receive descriptor on the active Rust network. The eight-character descriptor checksum remains an integrity check only; checksum equality cannot establish wallet equality. Creation and recovery compare exact descriptors inside Rust against every authoritative profile representation. A true duplicate returns the existing immutable wallet ID so the shell can select that exact profile; a missing or stale match never falls back to the currently selected wallet.

When another unlocked wallet has a saved protected network setup, new software
and hardware wallets offer to reuse its Bitcoin Core connection and
activity-sync method by default. Multisig setup leaves network adoption to Settings
after creation, so a locked source cannot block the final backup/PIN step.
Listing availability does not require the currently selected wallet to be
unlocked and returns no node, peer, proxy, or authentication settings. Duplicate
multisig descriptors are rejected before copying a setup or creating candidate files.
Groot rechecks the exact Core chain before copying, keeps wallet databases and
scan state isolated, and re-encrypts any RPC password with the new wallet
credential inside Rust; node credentials never enter the webview. A new software
or multisig profile is not selected, shown as successfully created, or exposed
to automatic refresh until this protected copy attempt finishes. For multisig
creation through native callers explicitly requesting reuse, a source that locks,
expires, changes, or fails validation rolls back the candidate and preserves the draft instead of silently
publishing an offline wallet. Software and single-key hardware creation retain
their existing offline fallback on copy failure. Settings lists saved setups on
every active network, including Mainnet, without exposing their node details
or credentials, marks whether each source is ready, and directs the user to
unlock a source before adoption when needed. From an offline wallet, manual sync
and the durable Overview retry open that setup choice directly, falling back to
the existing Core configuration dialog when no reusable source exists. The
result remains a per-wallet copy, so either wallet can later choose a different
node or sync method without changing the other.

A newly created external-hardware profile saves full history (block `0`) as its
initial scan choice because a signer provides no authoritative birthday. When a
managed or copied Bitcoin Core connection is ready, leaving onboarding immediately
starts the existing resumable history scan and Overview attaches to its progress
without flashing a manual-choice warning. Groot never assumes that hardware imported
today was first used today. A user who knows the wallet birthday can deliberately
replace the saved full-history choice in Scan settings.

Desktop navigation lists wallet profiles directly instead of hiding them in a native select. The active profile is visually identified; choosing another profile immediately removes the previous wallet's balance, activity, coins, and addresses from presentation, then shows the target wallet's loading, unlock, empty, or populated state. A late sync result from the wallet being left must never update the newly selected wallet's routes.

A registered watch-only or multisig profile counts as an existing wallet even though it intentionally has no software-wallet secret file. Startup loads the registry and exposes the existing wallet selector; it must never route such a profile set to first-run onboarding.

An older Regtest-only watch-only or standard multisig profile whose database and registry identity remain intact but whose public metadata or app-PIN verifier is missing enters an explicit repair state instead of pretending the wallet is absent. Rust reconstructs public-only metadata from the exact BDK receive/change descriptors, checks the registered descriptor checksum, and round-trips the supported BIP84 or `wsh(sortedmulti())` policy before writing anything. If the verifier is missing, the UI states that the previous PIN cannot be checked and asks for the PIN that should protect the repaired local profile; history, labels, proposals, and descriptors remain in the existing database. This bounded convenience is unavailable on public networks, which fail closed and require public-backup recovery. A partial or conflicting profile never silently repairs.

“Wallet” is the top-level user concept. A wallet can use one software key, one external hardware key, a shared threshold policy, or a reviewed recovery/inheritance policy. “Vault” is not a separate account container. Every selected wallet exposes the same Overview, Activity, and Coins information architecture; multisig and recovery wallets additionally expose Policy for signing keys and public backup. Spending-path controls and the recovery-policy lab appear only when the selected wallet persists a Miniscript recovery template; a standard `wsh(sortedmulti())` wallet never implies that a delayed branch can be added after creation. Multisig creation separates choosing the spending-policy family from naming and configuring the wallet; signer enrollment never shares the first decision screen.

An unfinished multisig setup is one resumable local draft. Groot atomically persists only public policy material and progress: wallet name, template, threshold, signer labels/fingerprints/account xpubs, current step, descriptor-backup acknowledgement, and descriptor-bound hardware-policy evidence. App PINs, hardware credentials, device paths, PIN challenges, and transient modal state are never persisted. Reaching the Signers step before adding the first signer is valid persisted progress. Signer insertion rejects a duplicate normalized fingerprint or account xpub immediately for every import transport; connected devices already present in the draft remain visible in USB discovery with a disabled **Already added** state. Removing an imported signer requires confirmation naming that signer; cancellation leaves the draft unchanged. On startup, the app shell shows a durable app-level unfinished-wallet notice with direct resume and confirmed discard actions. It remains stable above every locked-wallet screen; the locked shell keeps the notice generic, while unlocked screens may include the saved name, step, and signer count. Resuming does not require unlocking an unrelated existing wallet. Reopening creation restores the last valid step and re-derives the authoritative descriptor preview in Rust. The user may move backward or forward without losing imported signers, or explicitly discard the draft after confirmation; confirmed discard exits creation and returns to the selected wallet surface. Successful wallet creation clears it.

### Recover

1. Accept exactly 24 valid BIP39 words and the original wallet passphrase.
2. Restore descriptors and verify the expected wallet identity where local metadata exists.
3. Before the first Bitcoin Core history scan, require an explicit start choice: current tip only for a wallet the user confirms has no earlier activity, a birthday block before the first possible payment, or full history from height `0`. Height `0` is safest. A later birthday is an explicit performance tradeoff and can omit older history; the standard gap limit is 20 and affects address discovery rather than the number of blocks scanned. The rescan modal shows the current selected-network chain tip, rejects a birthday above that tip, and keeps the gap limit behind an explained optional address-discovery control. The scan runs outside the UI thread and reports progress. Cancellation, unexpected failure, and process interruption discard that run's progress presentation, so reopening always presents a fresh authoritative scan from the saved birthday rather than a partial range. Before replay, Groot removes only later local-chain checkpoints, verifies the highest retained checkpoint against Core, and extends that exact connected chain to the requested birthday anchor. A user-requested earlier or later rescan therefore cannot disconnect the introduced BDK chain after a previous sparse scan.

An explicit Core rescan keeps the window responsive during authenticated birthday validation and pending-transaction reconciliation. The modal replaces any previous completed range with the new zero-progress range before native polling begins. Remote indexed scans divide long birthday/genesis ranges into bounded sequential `scanblocks` requests and publish authoritative progress after every completed range, preventing a full-history request from exceeding the HTTPS gateway window without returning to per-height RPC. Block progress is not a completed wallet snapshot: after reaching the target height, Groot identifies the remaining pending-transaction check and publishes refreshed balance/history only after it finishes. Cancel checks occur between remote RPC calls; a single in-flight request remains bounded by its configured timeout. Manual actions on another read-only route observe the same active refresh instead of reporting it as a failure or starting a duplicate. The last committed balance, activity, proposal, and coin state remain visible without ad-hoc loading copy. A first complete mempool pass in the running app establishes a wallet-scoped public transaction-id baseline; later ordinary refreshes inspect only transactions added since that baseline plus the wallet's own still-pending transactions, while removals still evict relevant pending state. Revealing another receive address invalidates the baseline, and an explicit full rescan always establishes it again from the complete mempool. This does not replace confirmed or unconfirmed activity with a silent partial result.

### Unlock

The app shell checks the native non-refreshing session deadline independently of background sync, so an expired selected wallet immediately routes to its locked screen even on Settings and Send routes where sync is paused. A credential-authorized recovery or first-history scan may continue using its already-created node client after the wallet UI locks; it holds no wallet credential and cannot sign. Re-unlock reattaches to its persisted progress instead of cancelling or restarting it. An active hardware transaction review may finish within its separately bounded device-review window; the shell applies any elapsed idle lock immediately after that review finishes without changing the proposal or its signatures.

Receive and Send are foreground-action routes, but entering them does not cancel an active wallet refresh. Snapshot and proposal reads that may wait for serialized wallet access run off the native window thread. An exclusive mutation explicitly pauses and drains the automatic scheduler before taking wallet state, while a manual refresh continues if the user navigates to another read-only route.

Incorrect entry uses the credential term appropriate to the selected wallet without revealing verifier details. It does not reveal whether a guessed software-wallet passphrase maps to another BIP39 wallet. Rate limiting covers every credential-verification command, persists per wallet across restarts, and has a monotonic floor while the process remains open. Unlock state is isolated per wallet. One global, persisted inactivity preference applies to every wallet (default 5 minutes; supported values 1, 5, 15, 30, and 60 minutes), while each wallet keeps its own last-user-activity clock. Activity in one wallet never extends another wallet's session. Background sync and notification polling never extend a deadline. A foreground hardware discovery, unlock, address/policy review, or signing operation counts as active use: inactivity expiry is suspended only for that bounded native operation and its deadline restarts when the operation settles. Explicit lock or wallet replacement still revokes the session immediately. Automatic sync must not monopolize foreground wallet operations: opening Settings pauses it, and saving node configuration cancels an in-flight normal sync between bounded network requests before validating and persisting the replacement connection. Explicit lock, reset, and deletion revoke the affected wallet immediately without changing another wallet's session.

The locked screen names only the selected wallet in its central card. The persistent desktop wallet list remains available for profile switching, but wallet-scoped Overview, Activity, Coins, Policy, and Settings navigation is hidden until authentication. Saved descriptors, signer xpubs, and transaction data cannot be read while locked. Only profile switching/creation, theme selection, and a privacy-preserving network status control remain available. The status control shows the selected wallet's saved non-secret backend type, transport mode, and activity-sync method plus its last successfully verified public priority fee and network tip while locked; node credentials stay sealed, and fresh authenticated checks require unlock. Missing or invalid observations remain unavailable and are never invented. A wallet that has never saved a node configuration has no encrypted RPC credential and must still unlock normally. Once username/password node settings are saved, a missing encrypted RPC secret fails closed and requires explicit reconnection. The unlock card has no redundant Back or add-wallet action: adding or recovering another wallet starts from **Add wallet** in the persistent wallet list. The fresh-install chooser is inaccessible once at least one wallet exists unless that explicit add-wallet route is active. Existing-wallet setup can be closed from every step without completing or replacing the selected wallet. A software wallet labels its credential **Wallet passphrase** and explains that it belongs with the recovery words; multisig and external-hardware wallets label theirs **App PIN** and explain that it is local protection only. Every credential field has an explicit show/hide control.

Mainnet does not add RPC fields to the locked screen. The existing authentication
throttle is checked through a Rust-only, throttle-table database path; it does not
read wallet state. After PIN-only wallet authentication, Rust decrypts the selected
wallet's saved Core setup and Overview authenticates that exact admitted loopback
HTTP or direct HTTPS node and
Bitcoin genesis before the first wallet-data database read of the session. An
unavailable or invalid node remains an Overview connection failure with retry and
Settings recovery; the encrypted password never returns to the renderer.

Hardware and multisig profiles created before the current UUID-scoped public-metadata and encrypted-PIN-verifier format are unsupported disposable Regtest data. Groot identifies that incompatibility before credential entry, does not guess the missing metadata or reset the verifier, and leaves the profile files untouched until explicit deletion. Persisted-format compatibility changes require an approved ADR and migration-versus-discard decision before implementation.

The persistent wallet-list title includes the number of profiles. On unlock, the selected wallet name—not a generic greeting—is the primary heading. Settings puts **Lock now** first, describes backup/credential requirements without offering to reveal secrets, and clearly distinguishes selected-wallet actions from global preferences. The automatic-lock duration and appearance are global. Profile management and new-wallet policy choices remain in the persistent wallet list and its **Add wallet** flow.

Regtest builds expose a locked-screen deletion action for the selected disposable local wallet. It requires typing `RESET REGTEST`, works for single-key and multisig test profiles, and is not available on public networks.

## Overview

The first authenticated Overview read returns balance, complete pending-debit
accounting, current coin-policy state, and only the three most recent transactions.
Receive-address history and label suggestions are not fetched for this view.
Draft/proposal, saved signer, and health details load independently after that
read; failure leaves the balance visible with a durable details retry. Native
session and exact-wallet mainnet Core admission remain mandatory. The startup
gate ends when trusted session routing resolves, without an artificial delay.

Activity loads 50 transactions at a time through a native cursor endpoint (at
most 100 per request). Search and direction/date/amount ordering apply to the
complete history before paging. A changed history, query, wallet, or unlock
session invalidates the cursor and requires refreshing the list. Page failures
retain already displayed rows and offer retry. Equal sort values use transaction
identity as a stable tie-breaker; missing observation times remain unknown.
Pagination is a presentation boundary, never a limit on native accounting,
recovery monitoring, coin selection, or transaction review.

Show confirmed and total balance using the global sats/BTC preference; accounting stays in integer satoshis. The Overview total balance and both Coins summary totals toggle that global preference on click, tap, Space, or Enter. Do not fetch or display fiat prices or market data. Explain mempool accounting rather than collapsing it into one ambiguous pending number: unconfirmed incoming outputs, wallet-controlled change, and outgoing amount plus fee are distinct labels. A Rust-classified self-spend already reports its fee as the complete wallet debit, so pending accounting counts that debit exactly once instead of adding the same fee again. Show sync recency and the latest three transactions. Receive and Send are the primary actions. When the selected multisig or external-signer wallet has a persisted proposal that is still collecting signatures or is fully signed but not broadcast, show a compact status above those actions. It exposes only signature progress, distinguishes **Signing in progress** from **Payment ready to broadcast**, and resumes the exact proposal when opened.

A persisted global discreet mode hides wallet amounts across Overview and activity surfaces. It remains available as a quick desktop-shell control and from the balance card; it does not alter wallet accounting or transaction data.

If the saved Core endpoint is unreachable on unlock, Mainnet wallet-data reads
remain admission-gated. Overview must identify the node outage, stop its loading
skeleton, and offer a direct retry of the saved connection. It must not label the
wallet “Never synced” merely because this session could not load its persisted
snapshot. The connection check uses one five-second network attempt and must
not hold the renderer thread. For remote Core activity sync it also verifies the
two indexed-sync methods before reporting **Connected**. No failed network check
may erase or replace committed history.

## Receive

1. User requests a new address.
2. One to twelve distinct non-empty labels of at most 48 characters each are mandatory.
3. Address revelation and every immutable label assignment are atomic.
4. Multiple addresses may await payment concurrently, up to the configured recovery gap. Address revelation fails closed before it would create an index that a scan using that gap could miss; lowering the gap below the wallet's revealed receive/change requirement is rejected. The receive view lists every active payment request and lets the user inspect each address independently.
5. Creating a new address never retires another awaiting address.
6. Any awaiting address with no observed transaction may be discarded independently for privacy.
7. A discarded address is retired from presentation but monitored forever.
8. Any address with an observed transaction cannot be discarded.
9. The unlocked wallet suggests its most recently assigned labels without preselecting one. Choosing
   a suggestion adds a removable token inside the field and removes it from the available list; typing previously
   used normalized text intentionally reuses that stable label entity. Submitted address assignments
   are permanent and atomic; reuse expresses a relationship and does not imply that separate addresses
   are already linked onchain.
10. Receive provides one explicit manual refresh. It runs the selected wallet's existing sync operation, keeps the automatic scheduler paused on this foreground-action route, and replaces the address list from the returned authoritative snapshot so a newly observed mempool payment appears without navigating to Overview.

## Send

Single-key and multisig payments use the same **Economy**, **Standard**, **Priority**, and **Custom** fee selector. Public-network presets come only from the connected Bitcoin Core node. When its current mempool is empty or fits comfortably within one block, the presets may correctly share the same current low rate instead of repeating stale high historical estimates. The UI names Bitcoin Core as the source without exposing RPC method names. The global **sats** or **BTC** display preference applies across balances, coins, activity, send flows, alerts, errors, and notifications. The `sats` unit is always lowercase and `BTC` is always uppercase. BTC always displays eight decimals; accounting and IPC remain integer satoshis.

1. A labeled three-stage progress indicator keeps every send flow consistent: **Intent**, **Amount & fee**, and **Review & sign**. Intent asks for one to five mandatory permanent payment labels first, then a network-valid recipient address, so the user names the purpose before choosing how to fund it. The address field can scan a static QR containing either a plain address or a bounded BIP21 payment URI. Rust parses the exact payload without changing address case, rejects malformed, wrong-network, unknown-required, and unsupported Payjoin requests, and returns the canonical address plus optional integer-satoshi amount, label, and message. Payment destinations are limited to P2PKH, P2SH (including nested SegWit), SegWit v0 P2WPKH/P2WSH, and SegWit v1 P2TR; P2A and witness v2-v16 are rejected. Taproot remains send-only. The renderer prefills the amount and, when the user has not already chosen a permanent label, uses the URI message or label as an editable suggestion; every imported value remains visible for review before transaction preparation. Existing and provenance-derived records may display more than five labels after consolidation or other wallet activity. The selected unlocked wallet suggests at most four recently used labels without prefilling one; typing filters its complete label history and ranks exact normalized matches first without resizing the flow when nothing matches. Choosing a suggestion adds a removable token inside the field and removes that label from the available list. Enter, Tab, comma, and semicolon commit typed text as a token; empty-input Backspace selects the final token before a second press removes it. Choosing or typing matching normalized text intentionally groups the payment with that label entity; every submitted proposal assignment remains immutable. Amount & fee contains the integer satoshi amount, coin selection, and fee rate. Separate onchain clusters remain separate until a transaction links them, and review continues to report that public link honestly.
2. Choose economy, standard, priority, or a validated custom sat/vB rate greater than zero and no more than 10,000. Custom rates may be decimal and below 1 sat/vB; Rust preserves the requested decimal text and rounds upward only to Bitcoin's 0.004 sat/vB sat/kwu precision. The authoritative review reports the transaction's resulting effective rate, which may be slightly higher because the final fee is a whole number of satoshis. A node may still reject a rate below its current relay or mempool minimum; Groot surfaces that rejection instead of silently raising the user's choice.
3. Use **Balanced** automatic coin selection by default, excluding frozen coins. **More private** prioritizes avoiding address reuse, unknown provenance, and new label/cluster merges; **Lower fee** prioritizes fewer, larger inputs. The user may instead select one or more unfrozen UTXOs exactly. Manual selection shows the funding labels and selected amount by default, while input weight stays in optional detail. If the chosen coins would link existing privacy groups and one group can fund the payment alone, Groot offers an explicit switch to **More private** automatic selection; it never rewrites the manual set silently. Review discloses the selected input count and warns before signing when the resulting funding set combines permanent labels, contains unknown provenance, or spends an address-reused coin. **Max** comes from a non-persisted native drain preview using the active fee rate and exact coin-selection policy; the webview never guesses the spendable amount. It means the maximum currently spendable balance, not an implicit unfreeze: when frozen coins exist, the result states inline and in a toast that they remain in the wallet and links to the existing frozen-coin review.
4. Prepare a real unsigned transaction in Rust and return its authoritative review summary, including every input outpoint, authenticated input amount and sequence, network, locktime, RBF state, output count, and effective fee rate estimated from the descriptor's signed satisfaction weight.
5. Review the permanent label, recipient, amount, fee, total, and network by default. Compact hardware signing preserves the main review's amount-first hierarchy, `To → Label → Network → Network fee → Total` line-item order, type hierarchy, and row separators without repeating a **Transaction to verify** heading inside the already titled modal. One **View more details** disclosure consistently contains fee rate, aggregate input value/count, output count, locktime/RBF state, change amount/address, and the exact PSBT key-origin derivation paths for wallet inputs and change; its compact hardware form separates adjacent rows but adds no rule above the first or below the last row. Exact outpoints and sequences remain bound to and validated from the persisted PSBT in Rust, but are not repeated in the general transaction review. Rust rejects missing, foreign, or duplicate inputs, impossible input/output totals, and any non-recipient output not controlled by the selected wallet. Long recipient and change addresses use `prefix…suffix`; activating one opens the complete grouped, copy-safe address view. On Regtest, a Ledger Bitcoin Test or Trezor review replaces the canonical `bcrt1` recipient/change presentation with a Rust-supplied `tb1` alias only when both encodings decode to the identical PSBT output script.
6. Enter the wallet-specific credential: **Wallet passphrase** for a software-key wallet, or **App PIN** for an external-hardware or multisig wallet. The software-wallet authorization form keeps the authoritative recipient, label, amount, network, fee, total, and optional transaction details visible beside the credential action. Every prepared software, external-hardware, or multisig payment remains visible through the same Overview resume surface after navigation or restart and reloads its exact persisted proposal. Canceling any prepared payment uses the same destructive confirmation, reviews the payment and collected-signature count, and only then marks the proposal canceled. After external signatures satisfy the wallet, hide now-irrelevant signing transports and repeat the signed transaction review before authorizing broadcast. A signed external-hardware or multisig signer row may discard that signer's signature from Groot's local proposal after an explicit warning and confirmation. This preserves the reviewed transaction and is not revocation: any exported or shared PSBT copy may still contain the signature. Rust verifies, signs or authorizes broadcast as appropriate, persists, and clears secrets.
7. Show a durable success state plus a transaction-broadcast toast that explicitly labels the updated figure as the **remaining wallet balance**, never as the payment amount. **Return to wallet** always opens the selected wallet Overview; it never routes a completed multisig payment to Policy.
8. A pending wallet-originated transaction may be accelerated through RBF when it signals replacement. An incoming or outgoing pending transaction may use CPFP when it has a spendable wallet-controlled output. Incoming transaction details never offer sender-side RBF merely because the transaction signals replaceability. Frozen coins remain unavailable to both RBF and CPFP construction and final broadcast; acceleration never implies an unfreeze. RBF first asks Rust for an authoritative quote derived from the original fee/weight, BDK replacement construction, Bitcoin Core's incremental-relay policy, and the candidate replacement's signed size. CPFP asks Rust for an authoritative package quote derived from the parent fee and weight, the candidate child's signed size, and the combined parent-plus-child target rate; the child fee is the additional cost. The default screen leads only with that additional satoshi cost and lets the user continue to review and signing. Fee-rate editing is optional control; CPFP labels it as the package rate because Rust computes the child fee needed to lift both transactions to that target. Original or parent rate, exact minimum, selected/applied target, new or child fee, additional fee, resulting effective rate, recommendation source, and whole-satoshi rounding are optional insight. The initial target remains the greater of a usable Core priority estimate and exactly one sat/vB above the computed minimum; without a usable estimate, the technical disclosure identifies the deterministic replacement-only fallback rather than presenting it as a general fee estimate. A failed initial quote leaves the rate empty rather than presenting zero as a default. The editable decimal target is preserved to BDK's 0.004 sat/vB precision by rounding upward only at the sat/kwu boundary. A rate below the exact minimum returns `fee_rate_too_low`, never insufficient balance. Groot never silently reduces a normal recipient output to fund a replacement. When available change plus the wallet's other spendable coins cannot cover the higher fee, RBF explains that the recipient amount is preserved and tells the user to receive another confirmed coin or wait for the original transaction to confirm. Both acceleration paths create a normal persisted proposal and resume that exact proposal after navigation or restart.
9. After a successful RBF broadcast, Overview, Activity, and transaction details identify the active transaction as fee-increased and link it back to the original. Transaction details lead with a compact visual journey from earlier to newer transaction, visibly shorten both transaction IDs as `prefix…suffix`, and keep the accounting explanation under an optional disclosure. The original remains **Replaced**, links forward to the replacement, and is explicitly excluded from accounting. A rejected or raced replacement never changes the original status. Acceleration success states use the user-facing outcome **Transaction accelerated**, present the relevant payment amount or additional fee at normal confirmation prominence, and keep protocol terminology out of the default message. Every broadcast confirmation uses the standard compact copyable transaction-ID row, aligned primary/secondary actions, and the privacy-disclosed mempool.space action when that explorer is supported. CPFP must never be described as a zero-satoshi payment.

The send surface includes a compact public signer summary throughout the flow. On desktop it occupies the narrow right-hand column beside Intent, Amount & fee, and Review & sign so transaction entry remains immediately reachable; on mobile it stacks above the active card. Software wallets identify Groot on the current device as the signer. External-hardware and multisig wallets show imported signer labels/models and shortened master fingerprints plus the required threshold; a signer is marked signed only from authoritative proposal data. Imported identity never implies that a device is currently connected or healthy. A single-hardware Ledger flow offers its cable and file transports but omits QR signing controls that the signer cannot use.

Completing Send Intent persists one bounded public-only draft for the selected unlocked wallet before Groot enters Amount & fee. The same draft resumes after route navigation or a full app restart and unlock, with selected coins revalidated against the current snapshot. Overview and resumed Send expose **Discard draft** separately from **Resume/Back**. Its compact confirmation names the payment labels once, without a warning panel or a redundant saved-fields inventory, then clears the selected wallet's draft and suppresses Send's normal exit-save so navigation cannot recreate it. It contains no credential, private key, PSBT, device path, or hardware prompt state. Preparing an authoritative proposal clears the draft and transfers continuity to the existing exact-PSBT proposal lifecycle, where the separate proposal cancellation review remains authoritative.

After a PSBT, public-backup, PDF backup, or BIP329 label file is saved on macOS, the success toast offers **Show in Finder**. The webview receives only a short-lived, single-use reveal token; the saved filesystem path remains inside the trusted Rust boundary.

Saved PSBT filenames use the same short proposal identifier plus an explicit collected-signature suffix: `-s0`, `-s1`, or the corresponding higher count. Exporting the same proposal before signing, after a partial signature, and after threshold completion therefore creates distinguishable native save suggestions without placing recipient, label, wallet name, or signer identity in the filename.

When a locked hardware signer has no discovery fingerprint, the signing UI may associate it with the active proposal only when exactly one eligible saved signer belongs to that device family. Multiple eligible same-family signers fail closed and require unlock plus rescan. Ledger's saved policy reference remains available while its policy and transaction decision is pending. If the user requests modal closure during an active device decision, Groot keeps the request visible, gives the modal attention feedback, and instructs the user to reject or cancel on-device; the modal closes after the terminal device response is drained.

Hardware discovery is passive inventory, not an authentication or wallet action.
On macOS it lists every allowlisted candidate whose endpoint the host exposes,
including host-visible locked devices, without requesting unlock, PIN, login,
passphrase, policy registration, address display, signature, or approval. A
Coldcard that has not exposed USB after local unlock is necessarily absent. The
user explicitly chooses one row before Groot opens a vendor session. Every
subsequent account-key, PIN continuation, health, policy, address, and signing
command is bound to that selected non-empty exact transport path; unselected
devices remain untouched. Reconnect, picker close, navigation, timeout,
cancellation, and wallet replacement invalidate transient capabilities, and
multiple unresolved same-family candidates fail closed. Stock HWI 3.2.0

implementations as release blockers.

Transaction history details use the same progressive-disclosure pattern as transaction review. Status, amount, label, date, confirmations, fee, and destination remain immediately visible. Rust derives actual signed-transaction input/output counts, wallet-side input/output amounts, fee rate, locktime, and RBF state for **View more details**, alongside transaction IDs, block/replacement identifiers, self-spend classification, and explorer controls. Metadata unavailable for a legacy synthetic replacement is omitted rather than inferred in the webview. **Increase fee (RBF)** is not offered for a self-spend because Groot preserves one external recipient and amount when constructing a replacement; the native preparation boundary continues to reject an ineligible direct request. Opening an eligible fee-acceleration route immediately presents an explicit preparing state while Groot reads the original transaction and Core fee policy.

When Rust proves that the proposal recipient output belongs to the selected wallet, Review & sign labels the destination **Self-transfer**, states that only the network fee leaves the wallet, and exposes the recipient output's PSBT key-origin path with the input/change paths. Rust also sums every PSBT output controlled by the selected wallet and shows that integer-satoshi total as **Consolidating**, allowing direct comparison with a hardware signer's self-spend review without renderer arithmetic. The renderer never infers wallet ownership or the consolidation amount.

## Activity and transaction details

Search matches the transaction title, payment-intent label, and inherited provenance labels. Direction filters combine with deterministic latest/earliest and largest/smallest sorting without changing wallet state. Time sorting keeps active pending transactions above confirmed history for **Latest first** and below it for **Earliest first**, then orders each group by its timestamp; this prevents a miner-supplied block timestamp from placing a newly seen mempool payment below older confirmed activity. When BDK has no unconfirmed `first_seen` value, Groot reuses the transaction's durable notification observation time instead of fabricating a new time on every snapshot. If pending timestamps are exactly equal, a locally broadcast payment with its permanent intent sorts first for **Latest first** and last for **Earliest first**.

List received/sent transactions with an authoritative typed classification, label, amount, date, and pending/confirmation state. A fee-only transaction whose value outputs all remain wallet-controlled is a **Self-spend**: its displayed wallet debit is the network fee and it has no counterparty address. An RBF conflict set is one payment in Overview and Activity, never two accounting rows: Groot presents the current canonical winner, or the broadcast replacement while confirmation is pending, with the sent amount shown normally. The detail view shows only a concise fee-increase outcome by default; one optional-insight disclosure reveals the original-to-replacement journey, compact identifiers, authoritative available fee rates, and accounting explanation. A successful replacement broadcast is not permanent chain truth; if the canonical graph later selects the original transaction, the same payment row represents that confirmed original while its attempted replacement remains visible only in the timeline. Optional details show the transaction ID, replacement lineage, self-spend classification, and a network-correct explorer action on supported public networks. Opening a third-party explorer carries a short privacy warning. In packaged apps Rust accepts only a valid transaction ID, constructs the exact allowlisted mempool.space HTTPS Mainnet, Testnet4, or Signet transaction path, and asks the OS to open it; failure is shown inline and as a toast. Browser fixtures use the same network/transaction policy. Regtest and unapproved networks never receive a dead public-explorer action. Compact addresses always preserve both identifying ends as `prefix…suffix`; opening one replaces that compact value with the complete grouped, copy-safe view rather than displaying both at once.

## Label interchange

Settings offers explicit **Import JSONL** and **Export JSONL** actions for the standard BIP329 representable subset. Before either action, Groot warns that labels, addresses, transaction/output references, public account keys, and their relationships disclose private wallet history. Export is deterministic and complete for permanent address, known transaction, wallet output/coin, and saved public signer labels. A completed RBF may remove either the superseded original or an unconfirmed replacement that lost to the confirmed original from BDK's current graph; Groot still exports and additively re-imports labels for both exact transaction members and their already-validated wallet outputs from the coherent persisted replacement history. Unbroadcast payment intents, policy names and descriptors, cluster identities, replacement lineage itself, and standalone input provenance are not representable and are omitted without proprietary records. The file never contains seeds, credentials, private descriptors or keys, RPC secrets, or PSBTs.

Import is bounded, exact-network and selected-wallet aware, schema/type validated, and atomic. Duplicate labels are no-ops. A new label is appended to the subject's permanent history under the existing cap; nothing is edited or erased. Foreign references, private material, contradictory spendability, signer-name conflicts, or capacity conflicts fail closed and leave the wallet unchanged. This separate `.jsonl` path does not alter existing profile or public-backup formats and does not implement cross-platform synchronization.

An empty activity view explicitly says that the wallet has no transactions yet. Filtered empty states distinguish no received transactions from no sent transactions.

## UTXOs

Coins default to the newest source transaction first. A compact sort control allows newest/oldest, largest/smallest, and permanent label A–Z/Z–A. Date sorting leaves coins without a known source-transaction timestamp after dated coins. Sorting is presentation-only and never changes selection, freeze state, labels, or spend eligibility.

Show amount, every immutable provenance label as a compact tag, confirmations, and frozen state by default. An exact incoming output inherits only the permanent label assigned to its receive address. Change inherits the deduplicated known provenance-label union of every spent wallet input: co-spending labels A and B produces change carrying both A and B. It is explicitly **Mixed** or **Unknown** when a single source cannot be claimed; an outgoing payment-intent label remains separate and never becomes change provenance. Coin details expose the Rust-derived source transaction, source payment intent when one exists, and the count of wallet inputs in change lineage. Address and outpoint are optional technical details, compacted as `prefix…suffix` until the user opens the full detail view. Users can select UTXOs with either the checkbox or the unfrozen row; pointer hover and a blue selected-row surface make the interaction and current set visible. Freeze and unfreeze require a brief confirmation that names the affected coin or selection and explains the spending-selection effect without exposing an outpoint. Freeze/unfreeze is persisted; frozen coins are excluded from automatic and manual spending until unfrozen. When two or more spendable outputs share a known receive address, mark each affected coin with a calm address-reuse privacy notice without blocking spending. Technical linkage, affected addresses, outpoints, provenance labels, privacy clusters, and totals stay collapsed until the user requests the optional detail. Discreet and locked states never reveal permanent-label text or coin amounts, including accessibility names and filters.

An externally funded descriptor-derived multisig address that Groot never created as a receive request remains honestly **Unknown source**. If that address now controls an observed unspent external output and has never had local address metadata or a label assignment, Coins may offer one explicit initial-label action. Rust binds it to the exact current wallet output and derivation index, atomically creates the used address record and receive-origin label, and rematerializes provenance. It rejects change, spent/foreign/arbitrary outputs, and an existing address record or assignment. This is initial metadata recovery, not editable labels: the assignment can never be changed, while its normalized label text may intentionally reuse an existing wallet label. Hardware-policy verification addresses are labeled as verification references and tell users to create a labeled Receive request before funding.

## Notifications

Durable in-app notification events are produced for:

- local transaction broadcast, with updated balance;
- newly observed incoming transaction, with updated balance;
- first confirmation, with updated balance.

Later confirmations do not create events. Delivery is explicitly acknowledged and may repeat after a crash before acknowledgement; stable event IDs and persistent transaction state make handling idempotent. Persistent transaction state remains the source of truth.

The first successful sync of a newly created or recovered local profile establishes a notification baseline. Existing transaction history is restored silently instead of replaying old receipt and confirmation toasts; only changes observed after that baseline produce new events.

While the unlocked desktop app is running, one centralized foreground scheduler syncs the selected wallet every 35 seconds and immediately when the app returns to the foreground. It stays active across Overview, Activity, Coins, Settings, Receive, and Send; exclusive mutations coordinate their own pause. On unlock, Groot verifies the saved Mainnet node when required, reads and paints the target wallet's persisted snapshot, then starts one immediate automatic sync. Returning to Overview during the same admitted session reads that snapshot without repeating the node connection test or starting another refresh. Automatic sync keeps the Overview layout stable: only the compact top-right spinner and percentage are visible until completion, while the detailed history-progress banner is reserved for an explicit user-requested refresh. A manual refresh continues as one native operation across read-only navigation, and the automatic scheduler remains paused until it settles. Both single-key and multisig Receive expose the same manual refresh action. Subsequent scheduler cycles stay visually quiet. Wallet selection cancels any previous-wallet sync before committing the target. Sync commands never overlap: slow or offline nodes coalesce wake-ups instead of building a queue. Until a saved Core connection is ready, Overview masks unverified wallet data and visibly links to network Settings. Once Core is ready, Groot automatically starts the resumable first scan without a modal or another credential prompt for a generated wallet. Native creation atomically saves the verified node tip as that wallet's birthday because its newly generated keys cannot have earlier activity. Recovered or imported wallets still require an explicit birthday or full-history choice and never silently default to genesis. Manual birthday/full-history and gap-limit controls remain in Settings. The scanner checkpoints every applied block, continues across inactivity locks, and reattaches after unlock or route remount. Before Groot begins any authoritative history scan, Bitcoin Core must be out of initial block download and its tip must have reached the wallet's last verified checkpoint; a pruned node must retain the block immediately before the selected birthday plus every later required block. Later normal scans compare persisted sparse checkpoints with the configured Core chain, construct an in-memory view ending at the highest active-chain agreement when a reorganization invalidated the saved tip, and replay from the saved recovery birthday rather than genesis. A node that is still catching up produces a stable actionable state instead of attempting an ambiguous BDK reconciliation. The replacement chain and stale-checkpoint removal remain staged with all other wallet changes until one atomic successful commit; cancellation or failure leaves the persisted wallet untouched. Normal scans report progress relative to the active checkpoint while the last verified state remains unchanged until that commit. Reusing another wallet's network setup never copies checkpoints or history. Individual transient Core transport failures are retried within a bounded scanner operation; exhausted failures use the stable sanitized network error and never expose JSON-RPC, authentication, endpoint, or transport internals. Remounting Overview reattaches to native progress instead of restarting it. Onboarding, lock, wallet selection, and automatic-lock expiry cancel only the ordinary foreground scan; a resumable first-history scan continues unless explicitly cancelled or the process exits. The Overview refresh action displays the last successfully committed `syncedAt` observation as a relative age and exposes the exact timestamp as supplementary detail; mounting or navigating a route never fabricates **Updated now**. Before the first completed scan the numeric zero is presentation-only and activity is not trustworthy. Successful update events carry the immutable wallet ID, and routes accept them only while that ID remains selected. A successful sync updates visible balance, activity, coins, and receive-address status without navigation or a manual refresh. Offline polling remains quiet; explicit user-requested sync continues to show detailed progress and a durable error whose sanitized description distinguishes Core still syncing, missing pruned history, node permission/configuration, and wallet-state reconciliation without exposing RPC details. Fully terminated background delivery is out of scope.

The foreground scheduler keeps its fixed 35-second post-attempt cadence after both success and failure and stays mounted across every normal wallet route. Quiet automatic attempts do not fabricate an **Updated now** timestamp: the displayed age advances only after a successfully committed snapshot. A manual refresh remains the same native operation when the user navigates to another read-only route.

An explicitly configured remote Core is the fast trusted-server mode. Groot sends
the selected wallet's bounded derived public output scripts to Core's indexed
`scanblocks` operation, then downloads and independently verifies only matching
full blocks. It uses mempool-only `getdescriptoractivity` to fetch only matching
pending transaction identifiers and raw transactions rather than the complete
public mempool. The operator can associate those scripts and wallet activity
with the connection. Settings discloses that tradeoff; private keys, labels,
wallet names, PSBTs, and signing material are never sent. Remote Core requires
Bitcoin Core 29+, a synced basic block-filter index, both RPC permissions, and
the narrowly scoped capability probes documented for the gateway. Only the
synchronous indexed block scan receives a 120-second request bound; health and
ordinary RPC remain short. An offline preflight must still select the correct
single-key, hardware, or multisig command family on retry. Remote mode does not
silently fall back to slow full-block or full-mempool scans. Local
Core and the separate P2P compact-filter source retain their existing privacy
and fallback behavior.

Explicit birthday and genesis rescans use the same indexed remote-Core path as ordinary refresh: sequential bounded server-side `scanblocks` ranges, metadata and full-block downloads only for matching hashes, a sparse verified target checkpoint, and the bounded descriptor-activity mempool pass. Groot does not walk every height or download every block over HTTPS. The shared gateway admits one indexed scan at a time and its outer proxy timeout exceeds the scan-operation bound. Local Core keeps its complete block-by-block recovery path, with guarded per-block checkpoints for interruption recovery.

An explicit Overview refresh cancels and fully drains any scheduler-owned ordinary sync before starting the user-visible operation, then restores the normal automatic interval afterward. Recovery-scan progress reads run away from the native UI thread so frequent status polling does not interrupt animation or input responsiveness.

Freezing or unfreezing coins also pauses and drains the scheduler before changing persistent spendability. The native database mutation runs off the UI thread, and the Coins route applies the confirmed state before automatic sync resumes, so an older snapshot cannot replace the newly frozen state.

In the isolated Mainnet candidate, a validated public BIP48 draft may create an

   Draft progress is neutral before review. Missing-field and policy errors appear only after the user attempts **Review wallet**. Imported-key cards identify the device fingerprint and connection/import method and make the complete public account key readable without horizontal overflow.

Interchange presents the standard multipath `/<0;1>/*` form when the two branches are provably identical apart from branch number; separate receive and change descriptors remain available as optional detail and remain BDK's internal representation.
5. User verifies connected devices where supported and confirms an offline descriptor backup before the wallet can receive funds. Rust then appends an address-specific event containing the verified time, signer fingerprint, device type, and returned public address; only the latest timestamp and fingerprint cross into the UI. A successful result never implies permanent firmware/device trust and **Verify again** appends a new event rather than replacing history. Coldcard signers receive a BIP-380 descriptor export and explicit on-device name, threshold, and fingerprint acknowledgement. Ledger, BitBox02 including Nova, and Jade receive an interactive policy-and-first-address verification task. All device-policy setup is optional during watch-only coordinator creation but must be explicitly deferred; every unfinished signer remains **Setup required**, and first signing opens its device-specific preparation before any transaction request. Before an interactive request begins, Groot shows the Rust-derived first address in the same readable format used by address review and keeps every fingerprint, derivation path, and account xpub available in the standard large identifier view. Devices with an approve/reject address decision persist evidence only after approval plus returned-address validation. Coldcard returns its displayed address automatically and has no address approve/reject step; Groot therefore persists evidence after exact returned-address equality and tells the user to compare the trusted display while it remains visible. On Testnet4, a Coldcard must be configured for Testnet4 and return the canonical `tb1` address exactly. A documented Regtest cross-prefix encoding is accepted only for its constrained device direction after both complete addresses decode to the identical output script, and Groot presents that complete device encoding for exact user comparison. Interactive evidence is descriptor- and fingerprint-bound and append-only. Coldcard's durable file-import acknowledgement uses a distinct scope and is never presented as address proof. Trezor One and Safe 3 have no persistent registration state, so they are marked **No setup needed**, not registered. BitBox02 Nova's pinned-HWI desktop USB path has exact-model local Regtest core and independent clean-profile recovery evidence, with a documented shared-pairing-cache limitation; no original BitBox02 result is inherited, and Testnet4, packaged-candidate, independent-review, and Whisper/Bluetooth rows remain separate. See [`hardware-policy-readiness.md`](hardware-policy-readiness.md).
   Selecting a signer during setup or from a saved wallet reveals its public fingerprint, BIP48 account path, import source, public account key, connection capability, and latest persisted health-check result. The signer’s local display name is editable from this shared detail surface, including filename-derived labels; renaming persists locally but cannot modify signer identity, descriptors, verification evidence, or the hardware wallet. A health check always requires the physical signer, even when its public key was imported by QR, file, or manual entry. One explicit passive inventory supplies an opaque, short-lived path hint. Under one exclusive native lease, Groot opens only that selected path, obtains a fresh BIP48 account key with HWI `getkeypool`, and requires the live type, fingerprint, derivation, and complete account xpub to match the saved identity before Rust persists the result. The renderer cannot submit a health record. Groot keeps only the latest result and timestamp per signer fingerprint; no health-check history is retained. Initial public-key import uses the same exact-path keypool proof before any identity has been saved. A format-only public-record check is not a health check and must not be offered as one. Before USB scanning, Groot states that a signer must already be initialized with a seed and offline backup and that vendor companion apps must be fully quit before Groot can own the USB session. Coldcard must be unlocked with USB communication enabled before its endpoint exists; other supported locked devices may appear before selection, while their selected action still requires the vendor-specific Bitcoin mode or local unlock. A selected locked Model One exposes Groot's PIN-position flow; if it is already unlocked, the exact-path readiness probe continues without asking for matrix input. Safe-family Trezors perform any unlock on-device. When HWI reports PIN and passphrase requirements together, PIN unlock always precedes standard/hidden wallet selection and fingerprint import in both multisig and external single-key setup. A standard Trezor wallet remains valid if passphrase support is enabled later; the resulting hidden wallet is a separate identity that must be added as a separate Groot wallet. An already-paired BitBox02-family device unlocks directly through Groot after scanning; BitBoxApp is used only when Groot explicitly reports that one-time pairing is required, and must then be quit before Groot takes the USB session. A selected BitBox action may report an interrupted secure-session handoff and offer an explicit retry on the same capability; picker discovery itself never starts BitBox unlock. Original BitBox02 and Nova do not display the master fingerprint during single-key import, so their public-data review identifies the imported public account without asking for an impossible fingerprint comparison and requires first-address verification on-device before funds are accepted. Ledger import visibly waits for on-device public-key export approval. Concise Coldcard, BitBox02, Ledger, Trezor, and Jade preparation help is available without exposing advanced descriptor details.
6. Send uses the same labeled **Intent → Amount & fee → Review & sign** stages as single-key wallets and presents the wallet threshold, signer labels/models, and shortened public fingerprints before proposal creation. It then creates and persists an authoritative PSBT. Partial signatures may arrive in any order over hardware, bounded `crypto-psbt` UR v2 QR, or file. A signed row may discard that signer's signature from Groot's local proposal after a warning and confirmation; this is not revocation, and the UI states that previously exported or shared PSBT copies may still contain the signature. PSBT export uses a native save dialog, validates the payload before writing, and suggests a short ASCII `groot-xxxxxxxx.psbt` filename suitable for hardware-wallet removable-media flows. Canceling a proposal requires a destructive confirmation that reviews the payment and states how many collected signatures will be discarded; the initial cancel action never deletes directly. Leaving the signing page also requires confirmation and explicitly preserves the proposal and collected signatures for resumption.
7. Rust validates every imported ECDSA partial signature against the actual PSBT input sighash and signer public key before it can count, merge, persist, or appear in progress. Matching valid PSBTs merge without changing any reviewed non-signature field, and broadcast remains unavailable until the descriptor is satisfied and the transaction is finalized. Hardware discovery can be refreshed without closing the modal; identity and signing failures stay visible inside that modal with a recovery action. A terminal hardware-signing result closes any address-detail overlay opened from that modal so the durable parent success or error state cannot remain hidden. A connected Ledger, BitBox02, or Jade without saved policy evidence cannot jump directly to transaction signing: Groot first shows the expected threshold and every full fingerprint, BIP48 origin, and public account key, then verifies the device-returned first address. Ledger may repeat its wallet-policy approval during the later signing request because the current HWI boundary does not preserve Ledger's host-side wallet HMAC between CLI calls.
8. Hardware-only wallets use an app PIN verifier but have no coordinator-held mnemonic or private key.
9. Setup offers Standard and self-managed Recovery on a dedicated policy-choice screen, plus a disabled **Assisted recovery · Coming soon** preview, followed by a separate wallet-name and policy-configuration screen. Standard means the selected threshold is always required. A standard 2-of-3 can be assigned assisted-signing roles: two independent owner keys and one trusted-helper key let either owner sign with the helper or both owners sign together, while the helper can never spend alone. This is guidance for the standard descriptor, not a distinct persisted policy type. Recovery uses an immediate 2-of-3 primary branch plus one delayed key and offers reviewed 4,320-, 13,140-, and 26,280-block presets, defaulting to 4,320. Existing Inheritance wallets remain compatible with their saved heir role and delay; new setup does not imply that a different name and delay form a distinct security template. Approximate time is always secondary to exact blocks. Descriptor logic is hidden by default but available before creation.
   Delayed-policy hardware support follows ADR 0044. The pinned HWI 3.2.0 boundary supports only standard multisig; delayed setup therefore accepts bounded file/manual public keys and offline PSBT exchange but does not offer USB enrollment, hardware address display, policy registration, or signing. BitBox02, Ledger, and Jade firmware are candidates for a future reviewed adapter and exact-model Testnet4 campaign, not currently supported delayed-policy devices. Existing delayed wallets and proposals remain compatible and unchanged.
   Guided delayed-recovery templates require four independent keys: three primary keys form the immediate 2-of-3 branch and a fourth recovery-only key is excluded from that branch. Reusing any primary signer as the sole delayed recovery key is rejected in both UI policy construction and Rust validation. The delayed key is an independent single-key spending branch, not a co-signer: after an individual received output has aged through its relative block delay, that key can spend the matured output without either normal 2-of-3 signature. Every newly received output starts its own delay. Setup states this consequence visibly and offers optional plain-language detail for Recovery and Inheritance.
   Groot tracks the relative delay independently for every unspent output. User-facing states name the security fact instead of the mechanism: **Wait starts after confirmation**, **Backup key protected**, **Recovery/heir key available in N blocks**, and **Recovery/heir key can spend**. Exact remaining blocks are authoritative and approximate duration is secondary. The approaching window begins at the smaller of the complete delay and the larger of 1,008 blocks or 10% of the delay: this preserves at least one expected week for coordinating the normal 2-of-3 keys at production defaults and gives long inheritance policies a proportional review window. Overview, Coins, and Policy keep durable inline state; singular and plural counts are grammatically exact. Ordinary Send lists only the primary-branch signers and offers a direct recovery/heir-key flow when an eligible coin exists. Approaching and mature threshold crossings also create restart-safe notifications. A backward reorg immediately regresses inline state without an alert and rearms the crossed threshold so a later forward crossing alerts once again.
   Countdown and delayed-spend claims require a recently verified chain observation. After 30 minutes—three expected block intervals—or when no verified observation exists, Groot keeps the saved state visible but pauses exact countdown and approximate-time presentation until sync succeeds. Copy must never say that a coin expires: availability leaves the 2-of-3 path valid while adding the independent single-key path and therefore changing the coin's security model. Ordinary Send remains on the reviewed immediate 2-of-3 path. A separate mature-coin action creates a one-input, one-output delayed-key sweep; only the persisted recovery/heir signer set is eligible, and finalization rechecks maturity after a reorg.
   A mature coin may optionally use **Restart recovery wait** (legacy Inheritance: **Postpone heir access**), a purpose-built normal 2-of-3 self-spend. Rust revalidates a recent chain tip, the verified delayed policy, exact mature outpoint, and unfrozen state; selects exactly that one input; drains it to one fresh wallet-controlled internal output; and persists the existing authoritative multisig proposal shape. The review states that the fee reduces the replacement coin, the transaction remains permanently visible onchain, no other existing coin group is linked, and the replacement coin starts its fresh relative-block wait only after confirmation. A stale tip, immature/missing/frozen coin, unsupported policy, extra input, or insufficient fee balance fails closed. This is distinct from the dedicated recovery/heir-key sweep. Deterministic funded Regtest covers independent coin ages, restart deduplication, backward reorg, re-maturity, isolated renewal, self-spend classification, the replacement confirmation boundary, and a funded delayed-key spend. Testnet4 physical-signing evidence remains a release gate.

Every explicit USB discovery request performs one passive OS inventory on macOS. Rust bounds and validates its records, omits out-of-scope families and models before any path is cached, rejects duplicate or conflicting non-empty paths among the remaining approved records, caches those approved candidates behind opaque short-lived capabilities, and only then filters the result to eligible saved families and fingerprints. No HWI process or vendor session starts during this scan. The cache may authorize only a selected action from that exact discovery flight; it never satisfies a later explicit discovery or **Scan again** request, so unplugged devices disappear after the next completed scan. Selecting a uniquely path-addressable candidate redeems its opaque capability into one exact-path HWI operation, while Rust still requires a fresh full identity match before accepting any account key, health result, policy/address proof, or signature. A selected BitBox action may retry only HWI's typed disconnected, locked, or busy handoff results, at most three attempts on the same path under the existing lease; cancellation and every identity or content failure remain terminal. Multiple unresolved paths for the same family fail closed. A selected Model One uses Groot's bounded PIN flow, Safe-family Trezors unlock on-device, and Coldcard remains absent until local unlock exposes USB. Concurrent callers share one native inventory flight and cache epoch, and **Scan again** remains available after empty, failed, and partial results.

HWI's exact Jade `Network type inconsistent with prior usage` response is a
stable `hardware_wrong_network` failure, not a generic locked-device error.
Groot explains that the PIN-saved Jade wallet and the active Groot network must
match; the renderer never receives arbitrary HWI stderr or device text.

After discovery returns a fingerprint that exactly matches a saved signer, wallet-scoped device lists show that signer's current user-defined name. The HWI factory/model label remains the fallback for locked, unmatched, and initial-import devices and is never used to infer identity.

Testnet4 hardware commands use HWI's explicit `testnet4` chain except for Jade. HWI 3.2.0's Jade adapter has no Testnet4 mapping and uses its `test` selector for Jade's shared test-network family, so Groot applies that selector only to exact-device Jade operations; wallet derivation and every saved-identity check remain Testnet4 authoritative. Cached paths are hints rather than identity. Disconnect, timeout, cancellation, wallet switch, or scan-generation change revokes them; the user must explicitly scan again after reconnect. Groot never retries discovery or an interactive device request automatically.

## Interoperable backups

Standard multisig wallets export and recover the public four-line BIP129/BSMS 1.0 descriptor record. Recovery also accepts bounded public descriptor text used by Groot and hardware-wallet workflows: a BIP-389 multipath descriptor, an explicit receive/change pair, or a checksummed standard `/0/*` receive descriptor whose `/1/*` change branch is reconstructed and validated. Imports are size bounded, public-only, descriptor parsed, network checked, and verified by deriving their first address; conflicting explicit and portable branches fail closed. Groot JSON retains the custom recovery-policy metadata and signer display labels needed to reconstruct that public coordinator. It does not contain the isolated wallet database's transaction history, receive/payment assignments, proposals, provenance, or label suggestions; preserving those local records requires preserving the wallet profile/database. The wallet app PIN re-authorizes export from protected local coordinator state even when the wallet view is already open; every failed export attempt participates in the persisted per-wallet throttle. It does not encrypt the exported public file. The export cannot spend, but exposes address derivation and wallet activity, so the UI labels it private financial metadata. Users can copy descriptors or save BSMS, JSON, and a human-readable QR PDF through explicit native save dialogs. A canceled dialog is silent; a successful macOS save offers **Show in Finder** without exposing the selected path to the webview. Deletion requires a successful recovery test, exact wallet name, app PIN, and a final irreversible confirmation modal. BIP129 encrypted coordinator/signer rounds are not implemented.

## Out of scope

Public Mainnet distribution, Lightning, arbitrary custom Miniscript editing, editable labels, contacts, cloud sync, background push while fully terminated, Payjoin sender/receiver sessions, and fiat purchase/sale. Delayed-branch coordinator spending, decaying multisig, expanding multisig, and BIP129 encrypted signer rounds remain later work described in `docs/roadmap.md`. Optional compact-filter/P2P sync is a confirmed-only test-network feature gated by ADR 0031; Payjoin V2 URI parsing is foundation only and sends no protocol traffic.

## Language and local preferences

Lock waits for coordinated hardware and ordinary sync cancellation on a blocking
worker before showing the locked route, so contention cannot stall the native window
event loop. Cancelling a sync preserves the previous atomically committed snapshot
and successful-sync timestamp. After the selected profile loads, the locked route
focuses its credential input.

- English, French, and Spanish are selected in the global **App appearance** section of Settings. The preference is stored locally, survives app relaunches, is applied before first paint, and is never synchronized over the network.
- In the multi-network desktop app, **Settings → Network services → Bitcoin network** offers Regtest, Testnet4, and Mainnet. Confirming a different network stores the non-secret choice natively and restarts Groot. The old network remains untouched and switching back restores only its isolated wallets and node settings. A Mainnet confirmation explicitly warns that it uses real bitcoin. ADR 0069 defines the approved v0.4.96 GA product shape.
- Every network presents the configured Core service as one **Bitcoin Core connection** setting. Regtest and Testnet4 show a separate **Wallet activity sync** row only while compact filters are selected, because activity discovery is then genuinely independent from Core fees and broadcast. Mainnet requires Core for all three and never shows the extra row.
- The unlocked desktop shell provides keyboard shortcuts: Command/Ctrl+1, +2, +3, and +4 open Overview, Activity, Coins, and Settings; Command/Ctrl+Shift+R or +S opens the selected wallet's Receive or Send flow; and Command/Ctrl+L immediately locks only the selected wallet. Settings presents the platform-correct keys. Shortcuts are inert during startup, onboarding, lock, text entry, and dialogs. Lock is the only shortcut that mutates wallet session state; it prevents a concurrent wallet selection, cancels coordinated hardware and sync work, and invokes the existing native lock command before showing the unlock route. It never submits, signs, broadcasts, or discards transaction data. The lock shortcut is neither shown nor active in browser prototypes and mobile builds.
- On native launch, Groot renders the canonical SVG lockup on a neutral branded startup surface only while Rust confirms the selected wallet's session state. The lockup reveals once from left to right; reduced-motion users receive the same brief gate with a static mark. Wallet balances, activity, actions, and other authenticated routes must never appear—even briefly—before the selected wallet is confirmed unlocked. A locked or expired session routes to the wallet lock screen before authenticated content mounts.
- The shared localization boundary covers all frontend product copy, including routes, modals, loading and error states, toasts, accessibility names, recurring statuses, and grammatical count labels. English source copy is the stable catalog key; the localization quality gate rejects uncatalogued rendered English. Native errors are localized by stable category or a localized safe fallback without changing wallet contracts or trusted Rust behavior.
- Wallet names, permanent labels, addresses, descriptors, transaction data, and user-entered text remain byte-for-byte user or protocol data and are never translated.
- A wallet may be software single-key, external-signer single-key, or descriptor multisig. Each profile has isolated storage, app credential, descriptor identity, proposals, labels, and node configuration.
- External-signer wallets store public BIP84 descriptors only. Their Groot app PIN is distinct from any optional hardware-signer seed passphrase.
- External-signer Overview exposes **Health check** in the wallet actions menu, and Settings exposes the same **Hardware signer identity & health** detail. Both entry points share the latest wallet-scoped result. Settings shows an honest **Checked**, **Attention**, or **Not checked** badge and, after an attempt, its locally formatted event time. An explicit aggregate scan supplies only an opaque path hint; under one exclusive lease the native health operation freshly reads and matches the device type, fingerprint, BIP84 derivation, and complete account xpub, revalidates the selected wallet, and atomically persists the result. The device path is never persisted, and the renderer cannot author a health result.
- An unlocked external-signer wallet can export its checksummed public receive descriptor only after fresh app-PIN authentication. The native, user-mediated save path produces an importable watch-only backup; the UI warns that it cannot spend but reveals the wallet's complete activity. Importing that descriptor must reconstruct the same receive and change descriptors without access to the hardware seed.
- USB, SD-card/file, manual descriptor, and QR-text public imports converge on the same Rust validation. Hardware passphrases must be selected on the device where supported. A Trezor may use a hidden passphrase wallet for one Groot profile and its seed-only standard wallet for another; selecting the standard wallet requires an explicit confirmation and binds the imported fingerprint to that signer.
- A directly connected signer matched to the wallet may return vendor-normalized transaction or public PSBT metadata. Groot never adopts those returned fields: it extracts only partial signatures and accepts them only when their public keys, fingerprints, SIGHASH_ALL types, and cryptographic verification match the untouched reviewed proposal. A signature made for changed inputs, outputs, amounts, sequences, prevouts, or locktime therefore fails closed. File, text, and QR imports additionally require explicit transaction and fee-source equality before signature validation.
- Multisig signing PSBTs include the authenticated policy's public account keys and origins so hardware wallets can reconstruct the BIP48 policy. Groot may add the same public metadata to an older active proposal only in the temporary device-signing copy; the persisted reviewed PSBT accepts only valid new signatures. A device response without its signature leaves the proposal unchanged and must not be described as an already-used signer unless that signer was already present on every input.
